# 1.7. Тонкий HTTP-адаптер и сборка приложения

## <Part kind="problem" /> Проблема: обработчик, который знает всё

Шесть уроков мы строили мессенджер изнутри: домен с правилами, <T id="use-case">use case'ы</T>, хранилища за <T id="hexagonal-port">портами</T>, ошибки, <T id="cancellation">отмену</T>, тесты. Снаружи его пока не потрогать: нет ни одного <T id="http">HTTP</T>-обработчика, нет `main`. В этом уроке мы прикрутим к сервису вход и соберём его в процесс, который отвечает на `curl`.

Самый короткий путь выглядит так:

<!-- go-check -->

```go
package snippet

import (
	"encoding/json"
	"net/http"
	"sync"
	"time"
)

// Message — доменная структура мессенджера: поля неэкспортируемые.
type Message struct {
	id     string
	text   string
	sentAt time.Time
}

type Store struct {
	mu   sync.Mutex
	msgs map[string][]Message
}

func (s *Store) Append(chatID string, m Message) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.msgs[chatID] = append(s.msgs[chatID], m)
	return nil
}

// sendMessage сам разбирает JSON, сам ходит в хранилище и сам решает, что ответить.
func sendMessage(store *Store) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		var req struct{ Text string }
		if err := json.NewDecoder(r.Body).Decode(&req); err != nil { // тело без лимита
			http.Error(w, err.Error(), http.StatusInternalServerError)
			return
		}
		msg := Message{id: "m1", text: req.Text, sentAt: time.Now()}
		if err := store.Append(r.PathValue("id"), msg); err != nil {
			http.Error(w, err.Error(), http.StatusInternalServerError) // текст сбоя — наружу
			return
		}
		_ = json.NewEncoder(w).Encode(msg) // клиент получит {}
	}
}
```

Код компилируется и даже работает. Но в нём три беды.

**Обработчик знает про хранилище.** Правило «писать может только участник чата» придётся проверять прямо здесь — и ещё раз в обработчике <T id="websocket">WebSocket</T> из модуля 3, и ещё раз в gRPC из модуля 6. Это тот самый обработчик, который делает всё, из урока [1.1](./01-architecture).

**Клиент получает пустой объект `{}`.** Пакет `encoding/json` видит только экспортируемые поля, а у доменного `Message` они все с маленькой буквы — так домен защищает себя от изменений в обход правил (урок [1.2](./02-domain)). «Исправить» это, сделав поля экспортируемыми и навесив теги `json`, ещё хуже: API становится слепком домена. Переименовали поле в домене — сломали всех клиентов. Захотели добавить в домен служебное поле — оно утекло в ответ.

**Любая ошибка — 500.** Битый JSON от клиента, несуществующий чат, сбой <T id="database">базы</T> — для клиента всё одинаково «сервер сломался». Хуже того, текст ошибки уходит наружу: `` failed to connect to `user=messenger database=messenger`: 10.0.3.7:5432 (db-1.internal): failed SASL auth: FATAL: password authentication failed for user "messenger" (SQLSTATE 28P01) `` расскажет атакующему, какая у вас база и как зовут её пользователя. А `json.NewDecoder(r.Body)` без лимита прочитает в память тело любого размера, сколько бы гигабайт ни прислали.

Подумайте, прежде чем читать дальше: что должно остаться в обработчике, если правила живут в домене, а сценарии — в use case'ах? И где тогда решается, что `ErrNotMember` — это 403, а не 500?

## <Part kind="theory" /> Ведущий адаптер: разобрать, вызвать, ответить

В уроке [1.1](./01-architecture) мы разделили <T id="adapter">адаптеры</T> на ведомые (их зовёт приложение — хранилища) и ведущие (они зовут приложение). HTTP-обработчик — ведущий адаптер. У него ровно три шага:

1. **Разобрать** запрос: путь, заголовки, строку запроса, тело — в простые значения Go.
2. **Вызвать** use case с `r.Context()` — тем самым <T id="go-context">контекстом</T>, который отменится, если клиент уйдёт (урок [1.5](./05-context)).
3. **Смаппить** ответ, то есть явно перевести из одного представления в другое (это делает <T id="mapper">маппер</T>, о нём ниже): результат use case'а — в JSON, ошибку — в статус и тело ошибки.

«Тонкий» значит: **бизнес-правил в адаптере нет**. Адаптер не проверяет длину текста, не решает, кто участник чата, не выдаёт номер сообщения. Он проверяет только то, что относится к самому HTTP: тело — JSON, а не что-то иное; оно не больше лимита; `limit` в строке запроса — число. Любое правило, которое имело бы смысл и для WebSocket, и для gRPC, адаптеру не принадлежит: иначе его придётся писать трижды.

Проверка простая: если завтра появится второй транспорт, сколько кода из обработчика придётся повторить? В тонком адаптере — ничего, кроме разбора и маппинга, а они у каждого транспорта свои.

## <Part kind="theory" /> Маршруты: ServeMux с шаблонами

До Go 1.22 стандартный маршрутизатор `http.ServeMux` умел только префиксы путей: метод и `{id}` приходилось разбирать руками или брать стороннюю библиотеку. С Go 1.22 шаблон маршрута выглядит так:

```text
POST /chats/{id}/messages
```

- **Метод** в начале шаблона. Запрос с другим методом этот шаблон не выберет. Шаблон с `GET` подходит и для `HEAD`.
- **`{id}`** — подстановка (wildcard): совпадает с одним сегментом пути. Значение достаётся через `r.PathValue("id")`. `{rest...}` в конце шаблона захватывает весь остаток пути.
- **Приоритет** — у более специфичного шаблона. `GET /chats/new` специфичнее, чем `GET /chats/{id}`: первый подходит для подмножества запросов второго. Поэтому оба можно зарегистрировать, и `/chats/new` уйдёт в первый, а `/chats/42` — во второй. Порядок регистрации роли не играет.
- **405 вместо 404.** Если путь подходит под какой-то шаблон, но метод — нет, `ServeMux` сам отвечает `405 Method Not Allowed` и ставит заголовок `Allow` со списком методов, которые для этого пути есть. Обработчик об этом не заботится.

Если два шаблона подходят для одних и тех же запросов, а специфичнее ни один, — `ServeMux` паникует **при регистрации**, а не при запросе. Почему так и как он вообще выбирает шаблон — «Под капотом» в разделе кода.

У мессенджера пять маршрутов:

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /users` | `{"username","display_name"}` | 201 `{"id","username","display_name","created_at"}` |
| `GET /users/{id}` | — | 200, тот же объект |
| `POST /chats` | `{"kind":"direct","member_ids":[…]}` или `{"kind":"group","title":"…","member_ids":[…]}` | 201 — создан, 200 — личный чат для этой пары уже был; `{"id","kind","title","member_ids","created_at"}`, `title` у личного опускается |
| `POST /chats/{id}/messages` | `{"text"}` | 201 `{"id","chat_id","author_id","text","seq","sent_at"}` |
| `GET /chats/{id}/messages?after=0&limit=50` | — | 200 `{"messages":[…]}` |

Это API на конец части 1a. В части 1b он изменится: пути получат префикс `/v1` (урок [1.8](./08-resources)), история станет страницей `{"items":[…],"next_cursor":…}` с курсором вместо `after` (урок [1.11](./11-pagination)), у сообщения появится обязательный `client_message_id` (урок [1.12](./12-idempotency)), а регистрация потребует пароль (урок [1.13](./13-passwords)).

Три маршрута `/chats` требуют заголовок `X-User-ID` — кто действует. О нём ниже. Время в ответах — строка RFC 3339 в UTC: `2026-10-13T13:18:14.324988718Z`. Клиенту не нужно гадать, в каком часовом поясе сервер.

Обратите внимание на 200 у повторного `POST /chats`. Use case для пары, у которой личный чат уже есть, возвращает существующий чат с `Created=false` (урок [1.4](./04-usecases)). Отвечать на это 201 Created было бы неправдой: ничего не создано. 200 и тот же объект говорят клиенту «вот ваш чат», и повторная отправка запроса безопасна.

## <Part kind="theory" /> DTO и маппер: два языка на границе

<T id="dto">DTO (data transfer object, объект передачи данных)</T> — тип, который описывает форму данных на проводе. В адаптере чатов их пять: `createChatRequest`, `chatResponse`, `sendMessageRequest`, `messageResponse`, `listMessagesResponse`. Все неэкспортируемые: за пределами пакета адаптера они никому не нужны. И только у них есть теги `json:"chat_id"` — имя поля в API задаётся здесь.

**Маппер (mapper)** — функция, которая явно переводит одно в другое: `toMessageResponse(domain.Message) messageResponse`. Она читает домен через методы (`m.Seq()`, `m.SentAt()`), а не через поля, и раскладывает по полям DTO: время — в строку RFC 3339, `ChatID` — в строку.

Направление зависимости такое же, как везде в мессенджере: адаптер импортирует домен, домен про адаптер не знает. В домене нет ни одного тега `json`. Импортировать `encoding/json` домену запрещает правило `depguard` из урока [1.1](./01-architecture), а вот сами теги <T id="linter">линтер</T> не поймает: тег — просто строка в объявлении поля, импорта ему не нужно. Их отсутствие держится на договорённости и ревью.

Что это даёт на практике:

- **Переименование в домене не ломает клиентов.** Поле `sentAt` в домене можно назвать `postedAt` — маппер поправится одной строкой, а JSON останется `"sent_at"`.
- **Внутреннее не утекает.** У чата есть `version` для <T id="optimistic-locking">оптимистической блокировки</T> и `lastSeq`. Клиенту они не нужны, и в `chatResponse` их нет. Если бы ответом был сам <T id="aggregate">агрегат</T> с тегами, номер версии стал бы частью API, и поменять схему блокировки было бы нельзя.
- **Вход не может записать лишнего.** В `sendMessageRequest` одно поле — `text`. Автор берётся из заголовка, чат — из пути. Клиент, который пришлёт `"author_id"` в теле, получит 400, а не сообщение от чужого имени (атака mass assignment, о ней ниже).

Одна мелочь, на которой спотыкаются. Use case `ListMessages` для пустой истории возвращает `nil`-срез, а `encoding/json` пишет `nil`-срез как `null`. Клиент на JavaScript, который делает `response.messages.length`, упадёт. Поэтому маппер создаёт срез через `make(…, 0, len(msgs))`: пустая история — `{"messages":[]}`. Это проверяет отдельный тест обработчика.

## <Part kind="theory" /> Разбор тела на границе

Тело запроса — ввод от недоверенной стороны, и его разбор — первая линия защиты. Общий для обоих адаптеров помощник `httpjson.Decode` делает четыре проверки.

**Тип тела.** Если `Content-Type` указан и это не `application/json` (параметр `charset=utf-8` допустим), — `415 Unsupported Media Type`. Если заголовка нет вовсе, разбор идёт дальше: по RFC 9110 (§8.3) получатель без `Content-Type` вправе сам определить тип, а строгий декодер всё равно отвергнет то, что не JSON. Ловушка, на которой мы споткнулись сами: `curl -d '…'` **без** `-H 'Content-Type: application/json'` не оставляет заголовок пустым, а ставит `application/x-www-form-urlencoded` — такой запрос получит 415. Поэтому во всех примерах урока заголовок указан явно.

**Размер.** `http.MaxBytesReader(w, r.Body, 1 МиБ)` оборачивает тело: прочитать больше лимита нельзя, `Read` вернёт ошибку типа `*http.MaxBytesError` (тип появился в Go 1.19; раньше узнать её можно было только по тексту). По ней адаптер отвечает `413 Content Too Large` (в старых RFC — Request Entity Too Large). Обёртке нужен `w` не случайно: она сообщает серверу, что после ответа соединение надо закрыть, — непрочитанный остаток тела иначе пришлось бы дочитывать перед следующим запросом. Почему 1 МиБ? Самое большое тело мессенджера — группа на 200 участников, это около 8 КиБ id; сообщение до 4096 символов — не больше 16 КиБ в UTF-8. Лимит с большим запасом, но 2 ГБ в память он прочитать не даст.

**Только известные поля.** `dec.DisallowUnknownFields()` превращает неизвестное поле в ошибку. Без этого `{"text":"a","author_id":"…"}` разобрался бы молча, а опечатка клиента `{"txt":"a"}` дала бы пустой текст и непонятный ответ «пустое сообщение».

**Ровно один объект.** `json.Decoder` читает поток: первый `Decode` разберёт `{"text":"a"}` и остановится, не глядя на то, что дальше. Поэтому после него делаем второй `Decode` и ждём `io.EOF`. Если там второй объект (`{"text":"a"}{"text":"b"}`) или мусор — 400. Мы проверили и неочевидный случай: если первый объект короткий, а лимит кончается на «хвосте» после него, второй `Decode` тоже возвращает `*http.MaxBytesError`. Значит, проверять тип ошибки нужно и во втором вызове, иначе вместо 413 клиент получит 400.

Что из этого защита, а что удобство? Лимит размера — защита: OWASP API Security Top 10 2023 вынес неограниченное потребление ресурсов в отдельную категорию **API4:2023 Unrestricted Resource Consumption**, и лимит на размер тела там — первая мера. Запрет неизвестных полей — защита от **mass assignment** (в редакции 2023 — часть категории API3:2023 Broken Object Property Level Authorization): клиент не может дописать в запрос поле, которое сервер не собирался принимать. Остальное — удобство для честного клиента: понятная ошибка вместо странного поведения. Подробно об OWASP и защите API — модуль 6.7.

## <Part kind="theory" /> Таблица ошибок: виноват клиент или сервер

Use case возвращает ошибку. Какой статус отдать? Ответ — в одной функции `httperror.Write` из `platform/httperror`. Это **единственное место**, где ошибка, которую вернул use case или разбор тела, становится HTTP-ответом: обработчики только зовут её. Часть таблицы общая для всех контекстов — ошибки разбора тела, уход клиента, истёкший <T id="deadline">срок</T>, «всё остальное»; её знает `httperror.Write`. Строки про валидацию и <T id="sentinel-error">сигнальные ошибки</T> знает только свой контекст — их адаптер передаёт функцией `problemFor`. В уроке [1.3](./03-errors) мы набросали эту таблицу; вот она целиком:

| Ошибка | Статус | `code` |
|---|---|---|
| `errors.As` → `*ValidationError` | 400 | `invalid_input` и `field` |
| `ErrUserNotFound`, `ErrChatNotFound` | 404 | `not_found` |
| `ErrNotMember` | 403 | `not_member` |
| `ErrUsernameTaken` | 409 | `username_taken` |
| `ErrConcurrentUpdate` | 409 | `conflict` |
| `context.Canceled`, и отменён `r.Context()` | ответа нет, в лог на уровне Info | — |
| `context.DeadlineExceeded` | 503 | `timeout` |
| всё остальное | 500 | `internal`, общее сообщение; детали — только в лог |
| ошибки разбора тела | 400 / 413 / 415 | `bad_json` / `body_too_large` / `unsupported_media_type` |
| нет `X-User-ID` или в нём не UUID | 401 | `unauthenticated` |

Тело ошибки у всего API одно: `{"error":{"code":"…","message":"…","field":"…"}}`. Клиент ветвится по `code` — это стабильный машинный ключ. `message` — для человека, его можно переписать, не сломав клиентов. `field` есть только у ошибок валидации: по нему клиент подсветит поле формы.

**4xx против 5xx — кто виноват.** Статусы 4xx говорят «ошибся клиент, и он может это исправить»: поправить JSON, выбрать другое имя, вступить в чат. Статусы 5xx — «сломались мы, клиент ни при чём; можно повторить позже». Разница не косметическая. Клиенты и прокси могут повторить запрос на 5xx — вдруг сбой временный — и не повторяют на 4xx: тот же запрос даст ту же ошибку. Мониторинг будит дежурного по доле 5xx (<T id="error-budget">бюджет ошибок</T> из урока [0.2](../00-foundation/02-what-is-system-design)). Если сбой базы отдавать как 400, дежурный о нём не узнает; если опечатку клиента отдавать как 500, дежурного разбудят зря.

Отсюда тонкость, которую легко пропустить. Генератор id у нас выдаёт строку, и use case разбирает её через `domain.ParseChatID`. Если генератор сломается и выдаст не UUID, разбор вернёт `*ValidationError` — и таблица честно превратит его в 400 «вы прислали неверные данные». Но клиент ничего неверного не присылал! Поэтому use case'ы оборачивают сбой генератора **без** `%w` (урок [1.4](./04-usecases)): цепочка обрывается, `errors.As` не находит `ValidationError`, и ошибка уходит в строку «всё остальное» — 500. Так тип ошибки говорит, кто виноват, а не где она возникла.

**Не раскрывать внутреннее.** На 500 клиент получает `"внутренняя ошибка сервера"`, а полная цепочка — `` send message (попытка 1): failed to connect to `user=messenger database=messenger`: 10.0.3.7:5432 (db-1.internal): dial error: dial tcp 10.0.3.7:5432: connect: connection refused `` — уходит в лог `slog.Error` с методом и путём запроса. Для отладки этого достаточно, а атакующему не достаётся ничего.

**`context.Canceled` — отвечать некому.** Если клиент закрыл соединение, сервер отменяет `r.Context()`, хранилище прерывается и use case возвращает ошибку с `context.Canceled` в цепочке. Писать ответ бессмысленно: его никто не прочитает. Это и не сбой сервера, поэтому в лог — на уровне Info, а не Error: иначе каждый пользователь, закрывший приложение посреди запроса, будил бы дежурного. Но молчим, только если отменён именно `r.Context()`: `context.Canceled` от какого-то внутреннего контекста при живом клиенте — наш сбой, и он идёт в строку «всё остальное», 500, — иначе клиент получил бы пустой ответ 200.

**`context.DeadlineExceeded` — 503.** Срок обработки истёк: сервер не успел. Виноваты мы или перегрузка, а не клиент, поэтому 5xx. Из пятисотых выбран 503 Service Unavailable: он говорит «временно, повторите позже». В этом уроке сроков в мессенджере ещё нет, но строка в таблице есть: срок запросу поставит <T id="middleware">middleware</T> `Timeout` из урока [1.17](./17-service-in-container), и обработчики менять не придётся. (В уроке 0.3 обработчик отвечал на дедлайн 504 Gateway Timeout. 504 по смыслу — ответ прокси, который не дождался вышестоящего сервера; наш сервис сам и есть конечный сервер, поэтому 503.)

**Порядок проверок важен.** Сначала ошибки разбора и валидации, потом сигнальные ошибки домена, потом контекст и в конце — «всё остальное». Ошибка может нести в цепочке несколько признаков сразу: с Go 1.20 `fmt.Errorf` принимает несколько `%w`, а `errors.Join` склеивает ошибки, и `errors.Is` найдёт в такой цепочке и `ErrConcurrentUpdate`, и `context.Canceled`. Таблица выбирает первое совпадение сверху, и порядок фиксирует, какой признак важнее.

**401 против 400 у `X-User-ID`.** Заголовок разбирает обработчик **до** вызова use case. Нет заголовка или в нём не UUID в нижнем регистре — 401 `unauthenticated`: «не знаю, кто вы». Если бы обработчик отдал сырую строку в use case, тот вернул бы `ValidationError{Field: "user_id"}`, и клиент получил бы 400 «неверные данные» — смысл другой. А вот корректный UUID пользователя, которого нет, — это 400 с `field: "creator_id"` при создании чата и 403 при отправке и чтении: такого пользователя нет ни в одном чате. Отдельного 401 «нет такого пользователя» мы не делаем сознательно: настоящая проверка личности появится только с JWT, а пока несуществующий id — просто неверные входные данные. Так записано в <T id="adr">ADR</T>-0002 — о нём в следующем разделе.

В уроке [0.3](../00-foundation/03-request-path) обработчик отвечал 401 на **любую** ошибку `h.auth.UserID(r)`. Теперь видно, что не так: если упало хранилище сессий, это не «вы не представились», а сбой сервера — 5xx. Правильная проверка различает «клиент не доказал, кто он» (401) и «мы не смогли проверить» (500) — ровно как таблица выше различает `ValidationError` и всё остальное.

## <Part kind="theory" /> X-User-ID: заглушка до JWT

Use case'ам чатов нужно действующее лицо: кто создаёт чат, кто пишет, кто читает. Аутентификации — проверки, что клиент тот, кем назвался, — в мессенджере пока нет: выпуск и проверка токенов JWT — тема части 1b. Мы выбрали заглушку: клиент присылает свой id в заголовке `X-User-ID`. Рассмотренные варианты и последствия записаны в ADR `messenger/docs/adr/0002-x-user-id-до-jwt.md`.

**Почему так нельзя в проде.** Заголовок присылает клиент, и подделать его может любой: `curl -H "X-User-ID: <id Боба>"` — и вы читаете переписку Боба. Сборку части 1a запускают только на своей машине. Комментарий у константы `UserIDHeader` в `auth.go` повторяет это предупреждение.

**Почему всё же так.** Домен и use case'ы уже работают с действующим лицом: правило «пишет только участник» проверяется по-настоящему. Контракт тел запросов окончательный: автора в теле нет и не будет. В 1b изменится только способ узнать id: вместо чтения заголовка — проверка подписи токена.

**Что изменится в 1b.** Появится middleware аутентификации. Middleware (промежуточный обработчик) — функция, которая принимает `http.Handler` и возвращает новый: он делает общую для всех запросов работу (проверить токен, записать в лог, засечь время) и зовёт исходный. Middleware проверит токен и положит id пользователя в контекст запроса, а `authenticate` в `auth.go` будет брать его оттуда. Обработчики, use case'ы и домен не изменятся — в этом и смысл того, что разбор `X-User-ID` собран в одном файле. (Так и вышло, с одной поправкой: в уроке [1.8](./08-resources) `authenticate` и файл `auth.go` заменила функция `caller`, которая только достаёт личность из контекста, а в уроке [1.14](./14-jwt) заголовок сменился проверкой токена.)

## <Part kind="theory" /> Мост userchecker: исключение из правила

Правило из урока [1.1](./01-architecture): адаптеры не знают друг о друге, а <T id="bounded-context">контексты</T> `chat` и `user` не импортируют друг друга. Но use case создания чата должен проверить, что участники существуют, а пользователи живут в контексте `user`. Как быть?

В уроке [1.4](./04-usecases) мы объявили в `chat/usecase` порт `UserChecker` — на языке чатов: «кого из этих `chat/domain.UserID` не существует?». Реализует его адаптер `chat/adapters/userchecker`. Он единственный в контексте `chat` импортирует `user/usecase` и `user/domain`, и правило `depguard` `chat-context` делает исключение ровно для его каталога. Сам адаптер узко зависит от одного use case чужого контекста — `GetUser` — через собственный порт `UserGetter`.

Почему это исключение безопасно:

- **Связь одна и видна.** Вся зависимость `chat → user` — один пакет из полусотни строк. Линтер запретит её в любом другом месте.
- **Направление сохранено.** `chat/usecase` по-прежнему не знает про `user`: он видит только свой порт. Мост — адаптер, внешний слой; ему разрешено знать детали.
- **Ошибки чужого контекста не просачиваются.** `user.ErrUserNotFound` мост переводит в «этот id в списке отсутствующих», а любую другую ошибку оборачивает как сбой зависимости. `%w` сохраняет `context.Canceled` для таблицы, а `user`-ную `ValidationError` адаптер чатов не узнает (у него свой тип) — и честно ответит 500.
- **Готов к распилу.** В модуле 6 `user` станет отдельным сервисом, и на месте моста появится gRPC-клиент. Порт `UserChecker` и use case чатов этого не заметят.

Мост и хранилища — ведомые адаптеры; HTTP-обработчики — ведущие. Правило «адаптеры не знают друг о друге» к мосту применимо в полной мере: он не импортирует ни `memory`, ни `httpapi`.

## <Part kind="theory" /> Корень композиции: main.go

<T id="composition-root">Корень композиции (composition root)</T> из урока [1.1](./01-architecture) наконец появился: `cmd/messenger/main.go`. Это единственное место, где известны конкретные типы: `clock.System`, `idgen.UUIDv7`, `memory.Store`. (С урока 1.14 сборка вынесена из `main.go` в функцию `newApp` в соседнем `cmd/messenger/app.go` — её вызывают и `main`, и сквозной тест; в `main.go` остались `run`, конфиг и запуск сервера. Поэтому фрагмент «Сборка» ниже подключён из `app.go`.) Он создаёт их, передаёт в конструкторы use case'ов, use case'ы — в конструкторы адаптеров, а адаптеры регистрирует в `http.ServeMux`. Прочитав одну функцию, видишь весь граф приложения.

Несколько решений в нём стоит объяснить.

**`run() error` вместо работы в `main`.** `os.Exit` завершает процесс немедленно и **не выполняет** отложенные вызовы `defer`. Если бы `main` создавал контекст сигнала с `defer stop()` и при ошибке звал `os.Exit(1)`, `stop` не отработал бы. Поэтому вся работа — в `run`, она возвращает ошибку, её `defer` выполняются на выходе, и только потом `main` пишет ошибку в лог и выходит с кодом 1.

**Любая ошибка сборки — выход.** Конструкторы проверяют зависимости на `nil` и возвращают ошибку. Сервер с недособранным графом хуже, чем сервер, который не запустился: первый упадёт на первом запросе, второй — сразу и с понятным сообщением.

**Конфиг из окружения.** Адрес — переменная `MESSENGER_ADDR`, по умолчанию `127.0.0.1:8080`: только loopback, с другой машины до сервера не достучаться. Для сборки с заглушкой `X-User-ID` это осознанная защита (ADR-0002): слушать все интерфейсы — явное решение, `MESSENGER_ADDR=:8080`. Окружение — стандартный способ передать настройки контейнеру (принцип III «Config» манифеста Twelve-Factor App). Модуль 1c этого правила держится: урок [1.17](./17-service-in-container#конфигурация-по-двенадцати-факторам) добавит переменные сроков запроса и остановки, а секрет — ключ подписи — передаст файлом, а не переменной.

**Логи — JSON через `slog`.** `slog.New(slog.NewJSONHandler(os.Stdout, nil))`: каждая строка лога — JSON-объект с полями `time`, `level`, `msg` и нашими ключами. Человеку читать чуть труднее, но системе сбора логов не нужно угадывать формат: поиск «все ERROR с путём `/chats/…/messages`» — запрос по полям, а не регулярное выражение. Логгер приходит в адаптеры через конструктор, а не из глобальной переменной.

**Сигналы.** `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` возвращает контекст, который отменится по Ctrl+C (SIGINT) или по SIGTERM — так Docker и Kubernetes просят процесс завершиться.

## <Part kind="theory" /> Таймауты сервера и корректное завершение

`platform/httpserver` собирает `http.Server` с четырьмя таймаутами. Зачем каждый — подробно в уроке [0b.6](../00b-network/06-http1-pools): у `http.Server` по умолчанию нет ни одного, и `http.ListenAndServe` создаёт сервер, который один медленный клиент держит сколько угодно.

| Поле | Значение | Зачем |
|---|---|---|
| `ReadHeaderTimeout` | 5 с | заголовки — сотни байт; 5 с обрывают Slowloris |
| `ReadTimeout` | 10 с | весь запрос с телом до 1 МиБ |
| `WriteTimeout` | 10 с | от конца чтения заголовков до конца ответа; наши обработчики отвечают за миллисекунды. С урока [1.17](./17-service-in-container) — таймаут запроса + 5 с, то есть 15 с |
| `IdleTimeout` | 60 с | сколько держать простаивающее <T id="keep-alive">keep-alive</T>-соединение |

`ErrorLog` сервера — тот же `slog` на уровне Warn: внутренние жалобы `net/http` (например, на панику в обработчике) попадают в общий JSON-лог, а не в стандартный `log`.

**Корректное завершение (graceful shutdown).** `httpserver.Run` запускает `ListenAndServe` в горутине и ждёт одного из двух: сервер упал сам (порт занят — ошибка) или отменили контекст (пришёл сигнал). Во втором случае зовёт `srv.Shutdown`: сервер перестаёт принимать новые соединения, закрывает простаивающие и ждёт, пока текущие запросы допишут ответы, — но не дольше 10 секунд (в этом уроке — константа `shutdownTimeout` в `main.go`; с урока [1.17](./17-service-in-container) срок задаёт переменная `MESSENGER_SHUTDOWN_TIMEOUT`, по умолчанию те же 10 с, и `Run` получает его в `httpserver.Stop` вместе с паузой дренажа). Если не дождались, `Run` зовёт `srv.Close()` и обрывает оставшиеся соединения сам: иначе зависший запрос пережил бы `Run`. 10 секунд меньше 30 секунд, которые Kubernetes по умолчанию даёт процессу между SIGTERM и SIGKILL: сервер должен закончить сам, а не быть убитым посреди ответа.

Ещё две детали. Контекст для `Shutdown` создан через `context.WithoutCancel(ctx)`: исходный контекст уже отменён сигналом, и `Shutdown` с ним не стал бы ждать вовсе. А после `Shutdown` `ListenAndServe` возвращает `http.ErrServerClosed` — это не ошибка, а штатное «я остановлен». У горутины есть владелец (`Run`) и способ остановки (`Shutdown`), как требует стандарт мессенджера.

<Deep title="как ServeMux выбирает шаблон">

Шаблоны проверяются на конфликт один раз — при регистрации, а при запросе мультиплексор уже не сравнивает их, а просто спускается по дереву. Логика лежит в двух файлах стандартной библиотеки: `net/http/pattern.go` (сравнение шаблонов) и `net/http/routing_tree.go` (дерево поиска).

**Сравнение.** Для двух шаблонов вычисляется отношение — одно из пяти: равносильны (подходят для одних и тех же запросов), первый общее второго, первый специфичнее, не пересекаются, перекрываются (есть общий запрос, но ни один не специфичнее). Сначала сравниваются методы: шаблон без метода общее любого с методом, `GET` общее `HEAD`, а разные методы не пересекаются вовсе. Потом пути — посегментно: литерал специфичнее подстановки `{id}`, а одиночная подстановка специфичнее хвостовой `{rest...}`. Отношения сегментов складываются: если в одном сегменте специфичнее первый, а в другом второй, шаблоны перекрываются.

**Конфликт** — это «равносильны» или «перекрываются» при одинаковом хосте. Тогда регистрация паникует, а сообщение объясняет причину на примере. Мы проверили: `GET /chats/{id}` и `GET /chats/{name}` — «matches the same requests», а `GET /chats/{id}` и `GET /{kind}/new` — «both match some paths, like "/chats/new". But neither is more specific than the other». Почему при регистрации? Ошибка в таблице маршрутов — ошибка программиста, и лучше упасть при старте, чем однажды ночью отдать запрос не тому обработчику. Кроме того, отсутствие конфликтов — то, на чём держится быстрый поиск.

**Поиск.** Дерево ветвится сначала по хосту, потом по методу, потом по сегментам пути. На каждом сегменте узел сначала пробует ребёнка-литерал, затем ребёнка-подстановку, в конце — хвостовую подстановку. Такой порядок правилен как раз потому, что конфликты исключены при регистрации: литерал в этой позиции всегда специфичнее. Иногда приходится откатываться: при шаблонах `/a/b/z` и `/a/{x}/c` путь `/a/b/c` сначала идёт по литералу `b`, не находит `c` и возвращается к подстановке. Если для метода ничего не нашлось, `HEAD` пробует `GET`, затем — шаблоны без метода.

**405.** Когда совпадения нет, мультиплексор собирает методы всех шаблонов, подходящих по пути, сортирует их и отвечает 405 с заголовком `Allow` — RFC 9110 требует его в каждом ответе 405. Отсюда `Allow: GET, HEAD, POST` в нашем тесте.

**Совместимость.** До Go 1.22 шаблоны с методом и `{id}` не существовали. Переменная окружения `GODEBUG=httpmuxgo121=1` возвращает старое поведение; она читается один раз при старте. По умолчанию её значение зависит от строки `go` в `go.mod` главного модуля: у мессенджера `go 1.27`, значит, новые правила. Мы запустили сервер с `httpmuxgo121=1`: паники нет, но `POST /users` отвечает 404 — старый мультиплексор принял «POST /users» за хост и путь, и ни один маршрут больше не совпадает.

```text
    │       ├── memory/                # 1.4  хранилище, оптимистическая блокировка

```

Каждый слой можно прочитать отдельно, и каждый проверен на своём уровне: домен — <T id="table-driven-test">табличными тестами</T>, use case'ы — на фейках, хранилища — <T id="contract-test">контрактом</T>, HTTP — через `httptest`, всё вместе — `curl`. Правила зависимостей проверяет линтер, а не внимательность ревьюера.

**Что дальше.** Часть 1b — REST API по-взрослому: ресурсы и коды ответов как контракт, идемпотентность повторных запросов, пагинация курсором, версия API и, главное, аутентификация JWT вместо `X-User-ID`. Её middleware встанет перед нашими обработчиками, а сами обработчики, use case'ы и домен не изменятся.

## <Part kind="mistakes" /> Типичные ошибки

<Callout type="mistake">

**Доменная структура в ответе.** `json.NewEncoder(w).Encode(chat)` — либо пустой `{}` (поля неэкспортируемые), либо, если поля открыть и навесить теги, API — слепок домена: наружу уходят `version` и прочие служебные поля, а переименование в домене ломает клиентов. Ответ — всегда DTO и маппер.

**`json.NewDecoder(r.Body)` без лимита.** Клиент присылает тело на 2 ГБ — сервер честно читает его в память. Десяток таких запросов одновременно — и процесс убит за нехватку памяти. Сначала `http.MaxBytesReader`, потом декодер. Харсаньи в «100 ошибках Go» отдельно разбирает и обратную сторону — забытый `Close` у тела ответа на клиенте (№ 79 «Not closing transient resources»); сервер закрывает тело запроса сам.

**500 с текстом ошибки наружу.** Самое короткое и самое опасное:

<!-- go-check -->

```go
package snippet

import (
	"net/http"

	"github.com/jackc/pgx/v5/pgxpool"
)

func getChat(db *pgxpool.Pool) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		var title string
		err := db.QueryRow(r.Context(), "SELECT title FROM chats WHERE id = $1", r.PathValue("id")).Scan(&title)
		if err != nil {
			// pgx.ErrNoRows станет 500 вместо 404, а текст драйвера уйдёт клиенту.
			http.Error(w, err.Error(), http.StatusInternalServerError)
			return
		}
		_, _ = w.Write([]byte(title))
	}
}
```

Клиент узнаёт имя драйвера, иногда адрес базы и фрагмент запроса; а «чат не найден» превращается в «сервер сломался». Внутренние ошибки — в лог, наружу — общее сообщение; доменные — по таблице.

**Логировать и возвращать одну и ту же ошибку.** Обработчик пишет `log.Error("send failed", "err", err)` и зовёт `writeError`, который на 500 пишет в лог ещё раз. Или хуже: use case логирует, адаптер логирует, `main` логирует — одна ошибка пять раз (урок [1.3](./03-errors)). Правило «обработай или верни»: use case возвращает ошибку, а логирует её одно место — политика ошибок `httperror.Write`.

**`http.DefaultServeMux` и регистрация в `init`.**

<!-- go-check -->

```go
package snippet

import "net/http"

// Маршрут регистрируется при импорте пакета, в глобальном мультиплексоре.
func init() {
	http.HandleFunc("POST /chats", createChat)
}

func createChat(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusCreated)
}
```

Маршруты появляются от самого факта импорта, и в `main` не видно, что сервер умеет. Глобальный мультиплексор общий для всех пакетов программы: стандартный `net/http/pprof` при импорте регистрирует в нём `/debug/pprof/` — и если сервер запущен через `http.ListenAndServe(addr, nil)`, профилировщик с дампами памяти окажется открыт наружу. А два пакета, зарегистрировавшие один и тот же маршрут, уронят программу паникой ещё до `main`. Свой `http.NewServeMux()` в корне композиции и явный `Register(mux)` решают всё сразу.

**Бизнес-правило в обработчике.** `if len(req.Text) > 4096 { … }` в адаптере — проверка в байтах, а не в символах, и она разойдётся с доменом при первой правке. Правило живёт в одном месте — в `NewText`; адаптер отдаёт ошибку домена по таблице.

</Callout>

## <Part kind="tradeoff" /> Компромисс: DTO и мапперы против одной структуры

<Callout type="tradeoff">

**DTO и мапперы дают** независимость: домен и API меняются каждый по своим причинам. Можно переименовать поле в домене, разбить <T id="entity">сущность</T>, поменять схему блокировки — клиенты не заметят. Можно выпустить вторую версию API с другой формой ответа на тот же домен. Внутренние поля не утекают, а лишние поля во входе отвергаются.

**Чем платим.** Дублированием: поля сообщения описаны трижды — в домене, в DTO и в маппере, и новое поле — три правки вместо одной. Мапперы — скучный код, в котором легко ошибиться копированием (`ChatID: m.ID().String()`). Поэтому тесты обработчиков сравнивают тело ответа целиком, до байта.

**Когда не применять:** во внутренней утилите или прототипе, где «API» читает один скрипт того же автора и никогда не станет контрактом. И когда сущность и её представление действительно одно и то же — например, ответ `/healthz` из одного поля.

**Как выбирать:** как только у данных есть внешний потребитель, которого вы не контролируете (мобильное приложение, другая команда), — DTO на границе обязательны. Дублирование здесь — случайное совпадение кода, а не дублирование знания (правило DRY из стандарта мессенджера): знание «как называется поле в API» и «как называется поле в домене» — разные знания, просто сейчас они совпадают.

</Callout>

## <Part kind="selfcheck" /> Самопроверка

<SelfCheck question="Use case вернул ошибку, в цепочке которой есть context.Canceled. Почему адаптер не пишет ответ и пишет в лог на уровне Info, а не Error?">

`context.Canceled` на `r.Context()` значит, что клиент закрыл соединение. Ответ некому прочитать: писать его — пустая работа. Это и не сбой сервера: пользователь просто закрыл приложение или ушёл со страницы. Если логировать такое как Error, дежурного будили бы обычные действия пользователей, а настоящие сбои тонули бы в шуме.

</SelfCheck>

<SelfCheck question="Клиент прислал X-User-ID: ALICE. Что он получит и почему не 400 invalid_input?">

401 `unauthenticated`. Обработчик разбирает заголовок сам, до вызова use case: не UUID в нижнем регистре — «не знаю, кто вы». Если бы строка ушла в use case, тот вернул бы `ValidationError` с полем `user_id`, и клиент получил бы 400 «неверные данные» — другой смысл и другая реакция клиента: на 401 приложение отправляет пользователя войти заново, а на 400 — показывает ошибку в форме.

</SelfCheck>

<SelfCheck question="Генератор id сломался и выдаёт не UUID. Разбор id в use case возвращает *ValidationError. Какой статус получит клиент и за счёт чего?">

500. Use case оборачивает этот сбой без `%w` — `fmt.Errorf("… генератор выдал не UUID: %q", raw)`, — и цепочка обрывается: `errors.As` в таблице не находит `ValidationError`, и ошибка попадает в строку «всё остальное». Клиент ничего неверного не присылал, виноват сервер, поэтому 5xx. Тест `TestErrorMapping/сбой_генератора_id_—_не_ошибка_клиента` фиксирует это поведение.

</SelfCheck>

<SelfCheck question="В mux уже есть GET /chats/{id}. Что будет, если зарегистрировать GET /chats/mine? А GET /{owner}/mine?">

`GET /chats/mine` зарегистрируется: литерал `mine` специфичнее подстановки `{id}`, и запрос `/chats/mine` уйдёт в него, а `/chats/42` — в `{id}`. `GET /{owner}/mine` вызовет панику прямо при регистрации: оба шаблона подходят для `/chats/mine`, но ни один не специфичнее — первый точнее в первом сегменте, второй во втором. Паника при старте лучше, чем запрос, ушедший не тому обработчику.

</SelfCheck>

<SelfCheck question="Почему ответ на пустую историю — {&quot;messages&quot;:[]}, а не {&quot;messages&quot;:null}, и где это решается?">

Use case для пустой истории возвращает `nil`-срез, а `encoding/json` пишет `nil`-срез как `null`. Клиенту пришлось бы отдельно обрабатывать `null` и пустой массив, а код вида `messages.length` упал бы. Решается в маппере `toListMessagesResponse`: срез создаётся через `make(…, 0, len(msgs))`, и пустой срез кодируется как `[]`. Это деталь формата API, поэтому ей место в адаптере, а не в use case.

</SelfCheck>

<SelfCheck question="Почему корень композиции — run() error, а не код прямо в main с os.Exit(1) на каждой ошибке?">

`os.Exit` завершает процесс немедленно и не выполняет `defer`. `defer stop()` для контекста сигналов и любые другие отложенные уборки не отработали бы. В `run` ошибка возвращается обычным путём, все `defer` выполняются, и только потом `main` пишет её в лог и выходит с кодом 1. Заодно `run` проще проверить и прочитать: это обычная функция с одним выходом для ошибки.

</SelfCheck>
