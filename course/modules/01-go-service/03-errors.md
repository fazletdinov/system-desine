# 1.3. Ошибки в Go: сигналы, обёртки и границы

## <Part kind="problem" /> Проблема: 500 вместо 404 и одна ошибка пять раз

Пользователь удалил группу на телефоне, а на ноутбуке она ещё открыта. Он пишет в неё сообщение. Чата больше нет, и правильный ответ сервера — `404 Not Found`: клиент уберёт чат из списка и покажет «чат удалён». Вместо этого приходит `500 Internal Server Error`. Клиент считает, что сервер упал, показывает «что-то пошло не так, попробуйте позже» и через несколько секунд повторяет запрос. И снова, и снова — на каждом ноутбуке, где эта группа осталась открытой.

Дежурный открывает логи и видит одну и ту же беду, записанную несколько раз подряд:

```
level=ERROR msg="find chat failed"   err="чат не найден"
level=ERROR msg="load chat failed"   err="load chat: чат не найден"
level=ERROR msg="send message failed" err="send message: load chat: чат не найден"
level=ERROR msg="use case failed"    err="send message: load chat: чат не найден"
level=ERROR msg="request failed"     err="send message: load chat: чат не найден" status=500
```

<N>5 записей</N> об одной ошибке одного запроса: её логировал каждый уровень, через который она проходила. При тысяче таких запросов в минуту — <N>5000 строк</N> в минуту, и настоящие аварии в них тонут.

Хуже другое: в тексте ясно написано «чат не найден», а ответ — 500. HTTP-обработчик проверял `errors.Is(err, ErrChatNotFound)` и получал `false`. Причина — одна буква. Полгода назад кто-то в <T id="use-case">use case (сценарии использования)</T> написал `fmt.Errorf("send message: %v", err)` вместо `%w`. Текст ошибки остался тем же, а связь с исходной ошибкой пропала, и обработчик больше не может узнать, что случилось.

В Go ошибка — это обычное значение, и с ним можно обойтись правильно или неправильно десятком способов. В этом уроке разберём, как устроены ошибки в Go, как их различать, как обёртывать, не теряя причину, кто должен их логировать и где ошибка превращается в HTTP-статус. И заведём в мессенджере доменные ошибки, которыми будем пользоваться до конца курса.

Подумайте, прежде чем читать дальше: почему текст ошибки в логе одинаковый, а программа видит разницу? Что такого есть в ошибке, кроме текста?

## <Part kind="theory" /> Ошибка — это значение

В Java или Python о сбое сообщают **исключением**: оно летит вверх по стеку, пропуская все функции, пока его кто-нибудь не поймает. В Go исключений нет. Функция, которая может не справиться, возвращает ошибку последним результатом, и вызывающий проверяет её явно:

<!-- go-check -->

```go
package snippet

import (
	"fmt"
	"os"
)

func ReadConfig(path string) ([]byte, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read config: %w", err)
	}
	return data, nil
}
```

Ошибка в Go — любое значение, у которого есть метод `Error() string`: `error` — встроенный интерфейс ровно с одним этим методом. `nil` значит «ошибки нет». Всё остальное — ошибка, и что у неё внутри, решает тот, кто её создал: это может быть просто текст, а может быть структура с полями.

Почему Go обходится без исключений? Авторы языка объясняют это в FAQ (раздел «Why does Go not have exceptions?»): исключения делают путь ошибки невидимым. Глядя на строку `chat := store.FindChat(id)` в Java, не скажешь, может ли она бросить исключение и кто его поймает. В Go строка `chat, err := store.FindChat(ctx, id)` прямо говорит: здесь может не получиться, и следующая строка решает, что с этим делать. Цена — многословие: `if err != nil` встречается в коде на Go очень часто. Зато каждый путь ошибки виден при чтении, и его можно проверить тестом.

Удобная модель — **конверт с запиской**. Функция, которая не справилась, кладёт записку в конверт и отдаёт его наверх. Записка — текст для человека (`Error()`). Но на конверте может быть и отметка, которую понимает программа: «это именно "чат не найден"», «это ошибка валидации поля text». Весь урок — о том, как ставить такие отметки и как их не потерять, пока конверт идёт наверх. Где аналогия перестаёт работать — увидим через раздел: конверты в Go вкладываются друг в друга, и проверяющий умеет заглядывать внутрь.

## <Part kind="theory" /> Сигнальные ошибки: различаем по значению, а не по тексту

Самая простая отметка на конверте — сама ошибка как уникальное значение. В мессенджере их объявляет домен:

<<< @/../messenger/internal/chat/domain/errors.go#sentinels{go}

Это <T id="sentinel-error">сигнальные ошибки (sentinel errors)</T> — переменные пакета, по которым вызывающий узнаёт, что именно случилось. Имя по соглашению начинается с `Err`. В домене пользователей так же объявлены `ErrInvalid`, `ErrUserNotFound` («пользователь не найден») и `ErrUsernameTaken` («имя пользователя занято»).

Как их сравнивать? Есть три способа, и правильный — только один.

**По тексту:** `err.Error() == "чат не найден"`. Это хрупко. Текст написан для людей: его поправят («чат не найден или удалён»), переведут, к нему допишут контекст — и сравнение молча перестанет срабатывать. Компилятор не поможет: строки он не проверяет.

**Через `==`:** `err == domain.ErrChatNotFound`. Это сравнивает уже значение, а не текст: `errors.New` возвращает указатель на новую структуру, поэтому две ошибки с одинаковым текстом всё равно разные, а `ErrChatNotFound` равна только самой себе. Но `==` ломается, как только ошибку обернули (об этом следующий раздел): снаружи окажется уже другой конверт.

**Через `errors.Is`:** `errors.Is(err, domain.ErrChatNotFound)`. Функция сравнивает с целью и саму ошибку, и все ошибки, вложенные в неё. Это единственный способ, который переживает обёртку. Правило простое: сигнальные ошибки проверяются только через `errors.Is`.

Зачем `ErrInvalid` и `ErrConcurrentUpdate`, `ErrDirectChatExists`, если пока их никто не возвращает? Сигнальные ошибки — часть <T id="ubiquitous-language">единого языка (ubiquitous language)</T> домена (урок [1.2](./02-domain)): «чат не найден», «чат изменился одновременно с вами» — это события предметной области, а не детали хранения. Хранилище вернёт `ErrChatNotFound` и `ErrConcurrentUpdate` в уроке 1.4, а use case создания личного чата будет ловить `ErrDirectChatExists`, когда два запроса создают чат для одной пары одновременно. Последние две ошибки в списке — `ErrDuplicateMessage` и `ErrClientMessageIDReused` — появятся в уроке 1.12 вместе с защитой от повторной отправки; фрагмент показывает файл в его нынешнем виде.

## <Part kind="theory" /> Обёртка ошибки: %w против %v

Use case отправки сообщения загружает чат из хранилища. Если чата нет, хранилище вернёт `ErrChatNotFound`. Use case может отдать её наверх как есть — но тогда в логе будет просто «чат не найден», и непонятно, на каком шаге какого сценария. Лучше добавить контекст: `return domain.Message{}, fmt.Errorf("send message: %w", err)`.

Это <T id="error-wrapping">обёртка ошибки (error wrapping)</T>. Глагол `%w` (от *wrap*) в `fmt.Errorf` делает две вещи. Вставляет текст исходной ошибки в новую строку — получается «send message: чат не найден». И сохраняет саму исходную ошибку внутри новой: у результата есть метод `Unwrap() error`, который её возвращает. Конверт вложен в конверт: снаружи новая записка с контекстом, внутри — исходный конверт со всеми отметками. `errors.Is` открывает конверты по одному, пока не найдёт нужный или пока они не кончатся.

Глагол `%v` делает только первое. Он вставляет **текст** ошибки в строку и забывает её саму. Результат — новая ошибка без `Unwrap`, внутри пусто. Текст буква в букву тот же, а `errors.Is(err, domain.ErrChatNotFound)` возвращает `false`. Именно это и случилось в начале урока: одна буква — и 404 стал 500.

Когда оборачивать, а когда отдавать как есть?

- **Оборачивайте через `%w`**, когда добавляете полезный контекст: «send message: …», «load chat 0192…: …». Читатель лога поймёт, где случилось, а программа всё равно найдёт причину.
- **Отдавайте как есть**, когда добавить нечего. Ошибка валидации из `domain.NewText` уже говорит «text: пустое сообщение» — приписывать к ней «send message» мало пользы, use case в мессенджере возвращает её без обёртки.
- **Используйте `%v` сознательно**, только когда хотите спрятать причину от вызывающих (об этом в «Типичных ошибках»). Но обычно лучше не прятать, а **перевести** ошибку в свою: хранилище превращает «строк не найдено» базы данных в `ErrChatNotFound`.

Обёртки появились в Go 1.13 (2019): тогда в стандартную библиотеку пришли `%w`, `errors.Is`, `errors.As` и `errors.Unwrap`. До этого обёртывали сторонними пакетами или не обёртывали вовсе. В Go 1.20 добавили обёртку **нескольких** ошибок сразу: `fmt.Errorf` с несколькими `%w` и функцию `errors.Join`. Такая ошибка вместо `Unwrap() error` имеет `Unwrap() []error` — внутри не один конверт, а пачка. Это нужно, когда причин действительно несколько: скажем, при остановке сервиса не закрылись и пул соединений, и файл журнала, и сообщить надо об обоих. `errors.Join(errA, errB)` склеивает тексты через перевод строки, отбрасывает `nil`, а если все аргументы `nil` — возвращает `nil`. `errors.Is` и `errors.As` видят каждую ошибку пачки.

## <Part kind="theory" /> Ошибка с данными: тип и errors.As

Сигнальной ошибки хватает, когда нужно знать только «что случилось». Но для ошибки валидации этого мало. Клиенту надо ответить, **какое поле** неверно и **почему**: `{"error": {"code": "invalid_input", "field": "text", "message": "пустое сообщение"}}`. Делать сигнальную ошибку на каждое поле и каждую причину — `ErrTextEmpty`, `ErrTextTooLong`, `ErrTitleEmpty`… — десятки переменных, и HTTP-<T id="adapter">адаптер</T> должен знать их все.

Нужна ошибка, которая несёт данные. Это просто тип, у которого есть метод `Error()`:

<<< @/../messenger/internal/chat/domain/errors.go#validation-error{go}

`ValidationError` — структура с полями `Field` и `Reason`. Методы объявлены у указателя `*ValidationError`, поэтому ошибкой является именно указатель: функция `invalid` возвращает `&ValidationError{...}`.

Достать её из цепочки помогает `errors.As`. Так её будет использовать HTTP-адаптер в уроке 1.7 — здесь в упрощённом виде, с собственной копией типа, чтобы фрагмент собирался отдельно от мессенджера:

<!-- go-check -->

```go
package snippet

import (
	"errors"
	"fmt"
)

type ValidationError struct{ Field, Reason string }

func (e *ValidationError) Error() string { return e.Field + ": " + e.Reason }

// FieldOf возвращает имя неверного поля, если в цепочке err есть *ValidationError.
func FieldOf(err error) (string, bool) {
	var ve *ValidationError
	if !errors.As(err, &ve) {
		return "", false
	}
	return ve.Field, true
}

// Обёртка через %w не мешает: FieldOf(Wrapped()) вернёт "text", true.
func Wrapped() error {
	return fmt.Errorf("send message: %w", &ValidationError{Field: "text", Reason: "пустое сообщение"})
}
```

`As` идёт по цепочке так же, как `Is`, но ищет не конкретное значение, а ошибку нужного **типа**. Нашла — кладёт её в переменную `ve` и возвращает `true`. Поэтому `As` принимает указатель на переменную (`&ve`): иначе ей некуда записать находку. Передать саму переменную — частая ошибка, но её ловит `go vet` (анализатор `errorsas`), а во время работы `As` паникует: «errors: target must be a non-nil pointer». Мы проверили оба на Go 1.26.

В Go 1.26 появился и обобщённый вариант — `errors.AsType`: `ve, ok := errors.AsType[*domain.ValidationError](err)` делает то же без отдельной переменной, и документация пакета советует предпочитать его. Алгоритм обхода у них тот же (у `AsType` своя реализация); в тестах этого урока используем `As`, чтобы видеть его явно.

Последняя деталь — метод `Is` у `ValidationError`. Вызывающему не всегда важно, какое поле неверно: use case или тест хотят знать только «это ошибка валидации?». Для этого есть `ErrInvalid`. Но `ErrInvalid` никто не оборачивает — `invalid` возвращает `*ValidationError`, а не `ErrInvalid`. Как тогда `errors.Is(err, domain.ErrInvalid)` вернёт `true`? `errors.Is` на каждом конверте не только сравнивает его с целью через `==`, но и спрашивает: «есть ли у тебя метод `Is(error) bool`?» — и если есть, зовёт его. Наш метод отвечает «да» ровно на `ErrInvalid`. Получается, любая `*ValidationError` для `errors.Is` равна `ErrInvalid`, а данные о поле остаются доступны через `errors.As`. Так же устроены ошибки стандартной библиотеки: `syscall.Errno` через свой метод `Is` совпадает с `fs.ErrNotExist` и другими общими ошибками.

Почему `invalid` — функция, а не просто `&ValidationError{...}` в каждом конструкторе? В уроке 1.2 она возвращала `errors.New(field + ": " + reason)`, а её зовут <N>27 мест</N> в двух доменах — все конструкторы и методы <T id="aggregate">агрегата</T>. Сменить тип всех ошибок валидации оказалось правкой одной строки в каждом пакете. Текст при этом не изменился: `Error()` по-прежнему возвращает «поле: причина».

## <Part kind="theory" /> Обработай или верни, но не оба

Вернёмся к пяти строкам лога из начала. Каждый уровень сделал одно и то же: получил ошибку, записал её в лог и вернул наверх. Так делать нельзя, и правило звучит коротко: **ошибку либо обрабатывают, либо возвращают — но не то и другое сразу**. Тейва Харсаньи разбирает это в книге «100 ошибок Go» как ошибку № 52 «Handling an error twice».

Что значит «обработать»? Принять решение: ответить клиенту, повторить попытку, подставить значение по умолчанию, остановить программу. Запись в лог — тоже обработка: после неё ошибку не должен логировать никто другой. Если же функция решения не принимает, она возвращает ошибку наверх, добавив контекст через `%w`. Контекст, ради которого хотелось написать строку в лог («загружали чат такой-то»), переезжает в текст обёртки — и в итоге оказывается в **одной** записи лога с полной цепочкой: «send message: load chat: чат не найден».

Кто в мессенджере принимает решение? HTTP-адаптер. Только он знает, что ошибка превратится в ответ клиенту и с каким статусом, и только он видит запрос целиком: путь, пользователя, время. Поэтому домен ошибки создаёт и возвращает, use case оборачивает и возвращает, а адаптер решает и логирует. Домен логировать и не может: `log/slog` в нём запрещён правилом `depguard` из урока 1.1.

## <Part kind="theory" /> Доменные ошибки и граница: где ошибка становится статусом

Ошибки бывают двух родов.

**Доменные** — события предметной области: «чат не найден», «пользователь не участник», «текст пустой». Они часть единого языка, их понимает продакт, и для каждой понятно, что сказать клиенту.

**Инфраструктурные** — сбои механизмов: «connection refused», «таймаут запроса к базе», «диск полон». Они говорят о том, **как** система устроена, а не о том, **что** пользователь сделал не так. Клиенту их показывать нельзя: ему с ними нечего делать, а злоумышленнику они расскажут, какая у вас база и где она стоит.

Граница между ними — адаптеры. Адаптер хранилища переводит «строк не найдено» базы в `domain.ErrChatNotFound` (модуль 2a), и use case не знает, какая за <T id="hexagonal-port">портом</T> база. HTTP-адаптер переводит доменные ошибки в статусы. Набросок таблицы — полную реализацию напишем в уроке 1.7:

| Ошибка | Статус HTTP | Почему |
|---|---|---|
| `ErrInvalid` (через `errors.As` — с полем) | 400 Bad Request | клиент прислал неверные данные и может их исправить |
| `ErrChatNotFound`, `ErrUserNotFound` | 404 Not Found | такого ресурса нет |
| `ErrNotMember` | 403 Forbidden | ресурс есть, но этому пользователю нельзя |
| `ErrConcurrentUpdate`, `ErrUsernameTaken` | 409 Conflict | запрос конфликтует с текущим состоянием |
| всё остальное | 500 Internal Server Error | сбой на нашей стороне; детали — только в лог |

Последняя строка важна: ошибка, которую адаптер не узнал, — это 500 с общим сообщением наружу и полной цепочкой в лог. Теперь понятно, почему `%v` из начала урока так опасен: он превращает доменную ошибку в «неузнанную», и клиент получает 500 вместо 404.

Домен и use case HTTP-статусов не знают. Завтра появится gRPC (модуль 6) — у него свои коды (`NotFound`, `PermissionDenied`), и новый адаптер построит свою таблицу из тех же доменных ошибок. Ни строчки в домене менять не придётся.

**А паника?** `panic` в Go — не замена ошибке. Она для ситуаций, когда программа дальше работать не может: не прочитался обязательный конфиг, не открылся порт при старте. Код запуска в `main` может упасть с понятным сообщением — это стандарт мессенджера. Во время обработки запросов паники нет: всё, что может не получиться, возвращает `error`. Сервер `net/http` перехватывает панику в обработчике, чтобы один запрос не уронил процесс, и пишет в лог «http: panic serving …» — но это страховка от бага, а не способ сообщать об ошибках.

## <Part kind="viz" /> Визуализация: путь ошибки от хранилища до HTTP

Плеер проводит две ошибки от места, где они родились, до HTTP-ответа. Первая — `ErrChatNotFound` из хранилища: use case её оборачивает, кто-то ломает обёртку через `%v`, мы чиним, и адаптер отвечает 404. Вторая — `*ValidationError` из `domain.NewText`: адаптер достаёт её через `errors.As` и отвечает 400 с именем поля. Следите за индикаторами `errors.Is` и `errors.As` на каждом шаге.

<ErrorChain />

Задания:

1. На шаге с `%v` текст ошибки не изменился ни на букву. Почему `errors.Is` всё-таки вернул `false`? Чего не стало в цепочке?
2. На шагах с `ValidationError` в цепочке один конверт, и `ErrInvalid` в нём нет. Почему `errors.Is(err, domain.ErrInvalid)` даёт `true`?
3. Use case обернул `ErrChatNotFound` через `%w`, а ошибку валидации вернул как есть. Не противоречие ли это?
4. Представьте, что `errors.As` достал `*ValidationError`, а адаптер вместо `ve.Field` разбирает `err.Error()` по двоеточию. Что сломается, если use case однажды обернёт ошибку валидации в «send message: …»?

<SelfCheck question="Ответы">

1. `%v` вставляет в строку только текст ошибки, а саму ошибку не сохраняет. У результата нет метода `Unwrap`, и `errors.Is` не может заглянуть внутрь — там пусто. Глазами в логе разницу не видно; её видят тест (`TestPercentVBreaksChain`) и <T id="linter">линтер</T> `errorlint`.
2. У `*ValidationError` есть метод `Is(target error) bool`, который отвечает `true` на `ErrInvalid`. `errors.Is` на каждом конверте не только сравнивает его с целью через `==`, но и вызывает его метод `Is`, если он есть.
3. Нет. Оборачивают, когда есть что добавить. «Чат не найден» без контекста не говорит, в каком сценарии это случилось, — «send message: …» помогает. «text: пустое сообщение» уже говорит всё: поле и причину, а сценарий виден по запросу. Обернуть её тоже можно — `errors.As` найдёт её под любым числом обёрток через `%w`.
4. Разбор текста получит «send message: text: пустое сообщение», и полем окажется «send message». `ve.Field` от обёрток не зависит: `errors.As` достаёт исходную структуру из любой глубины цепочки. Данные из ошибки берут из полей, а не из текста.

</SelfCheck>

<Deep title="как устроены errors.Is и errors.As">

Обе функции живут в файле `src/errors/wrap.go` стандартной библиотеки, и устроены они почти одинаково. Мы читали версию Go 1.26.

Ошибку вместе со всем, что в неё вложено, документация называет деревом. Корень — сама ошибка. Если у неё есть метод `Unwrap() error`, у корня один потомок — то, что этот метод вернул. Если метод `Unwrap() []error` (так устроены `errors.Join` и `fmt.Errorf` с несколькими `%w`), потомков несколько. Обычная цепочка обёрток — частный случай дерева, вытянутый в линию.

`errors.Is` обходит это дерево в глубину: сначала проверяет сам узел, потом спускается к первому потомку, проверяет его и его потомков, и только потом переходит ко второму. На каждом узле две проверки. Первая — сравнение с целью через `==`, если значения типа цели вообще можно сравнивать (если тип цели — срез, `==` для него не определён, и эту проверку пропускают). Вторая — если у узла есть метод `Is(error) bool`, функция вызывает его и верит ответу. Совпадение на любом узле — `true`. Если `Unwrap` вернул `nil` или метода нет вовсе — ветка кончилась. Документация отдельно просит: метод `Is` должен сравнивать неглубоко и сам не разворачивать цепочку — разворачивание делает `errors.Is`.

`errors.As` идёт тем же путём, но вопрос на узле другой: можно ли присвоить этот узел переменной, на которую указывает цель? Для указателя на `*ValidationError` это значит «узел имеет тип `*ValidationError`». Есть и аналог метода `Is` — метод `As(any) bool`, который сам решает, подходит ли он, и сам заполняет цель. Первое найденное совпадение записывается в переменную, и обход останавливается.

Отсюда требования к аргументу `As`. Функции надо куда-то записать находку, поэтому нужен указатель на переменную, и не `nil`. А тип переменной должен быть интерфейсом или реализовывать `error` — иначе ни один узел дерева ей не подойдёт. Нарушение этих условий — паника в момент вызова, и именно поэтому анализатор `errorsas` в `go vet` проверяет их ещё при сборке.

Важное следствие — порядок. Обход идёт в прямом порядке: сначала корень, потом вся первая ветка до самого низа, и только потом вторая. Поэтому глубокое совпадение в первой ветке побеждает неглубокое во второй. Если в дереве две ошибки валидации, `As` вернёт ту, что встретилась раньше в этом порядке.

</Deep>

## <Part kind="mistakes" /> Типичные ошибки

Одна из самых коварных ошибок с ошибками компилируется, проходит `go vet` и выглядит невинно:

<!-- go-check -->

```go
package snippet

type NotFoundError struct{ ID string }

func (e *NotFoundError) Error() string { return "не найден: " + e.ID }

// lookup возвращает конкретный тип: при успехе — nil-указатель.
func lookup(id string) *NotFoundError {
	if id == "" {
		return &NotFoundError{ID: id}
	}
	return nil
}

// Load отдаёт результат lookup как error — и проверка err != nil ломается.
func Load(id string) error {
	err := lookup(id)
	return err
}
```

Мы запустили `Load("42")`: проверка `err != nil` дала `true`, хотя `lookup` вернул `nil`, а `fmt.Printf("%T %v", err, err)` напечатал `*main.NotFoundError <nil>`.

<Callout type="mistake">

**`nil`-указатель, возвращённый как `error`.** Значение интерфейса в Go — пара «тип + значение». Интерфейс равен `nil`, только когда пусты **обе** половины. `lookup` вернул `nil` типа `*NotFoundError`; при возврате из `Load` он упаковался в `error` с типом `*NotFoundError` и пустым значением — и такой интерфейс уже не `nil`. Вызывающий решит, что случилась ошибка, хотя её нет. Харсаньи описывает это как ошибку № 45 «Returning a nil receiver». Правило: функция, которая возвращает ошибку, объявляет результат типа `error` и при успехе пишет `return nil` явно. Конкретный тип ошибки создаётся только там, где ошибка действительно есть, — так устроена `invalid`.

**Сравнение по тексту.** `if err.Error() == "чат не найден"` или `strings.Contains(err.Error(), "not found")`. Текст для людей: его поправят, переведут, к нему допишут контекст — и проверка молча перестанет срабатывать. Значения сравнивают через `errors.Is`, данные достают через `errors.As` и поля структуры.

**`%v` вместо `%w`.** Текст тот же, цепочки нет, `errors.Is` и `errors.As` ничего не находят. Именно так 404 превратился в 500 в начале урока. Ловят тест на конкретную ошибку через обёртку и линтер `errorlint`.

**`==` вместо `errors.Is`.** `err == domain.ErrChatNotFound` работает, пока ошибку никто не обернул. Как только use case добавит контекст, сравнение сломается — без единого предупреждения компилятора. `errorlint` ловит и это.

**Логирование на каждом уровне.** Хранилище логирует и возвращает, use case логирует и возвращает, адаптер логирует — одна ошибка превращается в пять строк, и по логу уже не понять, сколько было сбоев. Обработай **или** верни. Контекст добавляется обёрткой, а логирует тот, кто принимает решение, — адаптер.

**Чужие ошибки как часть своего API.** Адаптер хранилища возвращает `fmt.Errorf("find chat: %w", pgx.ErrNoRows)`. Use case начинает проверять `errors.Is(err, pgx.ErrNoRows)` — и теперь use case привязан к драйверу PostgreSQL `pgx`: смените хранилище на Redis, и проверка молча перестанет срабатывать. Обернув чужую ошибку через `%w`, вы делаете её частью своего контракта — об этом предупреждает и статья «Working with Errors in Go 1.13» в разделе «Whether to Wrap». Адаптер **переводит** ошибку библиотеки в доменную: `pgx.ErrNoRows` → `domain.ErrChatNotFound`.

</Callout>

## <Part kind="tradeoff" /> Компромисс: часть API против удобства различения

<Callout type="tradeoff">

**Сигнальные ошибки дают:** вызывающий различает случаи одной строкой `errors.Is`, не разбирая текст; таблица «ошибка → статус» в адаптере читается как спецификация; тесты проверяют конкретную причину, а не просто «что-то пошло не так».

**Чем платим.** Каждая экспортированная ошибка — часть публичного API пакета, такая же, как функция. Переименовать `ErrChatNotFound`, удалить её или начать возвращать в другом случае — значит сломать всех, кто на неё проверяет, причём без ошибки компиляции: `errors.Is` просто начнёт возвращать `false`. Типизированная ошибка обязывает ещё сильнее: её поля тоже становятся контрактом. И ещё: каждая обёртка через `%w` раскрывает вложенную ошибку вызывающим.

**Когда не применять:** если вызывающему нечего делать с причиной, кроме как сообщить о ней, сигнальная ошибка не нужна — хватит `fmt.Errorf("…: %w", err)` с исходной причиной или просто текста. Заводите `ErrX`, когда у кого-то наверху **разное поведение** для этого случая: другой статус, повтор, запасной путь.

**Как выбирать:** спросите, кто и как будет проверять эту ошибку. Нужно знать только «что случилось» — сигнальная ошибка. Нужны подробности (поле, лимит, id) — тип с полями и `errors.As`. Никто не проверяет — обычная обёртка.

</Callout>

## <Part kind="selfcheck" /> Самопроверка

<SelfCheck question="Use case пишет return fmt.Errorf(&quot;send message: %v&quot;, err), где err — ErrChatNotFound. Тесты use case проверяют только err != nil и проходят. Что увидит клиент и какой тест это поймал бы?">

Клиент получит 500 вместо 404: `%v` вставил только текст, цепочки нет, и HTTP-адаптер не узнал `ErrChatNotFound`. Проверка `err != nil` этого не видит. Поймал бы тест, который проверяет **какая** ошибка: `errors.Is(err, domain.ErrChatNotFound)` для случая «чата нет». Ещё раньше — линтер `errorlint` в CI.

</SelfCheck>

<SelfCheck question="Почему ошибка валидации в мессенджере — тип *ValidationError, а «чат не найден» — переменная ErrChatNotFound? Нельзя ли сделать всё переменными?">

Для «чат не найден» вызывающему достаточно знать сам факт: ответ 404 одинаков для любого чата. Для ошибки валидации клиенту нужны данные — какое поле и почему. Переменными пришлось бы заводить по одной на каждое поле и причину, и адаптер должен был бы знать их все. Тип с полями несёт данные, а метод `Is` сохраняет простую проверку «это валидация?» через `errors.Is(err, ErrInvalid)`.

</SelfCheck>

<SelfCheck question="Хранилище, use case и адаптер — каждый пишет ошибку в лог и возвращает её. Что не так и как исправить, не потеряв информацию о том, где случился сбой?">

Одна ошибка даёт несколько записей, и по логу не понять, сколько было сбоев; настоящие аварии тонут в шуме. Правило — обработай или верни. Хранилище и use case не логируют, а оборачивают ошибку через `%w` с контекстом («send message: load chat: …»). Адаптер, который принимает решение об ответе, пишет одну запись с полной цепочкой — в ней видно все уровни.

</SelfCheck>

<SelfCheck question="Адаптер Postgres возвращает fmt.Errorf(&quot;find chat: %w&quot;, pgx.ErrNoRows), а use case проверяет errors.Is(err, pgx.ErrNoRows). Всё работает. Что не так?">

Use case теперь зависит от драйвера `pgx` — деталь хранилища утекла через ошибку, нарушив <T id="dependency-rule">правило зависимостей</T>. Смените хранилище, и проверка молча перестанет срабатывать. Адаптер должен переводить ошибку библиотеки в доменную: на `pgx.ErrNoRows` вернуть `domain.ErrChatNotFound`. Тогда use case проверяет только доменные ошибки и не знает, какая база за портом.

</SelfCheck>

<SelfCheck question="errors.Is(err, domain.ErrInvalid) возвращает true для любой *ValidationError, хотя ErrInvalid в цепочке нет. Как это работает и почему метод Is не должен сам вызывать Unwrap?">

`errors.Is` на каждом узле дерева, кроме сравнения через `==`, вызывает метод `Is(error) bool`, если он есть, и верит ответу. Метод `*ValidationError` отвечает `true` на `ErrInvalid`. Разворачивать цепочку — работа самой `errors.Is`: она обходит дерево в глубину. Если метод `Is` начнёт разворачивать ещё и сам, обход будет повторяться, а поведение станет непредсказуемым; документация пакета прямо просит сравнивать неглубоко.

</SelfCheck>

## <Part kind="sources" /> Источники

- Harsanyi T., «100 Go Mistakes and How to Avoid Them» (рус. «100 ошибок Go и как их избежать»), гл. 7 «Error management»: № 49 — когда оборачивать ошибку, № 50–51 — как правильно проверять тип и значение ошибки (`errors.As`, `errors.Is`), № 52 «Handling an error twice» — почему нельзя и логировать, и возвращать; гл. 6, № 45 «Returning a nil receiver» — ловушка с `nil`-указателем в интерфейсе.
- Neil D., Amsterdam J., [«Working with Errors in Go 1.13»](https://go.dev/blog/go1.13-errors), go.dev/blog, 2019 — `%w`, `errors.Is`, `errors.As`, метод `Is` у своего типа; раздел «Whether to Wrap» — почему обёртка делает вложенную ошибку частью API.
- Документация Go: пакет [`errors`](https://pkg.go.dev/errors) — описание дерева ошибок, `Is`, `As`, `AsType`, `Join`; [`fmt.Errorf`](https://pkg.go.dev/fmt#Errorf) — глагол `%w` и несколько `%w`; исходники `src/errors/wrap.go` — сам алгоритм обхода; [Go 1.20 Release Notes](https://go.dev/doc/go1.20#errors) — обёртка нескольких ошибок.
- Документация Go, [FAQ «Why does Go not have exceptions?»](https://go.dev/doc/faq#exceptions) — почему ошибки в Go значения, а не исключения; [FAQ «Why is my nil error value not equal to nil?»](https://go.dev/doc/faq#nil_error) — интерфейс как пара «тип + значение».
- Pike R., [«Errors are values»](https://go.dev/blog/errors-are-values), go.dev/blog, 2015 — как программировать с ошибками, а не только проверять их.
- Документация [errorlint](https://github.com/polyfloyd/go-errorlint) — какие проверки делает линтер: `%w` в `fmt.Errorf`, сравнения и приведения типов ошибок.

</Callout>
