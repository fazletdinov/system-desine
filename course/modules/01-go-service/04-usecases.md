# 1.4. Use case'ы и порты: сценарии отдельно от деталей

## <Part kind="problem" /> Проблема: сервис-бог и два сообщения с номером 5

Домен мессенджера готов: чат знает своих участников, `Post` выдаёт номера подряд, ошибки различаются через `errors.Is`. Но домен ничего не делает сам. Кто-то должен взять запрос «Алиса пишет в чат 42 текст "привет"», загрузить чат, позвать `Post` и сохранить результат. Самый частый способ это написать — один «сервис чатов», куда складывают всё:

<!-- go-check -->

```go
package snippet

import (
	"context"
	"database/sql"
	"fmt"
	"log/slog"
	"net/http"
	"time"
)

// ChatService — все сценарии чатов в одном типе: CreateChat, RenameChat, DeleteChat,
// AddMember, RemoveMember, LeaveChat, SendMessage, EditMessage, DeleteMessage,
// ListMessages, MarkRead, PinMessage, SearchMessages, MuteChat, ExportHistory.
type ChatService struct {
	db       *sql.DB
	replica  *sql.DB
	push     *http.Client
	search   *http.Client
	files    *http.Client
	log      *slog.Logger
	now      func() time.Time
	newID    func() string
	maxBatch int
}

// SendMessage нужны три поля из девяти, но тест всё равно собирает ChatService целиком.
func (s *ChatService) SendMessage(ctx context.Context, chatID, authorID, text string) (int64, error) {
	var seq int64
	err := s.db.QueryRowContext(ctx,
		`SELECT COALESCE(MAX(seq), 0) + 1 FROM messages WHERE chat_id = $1`, chatID).Scan(&seq)
	if err != nil {
		return 0, fmt.Errorf("send message: next seq: %w", err)
	}
	_, err = s.db.ExecContext(ctx,
		`INSERT INTO messages (id, chat_id, author_id, text, seq, sent_at) VALUES ($1, $2, $3, $4, $5, $6)`,
		s.newID(), chatID, authorID, text, seq, s.now())
	if err != nil {
		return 0, fmt.Errorf("send message: insert: %w", err)
	}
	return seq, nil
}
```

Сценариев пятнадцать, зависимостей девять. Чтобы проверить одну строчку `SendMessage`, тест строит весь `ChatService`: подставляет базу, реплику, три HTTP-клиента и логгер — или передаёт `nil` и надеется, что до них не дойдёт. Добавили шестнадцатый сценарий, которому нужен Redis, — десятое поле получают все пятнадцать, и все их тесты меняются. Этот тип меняется по пятнадцати причинам сразу, и каждая правка задевает чужие сценарии.

А в `SendMessage` прячется беда похуже. Алиса и Боб пишут в один чат одновременно, в чате уже 4 сообщения:

| Момент | Запрос Алисы | Запрос Боба |
|---|---|---|
| 1 | `SELECT MAX(seq) + 1` → 5 | |
| 2 | | `SELECT MAX(seq) + 1` → 5 |
| 3 | `INSERT … seq = 5` | |
| 4 | | `INSERT … seq = 5` |

Оба прочитали одно и то же, оба посчитали «5», оба записали. В чате два сообщения с номером 5. Клиент, который подгружает историю «после пятого», пропустит одно из них навсегда. Если на `(chat_id, seq)` есть уникальный индекс, второй `INSERT` упадёт, и Боб получит 500 — честнее, но ненамного лучше. Это классическая гонка «прочитал — посчитал — записал», которую называют **потерянным обновлением** (lost update): результат одного из двух писателей молча теряется. Каждая строчка верна, тесты с одним пользователем проходят, а ошибка появляется только под нагрузкой.

В этом уроке мы решим обе проблемы. Разрежем «сервис» на <T id="use-case">use case'ы (сценарии использования)</T> — по одному типу на сценарий, каждый со своими узкими зависимостями. И научим отправку сообщения переживать одновременные записи с помощью версии чата.

Подумайте, прежде чем читать дальше: правило «номера идут подряд» уже живёт в <T id="aggregate">агрегате (aggregate)</T> `Chat` из урока 1.2. Почему этого мало, чтобы два одновременных запроса не получили один номер?

## <Part kind="theory" /> Use case: один сценарий — один тип

Use case — это одна операция приложения, как её видит пользователь: «создать чат», «отправить сообщение», «показать историю». В мессенджере каждый сценарий — отдельный тип с единственным публичным методом `Execute`:

- `CreateChat`, `SendMessage`, `ListMessages` в пакете `chat/usecase`;
- `RegisterUser` и `GetUser` в пакете `user/usecase`.

Роберт Мартин в «Чистой архитектуре» (гл. 20 «Бизнес-правила») разделяет правила на два вида. **Критические бизнес-правила** существовали бы и без программы: «писать может только участник», «номера идут подряд». Они живут в <T id="entity">сущностях</T> и агрегатах — у нас в домене. **Правила приложения** описывают, как программа автоматизирует работу: «прочитать чат, проверить автора, сохранить сообщение, а при конфликте повторить». Это и есть use case. Он **оркестрирует**: решает, в каком порядке звать домен и хранилище, но сам бизнес-правил почти не содержит.

Удобная модель — **карточка рецепта** на кухне ресторана. Рецепт говорит: «взять из холодильника, приготовить по технологии, отдать на раздачу». Он не знает, кто поставщик продуктов и какая марка у холодильника, — поменяй поставщика, рецепт тот же. Технология приготовления («жарить до золотистой корочки») — это домен. Рецепт ссылается на неё, но не переписывает. Где аналогия перестаёт работать: повар сам выбирает, что делать, если продукта нет, а use case таких решений почти не принимает. Его ответ на любую неожиданность — вернуть ошибку наверх, <T id="adapter">адаптеру</T>, который знает, что сказать клиенту.

Как выглядит вход сценария? Это **команда** — структура из строк:

```
SendMessageCommand{ChatID: "0192…", AuthorID: "0192…", Text: "привет"}
```

Почему строки, а не готовые `domain.ChatID` и `domain.Text`? Потому что разбор строк в <T id="value-object">объекты-значения</T> — тоже часть сценария. Если бы разбирал HTTP-обработчик, то CLI, gRPC-сервер из модуля 6 и тест каждый повторили бы разбор у себя — и рано или поздно кто-то из них забыл бы `NewText`. Мартин в той же главе требует того же: модель запроса use case'а не знает про транспорт, в ней нет `http.Request`, заголовков и JSON. Команда — общий знаменатель всех транспортов, и валидация в ней одна на всех.

Для чтения вход называется **запросом** (query): `ListMessagesQuery{ChatID, ReaderID, AfterSeq, Limit}`. Разница в названии подсказывает разницу в смысле: команда меняет состояние, запрос только читает.

Выход сценария — доменные значения: `SendMessage` возвращает `domain.Message`, `CreateChat` — `CreateChatResult` с `*domain.Chat` внутри. В JSON их переведёт адаптер HTTP в уроке 1.7, через свои <T id="dto">DTO</T>. Use case про JSON не знает.

Каждый use case собирается конструктором, который проверяет зависимости:

```
func NewSendMessage(chats ChatFinder, messages MessageAppender, clock Clock, ids IDGenerator) (*SendMessage, error)
```

Если забыть передать часы, ошибка появится при старте сервиса, в <T id="composition-root">корне композиции</T>, а не паникой `nil pointer dereference` на первом же запросе в три часа ночи. Одна оговорка, которая следует из урока 1.3: проверка `clock == nil` ловит только «пустой» интерфейс. Указатель `(*memory.Store)(nil)`, переданный как интерфейс, уже не `nil` — у интерфейса есть тип, — и проверка его пропустит. Поэтому в корне композиции зависимости создают конструкторами, а не объявляют пустыми переменными.

## <Part kind="theory" /> Порты: у потребителя и узкие

Use case ходит во внешний мир через <T id="hexagonal-port">порты</T> — интерфейсы, которые описывают, что ему нужно. Все порты контекста чатов:

<<< @/../messenger/internal/chat/usecase/ports.go#ports{go}

Два правила видны сразу.

**Порт объявлен у потребителя.** Интерфейсы лежат в пакете `usecase`, а не рядом с хранилищем в `adapters/memory`. Это то самое «порт объявляется там, где потребляется» из урока 1.1. В Go это получается естественно: тип реализует интерфейс **неявно**, без слова `implements`. `memory.Store` ничего не знает про `ChatFinder` — у него просто есть метод `FindChat` с подходящей сигнатурой, и компилятор сам проверяет совпадение там, где `*memory.Store` передают в `NewSendMessage`. Значит, интерфейс может объявить тот, кому он нужен, — даже позже реализации и в другом пакете.

**Порты узкие.** У каждого — один метод. Это принцип разделения интерфейсов, ISP (Interface Segregation Principle), буква I в SOLID: клиент не должен зависеть от методов, которыми не пользуется. Посмотрите, кто что видит:

| Use case | Порты |
|---|---|
| `CreateChat` | `ChatCreator`, `DirectChatFinder`, `UserChecker`, `Clock`, `IDGenerator` |
| `SendMessage` | `ChatFinder`, `MessageAppender`, `Clock`, `IDGenerator` |
| `ListMessages` | `ChatFinder`, `MessageLister` |

Одно и то же хранилище `memory.Store` реализует <N>5 портов</N>: `ChatCreator`, `ChatFinder`, `DirectChatFinder`, `MessageAppender`, `MessageLister`. В корне композиции его передают сразу в несколько аргументов: `usecase.NewSendMessage(store, store, clock, ids)`. Но `SendMessage` видит только два его метода. Что это даёт:

- **Честная сигнатура.** По конструктору видно, что отправка сообщения не создаёт чатов и не листает историю. Это документация, которую проверяет компилятор.
- **Маленькая подмена в тестах.** Тесту `ListMessages` с отказом хранилища достаточно типа с одним методом `ListMessages`, а не заглушки на двадцать методов.
- **Свобода раскладки.** Когда-нибудь сообщения могут уехать в отдельное хранилище, а чаты остаться в Postgres (модуль 9). `ListMessages` получит `MessageLister` от другого адаптера — и не заметит.

Тейва Харсаньи в «100 ошибках Go» разбирает это тремя ошибками подряд. № 5 «Interface pollution» — интерфейсы «на всякий случай», которые никто не подменяет. № 6 «Interface on the producer side» — интерфейс рядом с реализацией: производитель не знает, что нужно каждому потребителю, и навязывает всем один широкий интерфейс. № 7 «Returning interfaces» — функция возвращает интерфейс вместо конкретного типа. Отсюда известная поговорка Go: **принимай интерфейсы, возвращай структуры** (accept interfaces, return structs). Наши конструкторы так и сделаны: `NewSendMessage` принимает интерфейсы и возвращает `*SendMessage`, а `memory.NewStore()` возвращает `*memory.Store`, а не «интерфейс хранилища». Вызывающий сам решит, через какой узкий порт на него смотреть.

Порты `Clock` и `IDGenerator` объявлены в обоих контекстах — и в `chat/usecase`, и в `user/usecase`, с одинаковыми сигнатурами. Это не забытое дублирование: порт принадлежит потребителю, а контексты не делят код (урок 1.1). Одна реализация из `platform` подходит обоим — неявная реализация интерфейсов снова делает это бесплатным.

## <Part kind="theory" /> Агрегат — граница согласованности

Вернёмся к вопросу из начала: почему правила «номера подряд» в агрегате мало? Потому что агрегат отвечает за согласованность **внутри одного объекта в памяти**. Запрос Алисы и запрос Боба загружают **две разные копии** чата. В каждой копии `Post` честно выдаёт `lastSeq + 1 = 5`. Каждая копия согласована, а вместе они — нет.

Ханонов в «Изучаем DDD» (гл. 6) формулирует это так: агрегат — граница согласованности. Внутри неё <T id="invariant">инварианты</T> соблюдает сам агрегат. А чтобы две копии не разошлись, хранилище должно сохранять агрегат **целиком и атомарно**, проверяя, что с момента чтения его никто не изменил. Отсюда правило, которое мы будем соблюдать весь курс: один сценарий меняет один агрегат, и хранилище сохраняет его за одну операцию.

Поэтому порядок в `SendMessage` такой: загрузить чат → `chat.Post` выдаёт номер → сохранить **и чат, и сообщение** одним вызовом `AppendMessage`. Номер выдаёт агрегат, а не хранилище: правило «подряд» — бизнес-правило, ему место в домене (урок 1.2). Хранилище отвечает за другое — чтобы сохранение случилось, только если чат не изменился.

## <Part kind="theory" /> Оптимистическая блокировка: версия вместо замка

Как хранилищу понять, что чат изменился? По версии. Поле `version` агрегата из урока 1.2 растёт на один при каждом изменении — в нашем случае при каждом `Post`. Use case запоминает версию, которую прочитал, и передаёт её в `AppendMessage` как `expectedVersion`. Хранилище сохраняет новое состояние, **только если** версия в нём всё ещё равна ожидаемой. Иначе — `domain.ErrConcurrentUpdate`, и ничего не записано.

Тот же сценарий с Алисой и Бобом, теперь с версиями (в чате 4 сообщения, версия 4):

| Момент | Запрос Алисы | Запрос Боба | В хранилище |
|---|---|---|---|
| 1 | `FindChat` → версия 4 | | версия 4 |
| 2 | | `FindChat` → версия 4 | версия 4 |
| 3 | `Post` → seq 5; `AppendMessage(…, 4)` — совпало | | версия 5, seq 5 — Алисы |
| 4 | | `Post` → seq 5; `AppendMessage(…, 4)` — **конфликт** | без изменений |
| 5 | | повтор: `FindChat` → версия 5; `Post` → seq 6; `AppendMessage(…, 5)` | версия 6, seq 6 — Боба |

Это <T id="optimistic-locking">оптимистическая блокировка (optimistic locking)</T>. «Оптимистическая» — потому что мы надеемся, что конфликтов мало, и не запираем чат на время сценария. Мы просто проверяем при записи, не опоздали ли. Мартин Фаулер описал этот приём в «Patterns of Enterprise Application Architecture» как Optimistic Offline Lock: у записи есть номер версии, изменение принимается только при совпадении номера, а при несовпадении сценарий откатывается.

Аналогия — правка статьи в вики. Вы открыли статью, полчаса редактировали и нажали «Сохранить». Вики сравнивает версию, с которой вы начали, с текущей: если кто-то успел сохранить раньше, вы получаете «конфликт правок». Где аналогия перестаёт работать: вики не может сама совместить две правки одного абзаца и отдаёт конфликт человеку. А у нас «правка» — добавить сообщение в конец, совмещать нечего. Поэтому use case повторяет сам, без человека:

<<< @/../messenger/internal/chat/usecase/send_message.go#send-execute{go}

Три детали, на которых держится корректность.

**Id сообщения и время берутся до цикла.** Повтор отправляет то же самое сообщение, а не новое: id у него один на все попытки, а время отправки — момент, когда пришёл запрос, а не момент удачной попытки. Сейчас проигравшая попытка ничего не записывает, так что и с новым id на каждой попытке история бы не испортилась. Но постоянный id — свойство, на которое удобно опереться, когда будем защищаться от повторов клиента (модуль 5).

**Повторяется вся связка, а не одна запись.** На каждой попытке use case заново читает чат и заново зовёт `Post`. Нельзя просто «сохранить ещё раз» старое сообщение: у него устаревший номер, а правила агрегата проверялись на устаревшем состоянии. Сейчас правило одно — «автор — участник», но когда появится удаление участников, повтор без новой проверки пропустил бы сообщение от того, кого уже исключили.

**Попыток не больше `MaxSendAttempts = 3`.** Если чат так горячий, что три попытки подряд проиграли гонку, крутиться дальше вредно: каждая новая попытка — ещё одно чтение и ещё одна потерянная работа, а нагрузка от этого только растёт. Use case возвращает `ErrConcurrentUpdate`, обёрнутую через `%w`, и адаптер ответит `409 Conflict` (таблица из урока 1.3) — клиент повторит позже. Как правильно повторять с паузами, чтобы клиенты не били в сервер одновременно, — модуль 5.

Другие ошибки не повторяются: `ErrChatNotFound` от `FindChat` или `ErrNotMember` от `Post` не исчезнут от повтора, их возвращают сразу.

Есть и **пессимистическая** альтернатива: запереть чат на весь сценарий — «прочитал, посчитал, записал» под одним замком. Пока процесс один, хватило бы `sync.Mutex` на каждый чат. Но в модуле 2.5 сервис запустится в нескольких экземплярах за балансировщиком, и мьютекс в памяти одного процесса не остановит запрос в соседнем. Замок придётся держать в базе или в Redis, ходить за ним по сети, а если процесс упадёт, держа замок, — освобождать по таймауту. Почему для нашего случая это дороже — в «Под капотом» ниже.

Похожая гонка есть и в `CreateChat`. Два запроса одновременно создают личный чат для одной пары: оба не нашли его через `FindDirectChat` и оба пытаются создать. Здесь версии не помогут — чата ещё нет. Помогает уникальность в хранилище: второй `CreateChat` получает `ErrDirectChatExists`, и use case отдаёт уже существующий чат с `Created = false`:

<<< @/../messenger/internal/chat/usecase/create_chat.go#create-direct{go}

Первая проверка `FindDirectChat` — не защита от гонки, а быстрый путь для частого случая «чат уже есть». Защиту даёт только проверка внутри хранилища, под той же блокировкой, что и запись. Это общее правило: «проверил, потом сделал» в двух отдельных шагах гонку не закрывает, закрывает только атомарная операция.

## <Part kind="theory" /> Снимок агрегата: копия без взлома

Хранилище лежит в пакете `chat/adapters/memory`, а поля `Chat` закрыты — так мы защитили инварианты в уроке 1.2. Как хранилищу сохранить чат и потом восстановить его?

Есть три пути, и два из них плохие. Открыть поля (`Chat.Members`, `Chat.LastSeq`) — и любой пакет сможет поменять номер в обход `Post`. Хранить сам указатель `*Chat` — и хранилище будет делить объект с use case'ом: `Post` поднимет версию в объекте, который лежит в хранилище, ещё **до** проверки версии, и проверка станет бессмысленной. Третий путь — **снимок**:

<<< @/../messenger/internal/chat/domain/chat.go#snapshot{go}

`ChatSnapshot` — плоская структура с открытыми полями. Агрегат сам отдаёт снимок своего состояния и сам умеет восстановиться из него. Хранилище держит у себя снимки, а не агрегаты: `CreateChat` и `AppendMessage` сохраняют `chat.Snapshot()`, `FindChat` возвращает `domain.RestoreChat(snap)`. Каждый вызов `FindChat` получает **свою** копию чата, и копии разных запросов не влияют друг на друга — ровно это и нужно для оптимистической блокировки.

`slices.Clone(c.members)` в обе стороны — не перестраховка. Срез в Go — это окно в общий массив: копия структуры со срезом копирует окно, а не данные. Без `Clone` снимок и агрегат делили бы один массив участников, и запись в один была бы видна в другом.

`RestoreChat` не проверяет инварианты: она доверяет снимку, потому что он получен из `Snapshot` и сохранён нашим же хранилищем. Это сознательный компромисс. Теоретически любой пакет может вызвать `RestoreChat` с мусором — но по соглашению её зовут только адаптеры хранилища. В модуле 2a тот же снимок понадобится Postgres-адаптеру: он разложит поля снимка по колонкам таблицы, а при чтении соберёт снимок обратно. Тегов `db:"…"` на снимке нет: как называются колонки — забота адаптера, не домена.

## <Part kind="theory" /> Часы и генератор id — тоже порты

`time.Now()` и генератор UUID — тоже внешний мир. Их результат каждый раз разный, и тест, который сравнивает время создания чата, не знает, с чем сравнивать. Поэтому use case получает их через порты `Clock` и `IDGenerator`, а тест подставляет предсказуемые реализации:

- `fixedClock` всегда возвращает 13 октября 2026, 12:00 UTC;
- `seqIDs` выдаёт `00000000-0000-7000-b000-000000000001`, `…002` и так далее.

Такие подмены называются <T id="fake">фейками (fakes)</T>: это настоящие, работающие, но упрощённые реализации порта. Подробно о фейках, моках и о том, когда что выбирать, — в уроке 1.6. Здесь важно одно: тест с фейками **детерминирован** — при каждом запуске он видит одни и те же id и время и проверяет их точно, а не «примерно сейчас».

Настоящие реализации живут в `platform`. `clock.System` возвращает `time.Now().UTC()`. `idgen.UUIDv7` выдаёт <T id="uuidv7">UUIDv7</T> — идентификаторы, в первых 48 битах которых записано время в миллисекундах. Поэтому строки таких id сортируются в порядке создания, и база вставляет новые записи в конец индекса, а не в случайное место. Почему это важно для Postgres, разберём в модуле 2a; здесь достаточно знать, что v7 — осознанный выбор, а не мода. Библиотека `github.com/google/uuid` ещё и следит, чтобы внутри одного процесса каждый следующий id был больше предыдущего, даже в пределах одной миллисекунды: следующие 12 бит она заполняет долями миллисекунды и при совпадении увеличивает на один.

У `NewID` нет ошибки в сигнатуре. Почему так можно? `uuid.NewV7` ошибается только тогда, когда ошибку вернул источник случайности — по умолчанию `crypto/rand.Reader`. А начиная с Go 1.24 стандартный источник ошибок не возвращает вовсе: если операционная система не смогла выдать случайные байты, программа аварийно завершается сама — без шанса перехватить это через `recover`. Документация `crypto/rand.Read` так и пишет: «никогда не возвращает ошибку». Мы проверили это по исходникам Go 1.26. `uuid.Must` в `NewID` — страховка на случай, если кто-то подменит источник через `uuid.SetRand`.

А что если генератор выдал не UUID? Use case разбирает его результат через `domain.ParseChatID` — и получил бы `*ValidationError`. Обернуть её через `%w` было бы ошибкой: HTTP-адаптер увидел бы в цепочке ошибку валидации и ответил `400 Bad Request` — «клиент, исправь запрос», хотя клиент ни при чём, сломан наш генератор. Поэтому сбой генератора use case описывает своей ошибкой, без `%w`: `fmt.Errorf("create chat: генератор выдал не UUID: %q", raw)`. Это тот случай из урока 1.3, когда причину сознательно не раскрывают вызывающему: такая ошибка не узнаётся ни как `ErrInvalid`, ни как какая-либо доменная, и адаптер ответит 500. Тесты `TestGarbageIDIsNotValidationError` закрепляют это в обоих контекстах.

## <Part kind="theory" /> Хранилище в памяти

До модуля 2a данные мессенджера живут в памяти процесса — в `memory.Store`. Это настоящий адаптер, реализующий порты, и он же служит фейком в тестах use case'ов: быстрый, без сети и диска, но с настоящей логикой, включая проверку версии.

<<< @/../messenger/internal/chat/adapters/memory/store.go#store{go}

Три карты: снимки чатов по id, id личного чата по ключу пары (тот самый `DirectKeyFor` из урока 1.2) и сообщения по чату. HTTP-сервер обрабатывает каждый запрос в своей горутине, поэтому к картам обращаются одновременно. Карта в Go не рассчитана на одновременную запись из разных горутин. Рантайм часто замечает такое обращение и аварийно завершает программу с «fatal error: concurrent map writes» (или «concurrent map read and map write»), но замечает не всегда — а незамеченная гонка тихо портит данные. Поэтому все карты защищает один мьютекс, объявленный прямо над ними. Подробно о мьютексах и модели памяти Go — модуль 1.5.

Мьютекс — `sync.RWMutex`, «замок для читателей и писателя». Его можно взять двумя способами. `RLock` — на чтение: читателей одновременно может быть сколько угодно. `Lock` — на запись: писатель ждёт, пока выйдут все читатели, и пока он внутри, не входит никто. `FindChat`, `FindDirectChat` и `ListMessages` только читают и берут `RLock`, поэтому история одного чата может отдаваться многим клиентам параллельно. `CreateChat` и `AppendMessage` пишут и берут `Lock`. Чтобы поток читателей не заставил писателя ждать вечно, `RWMutex` после вызова `Lock` перестаёт пускать **новых** читателей, пока писатель не отработает.

Главное место хранилища — сохранение сообщения:

<<< @/../messenger/internal/chat/adapters/memory/store.go#append{go}

Проверка версии и запись идут под **одним** `Lock`. Между «версия совпала» и «записали» не вклинится никто, поэтому два писателя с одной ожидаемой версией не пройдут оба. Если бы проверку сделали под `RLock`, отпустили его и потом взяли `Lock` для записи — гонка из начала урока вернулась бы в новом месте. Это та же мысль, что и про `CreateChat`: проверка и действие должны быть одной атомарной операцией.

Копии на входе и на выходе — второе правило хранилища. На входе `chat.Snapshot()` копирует состояние, и use case, который продолжит работать со своим `*Chat`, не изменит сохранённое. На выходе `RestoreChat` и `slices.Clone` в `ListMessages` отдают копии. Вернуть срез `all[from:to]` как есть нельзя: он смотрит в тот же массив, что и хранилище. Вызывающий, сделав `append` к нему, мог бы записать прямо в массив хранилища — без мьютекса, то есть устроить <T id="data-race">гонку данных (data race)</T> и испортить чужую историю.

`ListMessages` ищет первое сообщение после `afterSeq` двоичным поиском: `sort.Search(n, f)` возвращает наименьший индекс, для которого `f` истинна, деля отрезок пополам на каждом шаге. Это работает, потому что сообщения добавляются строго по возрастанию `seq`. Клиент листает историю **курсором**: «дай до 50 сообщений после номера 120», затем «после 170» — без номеров страниц, которые съезжают, когда приходят новые сообщения.

Хранилище пользователей устроено так же, только проще: `domain.User` — значение без срезов, его можно хранить и отдавать как есть. `CreateUser` под одним `Lock` проверяет, свободно ли имя, и записывает — два одновременных запроса с одним именем не пройдут оба.

## <Part kind="code" /> Код: отправка под нагрузкой

Главный тест урока проверяет оптимистическую блокировку под настоящей конкуренцией: 8 горутин отправляют по 50 сообщений в один чат, всего 400.

<<< @/../messenger/internal/chat/usecase/usecase_test.go#concurrent-test{go}

Что он проверяет:

- **Каждая отправка закончилась одним из двух исходов.** Либо успех, либо `ErrConcurrentUpdate` после трёх проигранных попыток. Любая другая ошибка — провал теста. Счётчики `ok` и `retry` защищены своим мьютексом: горутины пишут в них одновременно.
- **В истории ровно столько сообщений, сколько успешных отправок.** Ни одно успешное не потерялось, ни одно неудачное не записалось.
- **Номера идут 1, 2, 3… без пропусков и повторов.** Историю тест читает страницами через сам use case `ListMessages`, курсором `after`.

Две детали Go в тесте. `wg.Go(f)` — метод `sync.WaitGroup`, появившийся в Go 1.25: запускает `f` в горутине и сам делает `Add(1)` перед запуском и `Done()` по завершении. Мы не стали подгонять тест, чтобы конфликты были всегда: тест проверяет, что **при любом** их числе история остаётся корректной.

Рабочий код use case'а про адаптеры по-прежнему не знает, а тесту настоящее хранилище в памяти полезнее самодельного фейка: проверяется и use case, и проверка версии в хранилище. <Deep title="оптимистическая и пессимистическая блокировка">

Оба способа решают одну задачу — не дать двум писателям потерять работу друг друга, — но платят по-разному.

Пессимистическая блокировка исходит из того, что конфликт вероятен, и запрещает его заранее: прежде чем читать чат, сценарий берёт замок и держит его до конца записи. Остальные ждут. Пока всё происходит в одном процессе и сценарий длится микросекунды, это дёшево. Но в распределённой системе замок живёт в общем месте — в базе или в Redis, — и сценарий держит его на время всех своих сетевых походов. Пропускная способность одного чата падает до «один сценарий за раз», а каждый сценарий длится миллисекунды, а не микросекунды. Процесс, который упал с замком в руках, держит чат, пока не истечёт таймаут. А два сценария, которые берут два замка в разном порядке, могут навсегда ждать друг друга — это взаимная блокировка (deadlock).

Оптимистическая блокировка исходит из того, что конфликт редок, и проверяет его постфактум: читать может кто угодно и когда угодно, а при записи сверяется версия. Никто никого не ждёт, упавший процесс ничего не держит. Плата — работа, которую приходится выбрасывать. Чем больше писателей одновременно бьют в один объект, тем чаще повторы, и при высокой конкуренции большая часть работы уходит впустую: из N писателей в каждом раунде выигрывает один. Наш тест это и показал — под детектором гонок окно конфликта шире, и неудач больше.

Почему для чата выбран оптимистический путь? Конкуренция за один объект здесь низкая: десятки сообщений в секунду в один чат от разных людей — редкость даже для большой группы, а сама запись короткая. Конфликт случается редко, а если случается — повтор стоит одного чтения.

В модуле 2b мы увидим, как это устроено в Postgres. MVCC — многоверсионность — позволяет читателям не ждать писателей: каждая транзакция видит свой снимок данных. А `SELECT … FOR UPDATE` — пессимистический замок на строку, который держится до конца транзакции. В модуле 2a наша проверка версии превратится в `UPDATE … WHERE id = $1 AND version = $2`: если строка не обновилась, значит, версия уже другая — тот же конфликт, только проверяет его база.

</Deep>

## <Part kind="mistakes" /> Типичные ошибки

<Callout type="mistake">

**Сервис-бог.** Один `ChatService` на пятнадцать сценариев с конструктором на девять зависимостей — как в начале урока. Каждый сценарий получает все зависимости, хотя нужны ему две-три; тест любого метода собирает всё; правка одного сценария задевает остальные. Признак: тип, у которого больше пяти публичных методов, и тесты, где половина аргументов конструктора — `nil`. Лечение — один use case на сценарий, каждый со своими узкими портами.

**Интерфейс репозитория на двадцать методов рядом с реализацией.** `type ChatRepository interface { … }` с двадцатью методами в пакете `postgres`, и каждый use case принимает его целиком. Use case отправки «зависит» от удаления чатов и поиска; фейк для теста обязан реализовать все двадцать методов, большинство — заглушками. Это ошибка № 6 у Харсаньи: интерфейс на стороне производителя. Порт объявляет потребитель, и ровно на те методы, которые вызывает.

**Use case возвращает DTO с тегами `json`.** `SendMessage` возвращает `MessageResponse` с `json:"created_at"` — и use case теперь знает формат HTTP-ответа. Понадобится gRPC или ответ v2 — менять придётся сценарий, хотя бизнес-логика не менялась. Use case возвращает доменные значения, перевод в DTO — дело адаптера и его <T id="mapper">маппера</T> (урок 1.7).

**Номер сообщения выдаёт хранилище.** `SELECT MAX(seq) + 1` в адаптере или `seq SERIAL` в таблице — и правило «номера подряд в пределах чата» утекло из домена в хранилище. `MAX + 1` даёт гонку из начала урока. `SERIAL` (или `IDENTITY`) гонки не даёт, но номера у него сквозные на всю таблицу, а не по чату, и при откате транзакции в нём остаются дыры: последовательность в Postgres не откатывается. Номер выдаёт агрегат в `Post`, а хранилище только проверяет версию.

**Повторять запись без повторного чтения.** При `ErrConcurrentUpdate` снова вызвать `AppendMessage` с тем же сообщением и новой версией. Номер у сообщения устаревший, и в истории появится дубль номера — ровно то, от чего защищались. Повторяется вся связка: прочитать → `Post` → записать.

</Callout>

## <Part kind="tradeoff" /> Компромисс: повтор вместо ожидания

<Callout type="tradeoff">

**Оптимистическая блокировка даёт:** никто никого не ждёт; читатели не мешают писателям; упавший процесс не держит замков; механизм одинаково работает в одном процессе и в нескольких экземплярах сервиса — проверку версии делает хранилище.

**Чем платим.** Счётчик версий в агрегате и в хранилище; цикл повторов в use case'е с ограничением попыток; при высокой конкуренции — выброшенная работа и иногда честный отказ клиенту: «чат изменился одновременно с вами, повторите» (`409 Conflict`). И дисциплина: повторять надо всю связку «прочитать → проверить правила → записать», а не одну запись.

**Когда не применять:** если за один объект постоянно борются многие писатели — счётчик просмотров популярного поста, остаток товара на распродаже, — повторы съедят всю работу. Там лучше атомарная операция в хранилище (`UPDATE … SET n = n + 1`), очередь из одного писателя или пессимистический замок на короткое время.

**Как выбирать:** оцените, как часто два писателя трогают **один и тот же** объект одновременно. Редко — оптимистическая блокировка. Часто и запись короткая — пессимистическая. Часто и операцию можно свести к одной атомарной команде хранилища — атомарная операция.

</Callout>

## <Part kind="selfcheck" /> Самопроверка

<SelfCheck question="Почему SendMessage принимает ChatFinder и MessageAppender, а не один интерфейс ChatStore со всеми пятью методами memory.Store?">

Use case должен зависеть только от того, чем пользуется (ISP). С узкими портами сигнатура конструктора честно говорит, что отправка не создаёт чатов и не листает историю; фейк для теста реализует два метода, а не пять; а в будущем чаты и сообщения могут жить в разных хранилищах — `SendMessage` получит два разных адаптера и не заметит. Широкий интерфейс рядом с реализацией — ошибка № 6 у Харсаньи.

</SelfCheck>

<SelfCheck question="Хранилище проверяет версию под RLock, отпускает его, а затем берёт Lock и записывает. Что сломается?">

Между проверкой и записью появится окно. Два писателя с одной ожидаемой версией оба пройдут проверку под `RLock` — читателей может быть сколько угодно, — а затем по очереди запишут. Второй затрёт снимок чата первого, и в истории окажется два сообщения с одним номером. Проверка и запись должны быть одной атомарной операцией — под одним `Lock`.

</SelfCheck>

<SelfCheck question="В SendMessage id сообщения и время берутся до цикла повторов. Что изменится, если перенести вызов uc.ids.NewID() внутрь цикла?">

Каждая попытка создавала бы «новое» сообщение с новым id. Пока проигравшая попытка ничего не записывает, история не испортится, но пропадёт главное свойство: у сообщения один id на все попытки. Если сохранение когда-нибудь станет неатомарным (сообщение записалось, а ответ потерялся), повтор с новым id даст дубль, который нельзя распознать по id. Защита от повторов клиента в модуле 5 опирается как раз на постоянный id.

</SelfCheck>

<SelfCheck question="Почему хранилище в памяти держит ChatSnapshot, а не *domain.Chat?">

Указатель делил бы один объект между хранилищем и use case'ом. `Post` поднимает версию и номер в объекте use case'а ещё до `AppendMessage` — и если это тот же объект, что лежит в хранилище, проверка версии сравнит его с самим собой и всегда пройдёт. Снимок — независимая копия: хранилище меняет его только в `AppendMessage`, под замком, после проверки. Заодно снимок не требует открывать поля агрегата.

</SelfCheck>

<SelfCheck question="Тест TestSendMessageConcurrent без -race на 12 ядрах трижды показал 0 неудач. Значит ли это, что проверка версии не нужна?">

Нет. Ноль неудач после трёх попыток не значит ноль конфликтов: окно между `FindChat` и `AppendMessage` без детектора гонок очень узкое, а конфликт на первой попытке тест не считает — его исправляет повтор. Под `-race` окно шире, и неудачи видны. В настоящем сервисе между чтением и записью будут сетевые походы в базу длиной в миллисекунды, и окно станет на порядки шире. Тест проверяет корректность при любом числе конфликтов, а не их отсутствие.

</SelfCheck>
