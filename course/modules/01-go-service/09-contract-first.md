# 1.9. Contract-first: OpenAPI и генерация кода

## <Part kind="problem" /> Проблема: три описания одного API

Где сейчас записано, как выглядит API мессенджера? Попробуйте ответить, прежде чем читать дальше.

Честный ответ — в трёх местах, и ни одно не главное:

1. **В коде.** <T id="dto">DTO (data transfer object, объект передачи данных)</T> из урока 1.7 — `createChatRequest`, `messageResponse` и остальные — с тегами `json:"chat_id"`. Это то, что сервер делает на самом деле.
2. **В тексте уроков.** Примеры `curl` и пояснения «в ответе есть `seq`, номер сообщения в чате». Это то, что мы **думаем**, что сервер делает.
3. **В головах тех, кто пишет клиентов.** Это то, что клиент **ожидает**.

Пока клиент один и пишет его тот же человек, что и сервер, три описания совпадают сами собой. Но давайте проведём мысленный эксперимент. Кто-то решил, что `display_name` — длинно, и переименовал тег в DTO на `name`. Тесты адаптера сравнивают тело ответа со строкой — их поправили в том же коммите. Сборка зелёная, ревью прошло: изменение в две строки. Через час после выкладки мобильное приложение показывает пустые имена у всех пользователей: оно ищет в JSON поле `display_name`, а его больше нет. Ни компилятор, ни тесты не могли этого заметить — они проверяют сервер **сам с собой**.

Обратная ситуация не лучше. В тексте урока 1.8 написано, что ответ на ошибку — `{"error":{"code","message","field"}}`. Правда ли, что **каждый** обработчик, включая ответы маршрутизатора и аутентификации, пишет ровно это? Проверить можно только чтением всего кода. Описание, которое никто и ничто не сверяет с кодом, расходится с ним при первом же изменении — не из-за небрежности, а потому что ничто не мешает разойтись.

Сейчас это неприятно. Дальше — опасно. В модуле 3 появится мобильная команда, которая напишет клиента, ни разу не открыв наш Go-код. В модуле 6 перед сервисами встанет API-шлюз, который проверяет и маршрутизирует запросы по описанию API. Обоим нужно описание, которому можно доверять, и желательно машиночитаемое: чтобы генерировать из него код клиента, а не переписывать его руками с примеров.

Вопрос урока: как сделать так, чтобы описание API было **одно**, и чтобы сервер не мог незаметно от него отступить?

## <Part kind="theory" /> Code-first и contract-first: кто здесь главный

Подходов два, и различаются они ответом на вопрос «что первично — код или описание?».

**Code-first.** Сначала пишется код сервера, а описание API получается из него: генератор читает Go-типы и комментарии-аннотации (как `swaggo/swag`) и выдаёт документ. Удобно: пишешь как привык, описание «бесплатно». Но описание здесь — **следствие** кода. Оно честно рассказывает, что сервер делает сейчас, — включая случайные изменения. Переименование `display_name` из примера выше попало бы в описание автоматически и выглядело бы как законное. Обсудить API с клиентами до того, как написан сервер, тоже нельзя: описания ещё нет.

<T id="contract-first">Contract-first (сначала контракт; также API-first)</T> — наоборот: сначала пишется **контракт** — формальное описание API, — его обсуждают с клиентами, и только потом пишется код, который этот контракт выполняет. Контракт — <em>источник правды</em>: если код и контракт расходятся, ошибка в коде. Изменение API начинается с изменения контракта, а не с правки DTO.

Аналогия — строительство дома. Code-first — построить дом, а потом обмерить его и начертить план «как есть». Contract-first — сначала утвердить чертёж с заказчиком, а потом строить по нему, и прораб сверяет каждую стену с чертежом. Где аналогия перестаёт работать: стену дома нельзя «перекомпилировать», а код — можно. Поэтому в программировании чертёж можно не только сверять с постройкой, но и **генерировать** из него часть постройки — это мы и сделаем.

Как это устроено у тех, кто живёт с API много лет:

- **Google** описывает все свои API на языке protobuf: файл `.proto` — контракт, из которого генерируются сервер и клиенты на десятке языков. Даже HTTP-интерфейс к gRPC-сервисам задаётся аннотациями внутри `.proto`. Их API Design Guide, который мы цитировали в 1.8, написан для этого подхода.
- **Stripe** публикует OpenAPI-описание своего API (репозиторий `stripe/openapi`), и их официальные клиентские библиотеки генерируются из него — в файлах SDK так и написано: «File generated from our OpenAPI spec». Клиенты на разных языках не расходятся с API, потому что ни один из них не пишется по примерам.
- **Zalando** в своих RESTful API Guidelines делает API First первым правилом: «MUST follow API first principle» и «MUST provide API specification using OpenAPI». Контракт проходит ревью до реализации.

Общее у всех трёх — описание API живёт отдельно от реализации, машиночитаемо, и из него получают код. Различаются формат и строгость.

<Callout type="simplified">

На деле граница между подходами размыта. Code-first с дисциплиной (CI сравнивает описание, полученное из кода, с предыдущей версией и не пропускает ломающие изменения) защищает от многих тех же ошибок. А contract-first без проверки кода по контракту — это просто документация. Важно не название, а ответ на вопрос: **что проверяет, что сервер выполняет описание?** Весь остаток урока — про этот ответ.

</Callout>

## <Part kind="theory" /> OpenAPI: из чего состоит контракт

<T id="openapi">OpenAPI (OpenAPI Specification)</T> — стандартный формат описания HTTP API в YAML или JSON. Его предшественник назывался Swagger: в 2015 году спецификацию Swagger 2.0 передали OpenAPI Initiative под крылом Linux Foundation и переименовали, а первая версия, созданная уже под новым именем, — 3.0 — вышла в 2017 году. Мы используем версию **3.0.3**.

Документ OpenAPI — дерево. Верхние ключи:

- `openapi` — версия спецификации, по которой написан документ;
- `info` — название, версия **нашего** API (не спецификации) и описание;
- `servers` — где API доступен;
- `paths` — пути и операции; главная часть;
- `components` — переиспользуемые куски: схемы, параметры, ответы, заголовки, схемы безопасности;
- `tags`, `security` — группировка операций и требования к аутентификации.

**Путь и операция.** Ключ в `paths` — шаблон пути, `/v1/chats/{id}/messages`. Под ним — методы HTTP; пара «путь + метод» называется **операцией**. У операции есть:

- `operationId` — уникальное имя операции, `sendMessage`. Генератор сделает из него имя метода Go — `SendMessage`, поэтому его выбирают так же тщательно, как имя функции;
- `parameters` — параметры пути (`in: path`), строки запроса (`in: query`), заголовка, cookie. У каждого — имя, обязательность и схема;
- `requestBody` — тело запроса: обязательно ли и в каких медиатипах (`application/json`) какой схеме соответствует;
- `responses` — ответы по кодам статуса: `'201'`, `'400'`, … (ключи — строки, поэтому в кавычках). У каждого — описание, заголовки и тело;
- `tags` — метки для группировки; мы используем их ещё и как границу контекстов (об этом ниже);
- `security` — какая схема аутентификации нужна; у документа есть общее значение, операция может его переопределить. `security: []` у регистрации значит «без аутентификации».

**Ссылки `$ref`.** Двенадцать раз писать одну и ту же схему ошибки — значит двенадцать раз её не обновить. Поэтому повторяющееся выносят в `components` и ссылаются: `$ref: '#/components/schemas/Message'`. Это JSON Pointer — путь внутри документа от корня `#`. В `components` у нас пять разделов: `schemas` (формы данных), `parameters` (параметр `id` пути и `limit` — общие для нескольких операций), `responses` (готовые ответы-ошибки: `NotFound`, `Conflict`, …), `headers` (`Location`) и `securitySchemes` (`X-User-ID`).

Вот операция отправки сообщения в нашем контракте (полный текст — в разделе «Код»):

```yaml
/v1/chats/{id}/messages:
  parameters:
    - $ref: '#/components/parameters/ID'   # общий для POST и GET
  post:
    tags: [chats]
    operationId: sendMessage
    requestBody:
      required: true
      content:
        application/json:
          schema: { $ref: '#/components/schemas/SendMessageRequest' }
    responses:
      '201':
        description: Сообщение сохранено
        content:
          application/json:
            schema: { $ref: '#/components/schemas/Message' }
      '404': { $ref: '#/components/responses/NotFound' }
```

Обратите внимание: `parameters` стоит над методами, на уровне пути. Так параметр `{id}` описан один раз для `POST` и `GET`.

## <Part kind="theory" /> Схемы: подмножество JSON Schema

Форма данных в OpenAPI описывается **схемой** (Schema Object). Её язык — <T id="json-schema">JSON Schema</T>, отдельный стандарт описания JSON-документов. В версии 3.0 OpenAPI берёт его не целиком, а «расширенное подмножество» черновика JSON Schema Wright Draft 00: часть ключевых слов взята как есть, часть изменена, часть добавлена своя. Нам понадобятся такие:

| Ключевое слово | Что значит | Пример у нас |
|---|---|---|
| `type` | тип значения: `object`, `array`, `string`, `integer`, `number`, `boolean` | `seq: { type: integer }` |
| `format` | уточнение типа: `int64`, `date-time`, `uuid`, … | `sent_at: { format: date-time }` |
| `required` | какие свойства объекта обязательны | `required: [text]` |
| `properties` | схемы свойств объекта | `text: { type: string }` |
| `additionalProperties` | можно ли свойства сверх перечисленных | `additionalProperties: false` |
| `enum` | допустимые значения | `kind: { enum: [direct, group] }` |
| `minimum`, `maximum` | границы числа | `limit: { minimum: 1, maximum: 100 }` |
| `minLength`, `maxLength`, `pattern` | границы и шаблон строки | `username: { pattern: '^[a-z0-9_]+$' }` |
| `items` | схема элемента массива | `member_ids: { items: { type: string } }` |
| `nullable` | значение может быть `null` (только в 3.0) | — |

Две тонкости, о которые спотыкаются все.

**`required` и `nullable` — разные вещи.** `required` говорит, есть ли **ключ** в объекте. `nullable: true` — может ли значение быть `null`. Поле `title` у нашего `Chat` необязательное: у личного чата его просто нет в JSON. Это не то же самое, что `"title": null`, — и в контракте мы не разрешаем `null`, потому что сервер так не пишет.

**`format` — подсказка, а не всегда проверка.** Спецификация разрешает инструментам не проверять незнакомые форматы. Как увидим, генератор превратит `format: uuid` в тип Go `UUID`, а валидатор kin-openapi по умолчанию проверяет `date-time`, но **не** `uuid`. Что именно проверяет `format`, зависит от инструмента — это надо знать, а не предполагать.

**Почему 3.0.3, а не 3.1.** В версии 3.1 (2021) OpenAPI отказался от своего подмножества и стал полностью совместим с JSON Schema 2020-12: `nullable` заменён на `type: [string, "null"]`, появились `const`, `if/then/else` и многое другое. Для нового проекта это лучший язык. Мы всё же пишем 3.0.3 ради поддержки инструментами: на 3.0 описано подавляющее большинство существующих API, и её понимают все инструменты, которые встретятся нам дальше, — генераторы клиентов для мобильной команды, шлюзы, линтеры, интерфейсы документации. Поддержка 3.1 у многих из них моложе: в выбранном нами генераторе oapi-codegen она появилась недавно, и его README называет её начальной (initial). Возможности 3.1 нашему контракту пока не нужны — значит, нет причины платить за них поддержкой инструментов. Перейти позже несложно: это в основном механическая замена `nullable`.

## <Part kind="theory" /> Генерация кода: oapi-codegen

<T id="code-generation">Кодогенерация (code generation)</T> — программа пишет код за нас по формальному описанию. Из контракта можно получить три вещи: **модели** (Go-типы для схем), **серверную обвязку** (маршруты, разбор параметров, интерфейс, который должен реализовать наш обработчик) и **клиента** (функции, которые делают запросы). Мы генерируем первые две; клиентов из того же контракта будут генерировать мобильная команда и шлюз — каждый на своём языке.

Генератор — **oapi-codegen** v2, самый распространённый для Go. Он умеет генерировать сервер под разные маршрутизаторы — Chi, Echo, Gin, Fiber, gorilla/mux и стандартный `net/http` — и в двух стилях:

- **обычный сервер** (`std-http-server`, `chi-server`, …) — обработчик получает `http.ResponseWriter` и `*http.Request`, плюс уже разобранные параметры пути и строки запроса. Тело запроса и ответ — забота обработчика;
- **строгий сервер** (`strict-server`) — обработчик получает разобранное тело запроса и **возвращает** значение одного из сгенерированных типов ответа (`SendMessage201JSONResponse`, `SendMessage404JSONResponse`, …). Сериализацию делает сгенерированный код.

Мы берём `std-http-server`. Причины:

- маршрутизатор тот же `http.ServeMux`, что в уроках 1.7–1.8: генератор регистрирует на нём шаблоны вида `"POST /v1/chats/{id}/messages"`, и конвейер middleware из 1.8 работает без изменений. Никакого фреймворка;
- обработчики остаются нашими: тело по-прежнему разбирает `httpjson.Decode` — с лимитом 1 МиБ, запретом неизвестных полей, проверкой «ровно один объект» и ответом 415. Строгий сервер разбирает тело сам, простым `json.NewDecoder(r.Body).Decode` — без этих проверок (мы прочитали шаблон `strict-http.tmpl` в исходниках v2.8.0);
- ответы пишем мы, через тот же `httpjson.Write` и общую таблицу ошибок.

Цена — компилятор не проверяет форму ответов. Это мы закроем тестом; к этому компромиссу вернёмся в конце урока.

**Граница контекстов в генерации.** Если сгенерировать весь контракт в один пакет, адаптер контекста `chat` будет видеть тип `RegisterUserRequest` контекста `user` (с урока 1.13 эта схема называется `SignUpRequest` и принадлежит контексту `auth`) — правило из урока 1.1 «контексты не знают друг друга» нарушится в сгенерированном коде. Поэтому генерация идёт **по пакету на контекст**: опция `include-tags` оставляет только операции с нужным тегом. `user/adapters/httpapi/gen` получает операции с тегом `users`, `chat/adapters/httpapi/gen` — с тегом `chats`. Общие схемы — например, `ErrorResponse` — сгенерируются в оба пакета: это два независимых типа, и это правильно — каждый контекст владеет своими DTO.

**Как запускается генератор.** До Go 1.24 инструменты для разработки подключали через файл `tools.go` с пустыми импортами — обходной путь, чтобы версия инструмента попала в `go.mod`. В Go 1.24 появилась директива `tool`:

```bash
go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@v2.8.0
```

Команда добавляет в `go.mod` строку `tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen`, а версия фиксируется в `require` вместе с остальными зависимостями. После этого `go tool oapi-codegen` запускает **именно эту** версию — у каждого разработчика и в CI одинаковую, без отдельной установки.

Запуск генерации — `go generate ./...`. Эта команда не часть сборки: `go build` её не вызывает. Она ищет в исходниках комментарии `//go:generate команда` и выполняет команду в каталоге файла. Отсюда важное следствие: **сгенерированный код коммитится** в репозиторий. Проект собирается без генератора, а изменения API видны в ревью как изменения Go-типов.

## <Part kind="theory" /> Что ловит компилятор, а что — только тест

Генерация не делает сервер правильным автоматически. Она переносит часть ошибок из прода в сборку — но только часть. Разберём, кто что ловит.

Обработчик **читает** из контракта: имена и типы полей тела запроса, параметры пути и строки запроса, набор операций. Всё это пришло в Go-типах из `api.gen.go`, и строка `var _ gen.ServerInterface = (*Handler)(nil)` заставляет компилятор сверить наш тип с интерфейсом. Переименовали в контракте поле запроса — исчезло поле структуры, и `req.Text` не компилируется. Переименовали `operationId` — у интерфейса другой метод, и `*Handler` перестаёт его реализовывать.

Обработчик **пишет** ответ сам: `httpjson.Write(w, status, v)` принимает `any`. Компилятор не знает, что для 201 контракт обещал `Message`, а не `map[string]any`, и что статус 418 контрактом не предусмотрен. Это может проверить только тот, кто посмотрит на настоящий ответ и сравнит его со схемой, — <T id="contract-test">контрактный тест (contract test)</T>. У нас это обёртка из пакета `platform/openapitest`: тесты адаптеров гоняют запросы через настоящий маршрутизатор, а обёртка сверяет каждый ответ с `api/openapi.yaml`.

| Расхождение | Кто ловит | Когда |
|---|---|---|
| нет обработчика для операции; переименован `operationId` | компилятор: `*Handler does not implement gen.ServerInterface` | `go build` |
| переименовано или удалено поле тела запроса | компилятор: `req.Text undefined` | `go build` |
| сменился тип параметра пути или строки запроса | компилятор: другая сигнатура метода | `go build` |
| поле ответа другого типа (`"seq":"1"`) | контрактный тест | `go test` |
| в ответе нет обязательного поля или есть лишнее | контрактный тест | `go test` |
| статус, которого нет в контракте (404 у регистрации) | контрактный тест (`IncludeResponseStatus`) | `go test` |
| `api.gen.go` не обновили после правки контракта | проверка актуальности: `go generate` ничего не должен менять | `npm run check:messenger` |
| сервер отвечает по форме, но **не то** (404 вместо 403, чужие сообщения) | никто из них — только обычные тесты поведения | — |

Последняя строка важна. Контракт описывает **форму**: какие поля, каких типов, с какими статусами. Он не знает, что не-участник чата должен получить 403, а не 404, или что история должна быть отсортирована по `seq`. Это семантика, и её проверяют обычные тесты use case'ов и адаптеров, как раньше. Контрактный тест их не заменяет — он добавляется к ним.

И ещё одна тонкость: контрактный тест проверяет только те ответы, которые через него **прошли**. Если ни один тест не вызывает `GET /v1/users/{id}` с ответом 404, форма этого ответа не проверена. Поэтому у валидатора есть метод `Uncovered` — список операций, ни один ответ которых не проверялся. В уроке 1.14 сквозной тест потребует, чтобы этот список был пуст.

## <Part kind="theory" /> Эволюция контракта и совместимость

Контракт — не застывший документ: в следующих уроках мы добавим пагинацию, ключ идемпотентности, новый формат ошибок. Значит, нужно понимать, какие изменения клиенты переживут, а какие нет. Мартин Клеппман в главе 4 «Designing Data-Intensive Applications» разбирает это для форматов данных вообще и вводит два понятия.

<T id="backward-compatibility">Обратная совместимость (backward compatibility)</T> — новый код читает данные, записанные старым. **Прямая совместимость (forward compatibility)** — старый код читает данные, записанные новым. Для API по HTTP Клеппман делает практический вывод: сервер обычно обновляют раньше клиентов (особенно мобильных — их обновляют пользователи, когда захотят). Значит, нужно, чтобы **новый сервер понимал запросы старых клиентов** (обратная совместимость по запросам) и чтобы **старые клиенты понимали ответы нового сервера** (прямая совместимость по ответам).

Что из этого следует для изменений контракта:

- **добавить необязательное поле в запрос** — совместимо: старые клиенты его не пришлют, сервер обойдётся значением по умолчанию;
- **добавить поле в ответ** — совместимо, **если** старые клиенты игнорируют незнакомые поля;
- **сделать поле запроса обязательным, удалить поле ответа, сменить тип, переименовать** — несовместимо: это новая версия API (урок 1.8).

Условие «если клиенты игнорируют незнакомые поля» — это принцип терпимого читателя, частный случай **закона Постела** из спецификации TCP (RFC 793, 1981): «будь консервативен в том, что отправляешь, и либерален в том, что принимаешь». Клиент, который падает на незнакомом поле, превращает каждое добавление в ответ в несовместимое изменение. В индустрии нет единого мнения, хорош ли закон Постела в целом: RFC 9413 (2023) подробно разбирает, как чрезмерная терпимость годами консервирует ошибки отправителей. Но для **ответов** API терпимость клиента к новым полям — общепринятая норма. Zalando записывает её отдельным правилом («MUST prepare clients to accept compatible API extensions»), а Google и Microsoft в своих правилах совместимости относят добавление поля в ответ к совместимым изменениям — что и предполагает такого клиента.

Теперь посмотрите на наш контракт: у каждой схемы ответа стоит `additionalProperties: false` — «других полей нет». Не противоречие ли это? Нет, если понимать, **для кого** это ограничение. Для нашего контрактного теста оно означает: сервер не имеет права отдать поле, которого нет в контракте. Захотели добавить `last_message_at` в ответ чата — сначала добавьте его в контракт. Это защищает от случайных полей вроде отладочного `"debug": true`, которые клиенты начнут использовать и которые потом нельзя будет убрать. Клиентам же это ограничение **не** даёт права падать на новых полях: когда контракт вырастет, `additionalProperties: false` в новой версии будет перечислять уже больше полей. Генератор клиента, который понял его как «отвергай всё незнакомое», сделает клиента хрупким, — и это стоит явно оговорить в документации API для клиентов.

У нашего **сервера** с запросами ситуация обратная: `httpjson.Decode` отвергает неизвестные поля в теле (400 `bad_json`). Это сознательная строгость: опечатка `"txet"` вместо `"text"` должна давать понятную ошибку, а не молчаливо пустое сообщение. Цена — удалить поле из запроса будет несовместимо, мы обсуждали это в самопроверке урока 1.8.

## <Part kind="theory" /> Ограничения: контракт документирует, домен решает

В схеме `RegisterUserRequest` (с урока 1.13 — `SignUpRequest`) написано `username: { minLength: 3, maxLength: 32, pattern: '^[a-z0-9_]+$' }`. Ровно эти правила уже проверяет домен — конструктор `NewUsername` из урока 1.2. Разве это не дублирование знания, которое стандарт кода требует устранять сразу?

Это дублирование, и мы идём на него сознательно — но с чётким распределением ролей:

- **домен решает.** Только `NewUsername` определяет, допустимо ли имя. Сгенерированный код границ `minLength`, `maximum` и т. п. **не проверяет** — ни в теле (его разбирает наш `httpjson.Decode`), ни в параметрах: `?limit=500` пройдёт сгенерированную обёртку, и отказ даст use case. Второй проверки в адаптере мы не пишем;
- **контракт документирует.** Клиенту нужно знать правила, чтобы проверить ввод на экране, до отправки, — без запроса к серверу. Мобильная команда сгенерирует валидацию формы прямо из `pattern` и `maxLength`.

Если они разойдутся — например, домен разрешит имена до 64 символов, а контракт останется с 32, — **прав домен**, а контракт содержит ошибку документации, и чинят её в контракте. Так записано в ADR-0006. Контрактный тест такое расхождение не поймает: он проверяет ответы, а не запросы. Ловить его можно было бы, проверяя ещё и запросы тестов по контракту, — но тогда тесты, которые намеренно шлют неверные данные, чтобы проверить ошибки домена, пришлось бы помечать исключениями. Мы проверяем только ответы.

<Callout type="simplified">

Почему id в телах запросов — `string`, а не `UUID`? Если в схеме написать `format: uuid`, генератор сделает поле типа `openapi_types.UUID`, и кривой id в JSON упадёт в `encoding/json` ещё при разборе тела. Мы проверили: на `{"member_ids":["bob"]}` клиент получил бы 400 `bad_json` с текстом «некорректный JSON» и без `field` — ошибка разбора `uuid` не говорит, какое поле виновато. Поэтому у свойств-идентификаторов стоит расширение `x-go-type: string`: в контракте для клиентов это по-прежнему `format: uuid`, а в Go — строка, которую проверит домен (`ParseUserID`) и назовёт в ошибке поле `member_ids`, как в контракте. Параметр пути `{id}` — другое дело: его разбирает сгенерированная обёртка, ошибка приходит с именем параметра `id`, и мы переводим её в наш формат. Расширения `x-…` — штатный механизм OpenAPI для пометок, которые понимает конкретный инструмент; другие инструменты их просто игнорируют.

</Callout>

	CreatedAt time.Time `json:"created_at"`
	Id        string    `json:"id"`

<Deep title="как kin-openapi проверяет ответ">

Вся проверка ответа — функция `ValidateResponse` в файле `openapi3filter/validate_response.go` библиотеки kin-openapi (мы читали исходники версии v0.149.0). Она получает операцию, которую нашёл маршрутизатор, статус, заголовки и тело ответа и идёт по шагам.

Сначала короткие выходы. Ответ на `HEAD` не проверяется вовсе: тела у него нет. Не проверяются и перенаправления — 301, 304, 307, 308. Если у операции не описано ни одного ответа, проверять тоже нечего.

Затем поиск описания ответа. Функция ищет в `responses` операции точный код статуса — у нас, например, `'201'`. Не нашла — берёт ответ `default`, если он описан. Не нашла и его — и вот здесь решает флаг `IncludeResponseStatus`. По умолчанию он выключен, и функция возвращает «всё хорошо»: недокументированный статус считается допустимым. Это осознанное решение авторов — многие контракты описывают только успешные ответы, — но для нас оно означает, что 404 у регистрации прошёл бы молча. Поэтому мы флаг включаем, и неописанный статус превращается в ошибку «status is not supported».

Дальше — заголовки. Для каждого описанного у ответа заголовка, кроме `Content-Type`, функция достаёт значение, разбирает его по правилам сериализации OpenAPI и сверяет со схемой. Если заголовок помечен обязательным, а его нет, — ошибка. Наш `Location` не обязателен, поэтому проверяется только тогда, когда он есть.

Потом медиатип. Функция берёт `Content-Type` ответа и ищет его среди `content` описания: сначала полностью, затем без параметров — поэтому наш `application/json; charset=utf-8` находит описание `application/json`. Не нашла — ошибка: сервер ответил не в том формате, что обещал.

Наконец, тело. Его читают целиком и разбирают **декодером** для этого медиатипа — по умолчанию их зарегистрировано четырнадцать: JSON и его разновидности (включая `application/problem+json`, который понадобится нам в уроке 1.10), формы и `multipart/form-data`, YAML, CSV, простой текст и `application/octet-stream`; для прочих типов декодер регистрируют сами функцией `RegisterBodyDecoder`. Разобранное значение — уже не байты, а дерево из `map`, срезов, строк и чисел — передаётся методу `VisitJSON` схемы с пометкой «это ответ». `VisitJSON` рекурсивно обходит схему и значение вместе: проверяет тип, обязательные свойства, `additionalProperties`, `enum`, границы и форматы, для которых зарегистрирован проверяющий. Первая найденная ошибка возвращается с путём к полю — так и получается `Error at "/seq"`. Пометка «это ответ» нужна для свойств `writeOnly`: они могут быть в запросе, но не в ответе.

</Deep>

## <Part kind="mistakes" /> Типичные ошибки

<Callout type="mistake">

**Править `api.gen.go` руками.** «Мне нужно только поменять тег у одного поля». Правка проживёт до следующего `go generate`, который её молча сотрёт, — у другого разработчика, через месяц. Если сгенерированное не подходит, меняют контракт или конфигурацию генератора (`x-go-type`, `x-go-name`, `name-normalizer`), а не результат. Наша проверка актуальности поймает такую правку: `go generate` её откатит, и файл окажется изменённым.

**Один пакет `gen` на все контексты.** Удобно: один `config.yaml`, один `generate.go`. Но тогда адаптер чатов видит `RegisterUserRequest`, а адаптер пользователей — `Message`, и граница контекстов, которую охраняет `depguard`, обходится через общий пакет DTO. Начнут с «просто переиспользую тип», закончат связанностью, которую мы три урока разносили. По пакету на контекст и `include-tags` — граница в генерации такая же, как в коде.

**`format: uuid` везде, не думая, кто проверяет.** На параметре пути это хорошо: обёртка проверит и назовёт параметр. На поле тела запроса — генератор сделает тип `UUID`, и ошибка разбора придёт из `encoding/json` до домена: клиент получит безликое «некорректный JSON» без поля вместо доменного «должен быть UUID в нижнем регистре» с `field`, а правило «UUID только в нижнем регистре» вообще перестанет проверяться — `uuid.UUID` нормализует регистр. Решите, **кто** владеет проверкой, и опишите тип так, чтобы проверял он.

**Контракт как документ.** `openapi.yaml` лежит в репозитории, по нему сгенерирована красивая страница документации, но ни код, ни тесты от него не зависят. Через три месяца в нём нет половины полей и описан несуществующий статус. Это и есть «описание в тексте урока», только в YAML. Контракт без проверки хуже, чем отсутствие контракта: ему верят.

**Генерация в CI без проверки актуальности.** CI запускает `go generate` перед сборкой — и всё всегда зелёное, потому что собирается свежесгенерированный код. А в репозитории лежит устаревший `api.gen.go`, и ревьюер видит в diff не то, что поедет в прод. Генерировать нужно **у разработчика**, коммитить результат, а в CI — проверять, что генерация ничего не меняет: `go generate ./... && git diff --exit-code`.

**Описывать в контракте только успешные ответы.** «Ошибки и так понятны». Клиент не узнает, что `POST /v1/chats/{id}/messages` может вернуть 409 и что делать с ним — повторить. А валидатор без `IncludeResponseStatus` будет пропускать любые статусы, с ним — падать на каждом неописанном. Ответы-ошибки — такая же часть контракта, как 201, и `components/responses` делает их описание дешёвым.

</Callout>

## <Part kind="tradeoff" /> Компромисс: генерация против ручных DTO

<Callout type="tradeoff">

**Генерация из контракта даёт** гарантии на входе: всё, что обработчик читает из запроса, — имена полей, параметры, набор операций — сверено с контрактом компилятором. Клиенты получают описание, которому можно верить, и генерируют свой код из него же: мобильная команда не переписывает DTO с примеров. Изменение API становится видимым — сначала правка контракта, потом diff сгенерированных типов на ревью.

**Чем платим.** Новая зависимость, и не одна: генератор как инструмент, `oapi-codegen/runtime` в рантайме, kin-openapi в тестах. Сгенерированный код в репозитории (у нас — сотни строк) и процедура проверки его актуальности. Правила генератора, которые нужно знать: имена `Id` вместо `ID`, указатели для необязательных полей, алфавитный порядок полей, расширения `x-go-type`. И гарантия на выходе остаётся тестовой, а не компиляторной: ответ, который не проверил ни один тест, может не совпадать с контрактом.

**Ручные DTO гибче:** любые имена, любые типы, никаких генераторов. Но правду о форме API они не гарантируют — они и есть одно из трёх описаний из начала урока.

**Когда что выбирать.** Генерация из контракта окупается, когда у API есть клиенты, которых пишут другие люди, — мобильные приложения, другие команды, внешние интеграции — и когда API будет жить годами. Ручные DTO уместны во внутреннем API, у которого один клиент в том же репозитории и та же команда, или в прототипе, который проживёт неделю. Промежуточный вариант — `strict-server`: проверяет компилятором и ответы, но забирает у обработчика разбор тела; выбирайте его, если готовы жить с его декодером или подменять его своим middleware.

</Callout>

## <Part kind="selfcheck" /> Самопроверка

<SelfCheck question="Коллега говорит: «У нас теперь генерация из контракта, контрактные тесты можно удалить — компилятор всё проверит». Прав ли он?">

Нет. Компилятор проверяет то, что обработчик **получает** из контракта: поля тела запроса, параметры, набор операций — они пришли в Go-типах и сигнатуре `ServerInterface`. Ответ обработчик пишет сам через `http.ResponseWriter` и `httpjson.Write(w, status, v any)` — тип тела и статус компилятор не знает. Поле не того типа, лишнее поле, недокументированный статус ловит только проверка настоящего ответа по схеме. Компилятором ответы проверяет режим `strict-server`, но мы его не используем.

</SelfCheck>

<SelfCheck question="Мы хотим добавить в ответ Message поле edited_at. Что нужно поменять и в каком порядке? Что случится, если начать с маппера?">

Сначала контракт: свойство `edited_at` в схеме `Message` (необязательное — старые сообщения не редактировались). Затем `go generate ./...` — в `gen.Message` появится поле `EditedAt *time.Time`. Затем маппер `toMessage` и тест. Начать с маппера не получится: в `gen.Message` нет такого поля, и код не соберётся. А если обойти это, отдав ответ через `map`, контрактный тест упадёт на лишнем поле — схема `Message` запрещает его через `additionalProperties: false`. Добавление необязательного поля в ответ совместимо для клиентов, которые игнорируют незнакомые поля.

</SelfCheck>

<SelfCheck question="В контракте у username стоит maxLength: 32, а домен после правки разрешает 64. Какой тест упадёт? Кто прав?">

Никакой: контрактный тест проверяет ответы, а не запросы, и сгенерированный код ограничения тел запросов не проверяет. Регистрация с именем из 40 символов пройдёт — домен её разрешает. Прав домен: ограничения в контракте — документация для клиентов (ADR-0006). Расхождение — ошибка документации, исправлять нужно контракт; иначе клиенты будут отказывать пользователям в именах, которые сервер принял бы.

</SelfCheck>

<SelfCheck question="Зачем генерировать по пакету на контекст, если схема ErrorResponse одинаковая и в итоге сгенерируется дважды?">

Чтобы граница контекстов из урока 1.1 сохранилась и в сгенерированном коде. Общий пакет `gen` дал бы адаптеру чатов доступ к DTO пользователей, и связь между контекстами появилась бы в обход портов и `depguard`. Два одинаковых типа `ErrorResponse` в разных пакетах — не дублирование знания: знание (схема) записано один раз, в контракте, а Go-типы — его механические проекции, которые никто не правит руками.

</SelfCheck>

<SelfCheck question="Почему kin-openapi по умолчанию пропускает ответ со статусом, которого нет в контракте, и что мы с этим сделали?">

Функция `ValidateResponse` ищет описание ответа по коду статуса, потом `default`; если не нашла ни того, ни другого, а флаг `IncludeResponseStatus` выключен, она считает ответ допустимым — многие контракты описывают только успешные ответы, и строгость по умолчанию ломала бы их проверку. Нам нужна строгость: каждый статус — обещание клиенту. Поэтому `openapitest` включает флаг, и неописанный статус превращается в ошибку «status is not supported» — именно так нашёлся тест, проверявший 404 у регистрации.

</SelfCheck>
