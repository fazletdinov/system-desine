# ADR-0003. JWT с подписью Ed25519 вместо заголовка X-User-ID

## Статус

Принято, 2026-10-14. Заменяет [ADR-0002](0002-x-user-id-до-jwt.md).

## Контекст

До урока 1.14 личность вызывающего приходила заголовком `X-User-ID` (ADR-0002): клиент сам называл свой id, и сервер ему верил. Это заглушка — назваться можно кем угодно. В уроке 1.13 появились пароли и вход (`Login`), не хватало одного: чем вход доказывает личность в следующих запросах.

Силы, которые действуют на решение:

- **Распределённая проверка.** В модуле 6 мессенджер распадётся на сервисы за API-шлюзом. Личность будет проверять шлюз, а за ним — несколько сервисов. Если каждая проверка — поход в сервис auth или в его базу, auth становится узким местом и единой точкой отказа для всех запросов.
- **Выпускает только auth.** Право выдавать личность должно быть у одного контекста. Проверяющих много, выпускающий — один.
- **Отзыв.** Вышел из аккаунта, украли устройство, заблокировали пользователя — доступ должен прекратиться. Чем быстрее, тем лучше.
- **Хендлеры не меняются.** Порт `httpauth.Authenticator` из урока 1.8 создан ровно для этой замены: обработчики берут личность из контекста и не знают, откуда она.

## Рассмотренные варианты

1. **Сессии в базе с непрозрачным токеном.** Вход создаёт случайный токен, сервер хранит его (или его хеш) в таблице с владельцем и сроком; каждый запрос — поиск по таблице. Так делает Алекс Эдвардс в «Let's Go Further» (таблица `tokens`, хранится SHA-256 токена). Плюсы: отзыв мгновенный — удалить строку; токен ничего не рассказывает о пользователе; простая и проверенная схема. Минусы: каждая проверка — запрос к хранилищу auth; в модуле 6 это сетевой вызов из шлюза и из каждого сервиса.
2. **JWT с HMAC (HS256) и общим секретом.** Самодостаточный токен, проверка — пересчитать HMAC. Плюсы: проверка без сети; быстро. Минусы: секрет один на всех — каждый, кто умеет проверять, умеет и **выпускать**. Утечка секрета из любого сервиса — это возможность стать кем угодно везде. Смена секрета требует синхронно обновить всех.
3. **JWT с подписью открытым ключом (EdDSA, Ed25519).** Закрытый ключ только у auth, остальные проверяют открытым. Плюсы: проверка без сети и без права выпускать; утечка открытого ключа ничего не даёт; `kid` в заголовке позволяет держать несколько ключей на время смены. Минусы: выпущенный токен нельзя отозвать до истечения срока; токен длиннее непрозрачного; нужна дисциплина проверок (алгоритм, `aud`, `iss`, `exp`), иначе — известные атаки на JWT.
4. **mTLS между сервисами и OAuth 2.0 / OpenID Connect.** Плюсы: стандарт для федеративного входа и сторонних клиентов. Минусы: у нас нет ни сторонних клиентов, ни внешнего провайдера личности; объём протоколов несоизмерим с задачей. Вернёмся к ним в модуле 6.7.

## Решение

Мы принимаем вариант 3: JWT (RFC 7519) с подписью EdDSA на Ed25519 (RFC 8037).

- **Выпуск:** `POST /v1/tokens` (имя и пароль) → `200` с `access_token`, `token_type: Bearer`, `expires_in` и `Cache-Control: no-store` — форма ответа RFC 6749 §5.1, но без OAuth: нет клиентов, грантов и scope. Неверные имя или пароль — `401 invalid_credentials` с одним текстом на любую причину; причина — только в журнал под `request_id`.
- **Содержимое:** `iss = messenger`, `aud = messenger-api`, `sub` — id пользователя, `iat`, `nbf`, `exp = iat + 15 мин`, `jti` — UUIDv7. В заголовке `alg: EdDSA` и `kid` — отпечаток открытого ключа по RFC 7638.
- **Проверка** (`auth/adapters/jwt.Verifier`): алгоритм — только EdDSA, значение `alg` из токена не выбирает ничего; ключ — только из своего списка по `kid`; обязательны `exp`, `iss`, `aud`; `iat` не в будущем; допуск на расхождение часов — 30 секунд; пустой `sub` — отказ.
- **Транспорт:** заголовок `Authorization: Bearer <токен>` (RFC 6750). Отказ — `401` с `WWW-Authenticate: Bearer realm="messenger"`, а если токен был, но не прошёл, — с `error="invalid_token"`. Почему именно не прошёл, клиенту не сообщаем.
- **Порты:** `httpauth.TokenVerifier` объявлен в `platform/httpauth` (потребитель — `httpauth.Bearer`), реализация — `auth/adapters/jwt`. `TokenIssuer` объявлен в `auth/usecase`, реализация — тот же пакет. Соединяет их `cmd/messenger/app.go`.
- **Ключ:** Ed25519 в PKCS#8 PEM из файла `MESSENGER_JWT_KEY_FILE`; создаёт его `go run ./cmd/keygen -out jwt.pem` (права 0600, существующий файл не перезаписывается). Без переменной сервер не стартует. `*.pem` в `.gitignore`.

## Последствия

- **Плюсы:** проверка токена — чистая функция от токена, открытого ключа и часов: ни базы, ни сети. Шлюз и сервисы модуля 6 смогут проверять сами, не получив права выпускать. Подделать `sub`, сменить алгоритм или подсунуть чужой ключ нельзя — это закреплено тестом `TestVerifierRejects` (15 атак). Хендлеры, use case'ы и домен не изменились: заменилась одна реализация `Authenticator`.
- **Нельзя мгновенно отозвать токен.** Выход из аккаунта или блокировка пользователя не действуют на уже выданный токен до его `exp`. Срок 15 минут — это и есть худшее окно. Список отозванных `jti` и refresh-токены с ротацией (чтобы короткий срок не заставлял вводить пароль каждые 15 минут) — модуль 6.7.
- **Нет JWKS.** Открытый ключ сервис берёт из своего же закрытого. Публикация ключей по `/.well-known/jwks.json` появится вместе с первым внешним проверяющим — шлюзом модуля 6; `kid` уже в токене, так что формат не изменится.
- **Ротация ключа — вручную.** `Verifier` принимает несколько ключей, но загрузка списка и порядок смены (новый ключ сначала у проверяющих, потом у выпускающего) — модуль 6.7. Сейчас смена ключа обесценивает все выданные токены, поэтому `keygen` и не перезаписывает файл.
- **Токен — не шифрование.** Payload читается кем угодно (base64url). В токен не кладём ничего, кроме id и служебных claim'ов.
- **`X-User-ID` удалён** из контракта и кода. Запрос со старым заголовком получает `401`, как любой запрос без токена.
- **Без TLS токен виден в сети.** Сервис по умолчанию слушает только loopback; TLS — на шлюзе (модуль 6.7), в Docker (часть 1c) адрес задаётся явно.
