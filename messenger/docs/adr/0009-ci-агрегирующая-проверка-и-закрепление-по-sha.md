# ADR-0009. CI: фильтр путей на уровне джоб, агрегирующая проверка `ci-ok` и actions, закреплённые по SHA

## Статус

Принято, 2026-10-15.

## Контекст

До части 1c все проверки запускались руками: `npm run check:messenger`, `check:labs`, `check:images`. Ручную проверку забывают ровно тогда, когда она нужнее всего — в спешке перед слиянием. С урока 1.18 проверки выполняет GitHub Actions на каждый pull request и каждый коммит `main`, а ветка `main` защищена ruleset'ом: слить можно только то, что прошло обязательную проверку (задача 13, урок 1.19).

Силы, которые действуют на решение:

- **монорепозиторий.** В одном репозитории живут мессенджер (Go), курс (VitePress) и лабы. Правка опечатки в уроке не должна ждать `go test -race`, сборку образа и `trivy`; правка мессенджера должна проверить и курс — уроки ссылаются на его код через `<<<`;
- **обязательные проверки и пропуски.** По GitHub Docs («Troubleshooting required status checks»): джоба, пропущенная условием `if:`, отчитывается как Success; workflow, пропущенный целиком фильтром путей (`on.<событие>.paths`), фильтром веток или сообщением коммита (`[skip ci]`), не создаёт проверок вовсе, и обязательные проверки остаются в Pending, блокируя слияние;
- **кто открывает PR.** Сегодня — один разработчик, со следующей части — ещё и боты (Dependabot, урок 1.19). Репозиторий публичный: PR может прийти и из чужого форка, а журналы прогонов видны всем;
- **цепочка поставок.** Каждый `uses:` — чужой код, который выполняется на раннере с `GITHUB_TOKEN` и секретами. Теги действий изменяемы: в марте 2025 злоумышленник перевесил теги `tj-actions/changed-files` на коммит, который печатал секреты из памяти раннера в журнал (CVE-2025-30066, GHSA-mrrh-fwg8-r2c3, больше 23 000 репозиториев); в марте 2026 так же были перевешены 76 из 77 тегов `aquasecurity/trivy-action` — того самого action, которым мы сканируем образ (CVE-2026-33634, GHSA-69fq-xp46-6x23);
- **версия Go.** В `go.mod` записано `go 1.26.0` — минимальная версия языка. `setup-go` с `go-version-file` поставил бы ровно 1.26.0, и `govulncheck` нашёл бы уязвимости стандартной библиотеки, закрытые в патчах (на машине автора с Go 1.26.5 — 14 штук, урок 1.18).

## Рассмотренные варианты

1. **Без фильтра: все джобы на каждый PR.** Плюсы: проще некуда, обязательной можно сделать любую джобу. Минусы: правка урока ждёт сборку образа, `trivy`, сценарий лабы в privileged-контейнере — минуты раннера и внимания впустую; с ростом монорепозитория время растёт линейно.
2. **Фильтр через `on.pull_request.paths` в отдельном workflow на каталог.** Плюсы: стандартный синтаксис, workflow не запускается вовсе. Минусы: если такой workflow обязателен, PR без подходящих файлов висит в Pending навсегда — проверка ждёт статуса, который никто не пришлёт (GitHub Docs прямо советует не делать обязательными workflow, которые могут быть пропущены). Обходы — «пустой» двойник workflow с обратным фильтром или ручной обход ruleset — хрупки. Отвергнут.
3. **Фильтр на уровне джоб, обязательные проверки — по каждой джобе.** Плюсы: workflow стартует всегда, пропущенные джобы — Success. Минусы: имена девяти джоб зашиты в ruleset, и переименование или новая джоба требует правки настроек репозитория; хуже того, если упала сама джоба `changes`, все зависящие от неё джобы пропущены и формально «успешны» — обязательные проверки зелёные при не выполненной ни одной проверке. Отвергнут.
4. **Матрица по каталогам** (`strategy.matrix` по `messenger`, `course`, `labs`). Плюсы: одна джоба на все проекты. Минусы: шаги у проектов разные (Go, Node, Docker), матрица превращается в набор `if:` внутри шагов; имена проверок — `job (messenger)` и т. п. — всё так же надо перечислять в ruleset. Отвергнут для нашей формы проектов; матрица пригодится внутри проекта (шардирование тестов), когда он станет медленным.
5. **Фильтр на уровне джоб (`dorny/paths-filter` + `if:`) и одна агрегирующая джоба `ci-ok`** с `needs:` на все джобы и `if: always()`, которая падает, если хоть одна из них `failure` или `cancelled`. Плюсы: в ruleset одно стабильное имя; добавление и переименование джоб не трогает настройки; падение `changes` или отмена прогона дают красный `ci-ok`. Минусы: ещё одна джоба (секунды); `ci-ok` надо не забыть дополнить в `needs:` при добавлении новой джобы — это видно в ревью того же PR.

По цепочке поставок:

- **ссылка на action: тег (`@v7`), ветка (`@main`) или полный SHA.** Тег и ветка изменяемы — вариант защищает только от случайных поломок, не от атаки. Полный SHA неизменяем; цена — нечитаемые ссылки и ручное обновление, которое снимает Dependabot (`github-actions`, урок 1.19). Lockfile зависимостей workflow (`.github/workflows/actions.lock`, `gh actions-lock`) закрепляет и транзитивные actions, но на дату решения он в public preview;
- **права `GITHUB_TOKEN`:** умолчание репозитория или явный минимум. Явный минимум переживает смену настроек репозитория и виден в ревью.

## Решение

Мы принимаем пятый вариант и следующие правила для всех workflow репозитория.

- **Один workflow `ci`** на события `pull_request`, `push` в `main` и `workflow_dispatch`. Фильтры путей — только на уровне джоб: джоба `changes` с `dorny/paths-filter` выдаёт флаги `messenger`, `course`, `labs`, `workflows`; на `push` и `workflow_dispatch` все флаги истинны — `main` проверяется целиком. Фильтр `messenger` включает и сам `ci.yml`: правка workflow прогоняет всё, что он описывает.
- **`ci-ok` — единственная обязательная проверка** в ruleset для `main`. `if: always()`, `needs:` — все джобы, результат `needs.*.result` передаётся в скрипт через `env:`.
- **Каждый `uses:` закреплён полным SHA** с комментарием `# vX.Y.Z`; версия — не моложе двух недель на дату закрепления; SHA берётся из репозитория самого action, а не форка. Инструменты, которые ставятся командой, закреплены версией: `go run …@v1.7.12` (модули Go проверяются по `sum.golang.org`, Scorecard считает полную semver-версию модуля закреплённой), `golangci-lint` и `trivy` — входом `version`.
- **Права:** на уровне workflow `permissions: contents: read`; джоба, которой нужно больше, получает права сама и только свои (`changes` — `pull-requests: read`, без `contents`: checkout ей не нужен). `actions/checkout` — всегда с `persist-credentials: false`.
- **Событие `pull_request`, не `pull_request_target`.** PR из форка выполняется с токеном только на чтение и без секретов. `pull_request_target` в репозитории не используется.
- **Данные событий и `needs.*` в `run:` — только через `env:`**, никогда подстановкой `${{ }}` в текст скрипта.
- **Каждой джобе — `runs-on: ubuntu-24.04`** (закреплённая метка, не `ubuntu-latest`) и `timeout-minutes`; `concurrency` отменяет устаревший прогон PR, но не прогоны `main`.
- **Go в CI — `1.26.x`**, а не `go-version-file`; джоба `messenger-vuln` ставит ещё и `check-latest: true`: без него `setup-go` берёт подходящую версию из образа раннера, которая может отставать от последнего патча.
- **Синтаксис и выражения workflow проверяет `actionlint`** (джоба `workflows` и `npm run check:workflows` локально; `run:`-блоки — через `shellcheck`, если он установлен).

## Последствия

- **Плюсы:** правка урока проходит CI без джоб мессенджера, правка мессенджера — со всеми воротами; защита ветки не зависит от имён джоб; сбой фильтра или отмена прогона не превращаются в зелёный PR. Перевешенный тег чужого action не меняет код, который выполнится у нас; при закреплении `trivy-action` по SHA коммита после 2025-04-09 атака марта 2026 нас бы не задела — сам `trivy-action` с тех пор закрепляет `setup-trivy` по SHA. Утечка токена из джобы даёт только чтение публичного кода.
- **Минусы:** закреплённые SHA устаревают — без Dependabot они копят известные уязвимости, а обновления становятся ручной работой; каждое обновление — PR, который надо прочитать. `needs:` у `ci-ok` дополняется руками. Фильтр путей — эвристика: зависимость, которую он не описывает (например, урок, читающий файл вне `course/`, `messenger/` и `labs/`), останется непроверенной на PR и всплывёт только на `main`.
- **Что станет сложнее и когда пересмотреть:**
  - джобы станут медленными (больше ~10 минут на PR) — шардирование тестов матрицей, перенос тяжёлых сценариев на `main` или по расписанию;
  - появятся секреты в CI (публикация — урок 1.19) — они выдаются только джобам релиза через `environment`, а не всему `ci`;
  - lockfile зависимостей workflow выйдет из preview — переходим на него: он закрепляет и транзитивные actions;
  - понадобится запуск на PR из форков с секретами (например, комментарий бота) — отдельный workflow на `workflow_run` без checkout кода PR, а не `pull_request_target`.
