# ADR-0006. Contract-first: OpenAPI как источник правды, генерация и проверка ответов

## Статус

Принято, 2026-10-14.

## Контекст

До урока 1.9 форма HTTP API мессенджера жила в трёх местах: в ручных DTO адаптеров (`chat/adapters/httpapi/dto.go`, `user/adapters/httpapi/dto.go`), в тексте уроков и в головах тех, кто пишет клиентов. Эти три описания ничем не связаны. Переименовали поле в DTO — тесты адаптера поправили вместе с ним, сборка зелёная, а клиенты узнают о переименовании в проде. Описания в уроке и в коде расходятся молча.

Клиентов будет больше: мобильная команда в модуле 3 и API-шлюз в модуле 6 пишут код по описанию API, а не по исходникам сервера. Им нужно описание, которому можно доверять, — и машиночитаемое, чтобы из него генерировать клиентов и проверки.

Силы, которые действуют на решение:

- описание API должно быть одно, и сервер не должен иметь возможности незаметно от него отступить;
- архитектура из ADR-0001 сохраняется: контексты `user` и `chat` не видят типов друг друга, домен не знает о транспорте;
- без веб-фреймворков: маршрутизатор — стандартный `http.ServeMux` (урок 1.8);
- проверки данных — в домене; не хочется заводить второе место, где решается, корректен ли запрос.

## Рассмотренные варианты

1. **Code-first с аннотациями.** Описание OpenAPI генерируется из Go-кода и комментариев-аннотаций (как в swaggo). Плюсы: код пишется как привык, описание «бесплатно». Минусы: источник правды — код, и описание отражает то, что сервер делает, а не то, что обещано клиентам; аннотации — второй язык в комментариях, их никто не проверяет компилятором; согласовать API с клиентами до реализации нельзя.
2. **Контракт + только тест-сверка.** Пишем `api/openapi.yaml` руками, ручные DTO оставляем, а тесты проверяют каждый ответ по контракту. Плюсы: никаких генераторов. Минусы: запросы (имена полей, параметры, набор операций) сверяются только там, где тест их случайно задел; DTO и контракт по-прежнему два описания одного и того же.
3. **Контракт + генерация + тест-сверка.** Контракт — источник правды; из него генерируются Go-типы запросов и ответов и интерфейс сервера, хендлеры его реализуют, а тесты проверяют ответы по контракту. Плюсы: расхождение во входящих данных ломает сборку; расхождение в ответе ломает тест. Минусы: зависимость от генератора, сгенерированный код в репозитории, правила генератора нужно знать.
4. **Контракт как документ.** `openapi.yaml` пишется для клиентов, код от него не зависит и с ним не сверяется. Плюсы: дёшево. Минусы: это то же самое «описание в тексте урока», только в YAML, — расходится с кодом при первом же изменении.

## Решение

Мы выбираем вариант 3.

- `api/openapi.yaml` (OpenAPI 3.0.3) — единственный источник правды о форме API. Меняется API — сначала меняется контракт, потом `go generate ./...`, потом код.
- Генератор — oapi-codegen v2 в режиме `std-http-server`: он генерирует интерфейс `ServerInterface` и обвязку маршрутов поверх стандартного `http.ServeMux`, без фреймворка. Хендлеры пишем мы, сгенерированный код только разбирает параметры пути и строки запроса.
- Генерация — **по пакету на контекст**: `internal/user/adapters/httpapi/gen` (тег `users`) и `internal/chat/adapters/httpapi/gen` (тег `chats`), фильтр `include-tags`. Так граница контекстов из ADR-0001 сохраняется и в сгенерированном коде: адаптер `chat` не видит DTO контекста `user`.
- Генератор подключён директивой `tool` в `go.mod` (Go 1.24+) и вызывается `go tool oapi-codegen` из `//go:generate`: версия зафиксирована вместе с остальными зависимостями.
- Ответы проверяет пакет `platform/openapitest` на kin-openapi: в тестах адаптеров сервер обёрнут валидатором, каждый ответ сверяется с контрактом, недокументированный статус — ошибка (`IncludeResponseStatus`).
- Идентификаторы в телах запросов и ответов генерируются как `string` (`x-go-type: string`): их формат проверяет домен и называет поле в ошибке так, как в контракте. Параметр пути `{id}` — `openapi_types.UUID`, его проверяет сгенерированная обёртка; ошибку разбора адаптер переводит в общий формат с полем `id`.

## Последствия

- **Плюсы:** описание API одно и машиночитаемое, клиенты модулей 3 и 6 генерируют код из него же. Отсутствующий метод хендлера, переименованное поле запроса, сменённый тип параметра — ошибка сборки. Неверная форма ответа или неописанный статус — падение теста адаптера.
- **Зависимость от генерации.** В проекте появляются oapi-codegen (только как инструмент), `github.com/oapi-codegen/runtime` (в рантайме, разбор параметров) и kin-openapi (только в тестах). Обновление генератора может поменять сгенерированный код — это отдельное изменение с отдельной проверкой.
- **Сгенерированный код лежит в репозитории.** Это нужно, чтобы проект собирался без запуска генератора и чтобы изменения API были видны в ревью. Цена — риск устаревания: контракт поправили, `go generate` не запустили. Поэтому проверка мессенджера (`npm run check:messenger`) запускает `go generate ./...` и падает, если он что-то изменил. Файлы `api.gen.go` руками не правят.
- **Ограничения полей в контракте — документация, правила — домен.** `minLength`, `maxLength`, `pattern`, `minimum`/`maximum` в контракте сообщают клиентам те же правила, что проверяет домен; сгенерированный код их не проверяет, и проверять их второй раз в адаптере мы не будем. Это сознательное дублирование знания ради клиентов: при расхождении прав домен, а расхождение — ошибка в документации, которую чинят в контракте.
- **Ответы проверяет только тест.** Компилятор не знает, что мы пишем в тело ответа; гарантия формы ответа ровно такая, каково покрытие тестов адаптеров. В проде валидатор не работает — это стоило бы времени на каждом запросе.
- **Что станет сложнее:** правила генератора (имена `Id`, а не `ID`; указатели для необязательных полей; `x-go-type`) нужно знать. Если `std-http-server` перестанет хватать (например, понадобятся строго типизированные ответы), вернуться к решению и рассмотреть `strict-server`.
