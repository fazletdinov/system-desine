# ADR-0010. Доставка: образ в GHCR с тегами sha/main/semver, мультиархитектура кросс-компиляцией и аттестации GitHub вместо собственной подписи

## Статус

Принято, 2026-10-15.

## Контекст

С урока 1.18 каждое изменение проходит ворота CI (ADR-0009), но результат никуда не уезжает: образ собирается на раннере и исчезает вместе с ним. С урока 1.19 зелёный `main` и каждый тег релиза превращаются в опубликованный образ мессенджера, а сайт курса выкладывается на GitHub Pages.

Репозиторий публичный. Образ должен быть **доступен** (любой может сделать `docker pull` без учётной записи) и **проверяем**: по образу должно быть можно установить, из какого коммита и каким конвейером он собран, и что внутри. Отсюда три вопроса, на которые должен отвечать любой выпущенный образ:

- «какой код сейчас крутится?» — по тегу или digest найти коммит;
- «этот образ собрали мы?» — отличить образ из нашего CI от образа, собранного на чужом ноутбуке и запушенного украденным токеном;
- «где у нас уязвимая библиотека X?» — по списку компонентов, а не перебором образов.

Силы, которые действуют на решение:

- **секреты.** У проекта нет и не должно быть долгоживущих секретов: персональный токен (PAT) в секретах репозитория живёт месяцами и даёт доступ ко всем пакетам владельца. В CI уже есть `GITHUB_TOKEN`, который истекает с джобой;
- **цепочка поставок.** Тег в реестре изменяем, как и тег action (ADR-0009): кто получил право записи, тот переписал `latest`. Нужна подпись, которую нельзя подделать, украв секрет из CI;
- **архитектуры.** Разработчики на Mac с Apple Silicon, ARM-серверы (Graviton, Ampere) в облаках дешевле x86. Образ только под `amd64` на arm64-машине либо не запустится, либо пойдёт через эмуляцию;
- **цена ошибки.** Публикация — единственное место, где у конвейера есть права на запись (`packages: write`, `id-token: write`). Она не должна запускаться на непроверенный код и на код из PR.

## Рассмотренные варианты

**Реестр.**

1. **Docker Hub.** Плюсы: реестр по умолчанию, `docker pull messenger` без префикса. Минусы: нужен отдельный аккаунт и токен в секретах (PAT-подобный, долгоживущий); анонимные загрузки ограничены по частоте; связь образа с репозиторием и аттестациями GitHub — вручную.
2. **GHCR (`ghcr.io`).** Плюсы: публикация тем же `GITHUB_TOKEN` с правом `packages: write`, без секретов; пакет, опубликованный из workflow, автоматически связан с репозиторием; публичные образы скачиваются анонимно; аттестации GitHub кладутся рядом с образом. Минусы: привязка к GitHub; новый пакет по умолчанию приватный — его надо один раз сделать публичным руками.
3. **Собственный реестр** (Harbor, `distribution`). Плюсы: полный контроль, политики хранения. Минусы: сервер, TLS, бэкапы и обновления — эксплуатация, которой у учебного проекта нет. Отвергнут.

**Подпись.**

1. **Без подписи.** Плюсы: ничего не делать. Минусы: на вопрос «этот образ собрали мы?» ответа нет; любой, кто получил право записи в пакет, подменяет образ незаметно. Отвергнут.
2. **cosign с собственным ключом.** Плюсы: независимость от GitHub, проверка `cosign verify --key`. Минусы: приватный ключ надо хранить в секретах CI, ротировать и отзывать; украденный ключ подписывает что угодно, а узнать об этом нельзя. Ровно тот долгоживущий секрет, которого мы избегаем.
3. **Keyless через аттестации GitHub** (`actions/attest-build-provenance`, Sigstore). Workflow получает OIDC-токен GitHub, Fulcio выдаёт по нему сертификат на минуты, в котором записаны репозиторий, workflow и коммит; подпись попадает в публичный журнал прозрачности Rekor. Плюсы: нет ключа, который можно украсть; подпись утверждает не «у кого-то был ключ», а «это собрал такой-то workflow из такого-то коммита»; проверка — `gh attestation verify`. Минусы: доверяем GitHub как издателю OIDC и Sigstore как удостоверяющему центру; проверка требует `gh` (или совместимого инструмента, понимающего бандлы Sigstore).

**Теги.**

1. **Только `latest`.** Плюсы: просто. Минусы: изменяемый тег без истории — нельзя ни откатиться, ни понять, что запущено. Отвергнут.
2. **Только semver на релизе.** Плюсы: понятные версии. Минусы: между релизами `main` не публикуется, проверить свежий `main` в окружении нельзя.
3. **`sha-<7>` на каждую публикацию, `main` — на последний зелёный `main`, на теге `vX.Y.Z` — `X.Y.Z`, `X.Y` и `latest`.** Плюсы: `sha-…` — неизменяемая ссылка на коммит (переписывать её незачем, и её можно защитить правилами пакета); `main` удобен для «последнего проверенного»; semver — для потребителей; `latest` только на релизе, а не на каждом коммите. Минусы: много тегов в пакете, нужна политика очистки старых `sha-…`.

**Мультиархитектура.**

1. **QEMU** (`docker/setup-qemu-action`, вся сборка под arm64 в эмуляции). Плюсы: работает для любого Dockerfile, в том числе с `RUN apt-get install` в финальной стадии. Минусы: эмуляция процессора медленная: на машине автора сборка мессенджера под arm64 через QEMU заняла 2 мин 12 с против 13 с с кросс-компиляцией, а один шаг `go build` — 97,5 с против 5,8 с (урок 1.19).
2. **Кросс-компиляция Go** (`FROM --platform=$BUILDPLATFORM`, `GOOS=$TARGETOS GOARCH=$TARGETARCH`). Плюсы: компилятор работает «родным» на раннере, под целевую платформу собирается только бинарь; в финальной стадии нет `RUN`, поэтому эмулировать нечего. Минусы: работает, пока сборка — чистый Go (`CGO_ENABLED=0`); с cgo понадобится кросс-тулчейн C или QEMU.
3. **Нативные раннеры на каждую архитектуру** (`ubuntu-24.04-arm`) и сборка индекса из двух дайджестов. Плюсы: нативная скорость для любого Dockerfile. Минусы: две джобы и шаг склейки индекса — сложность, которая нужна только при cgo или тяжёлых `RUN`. Отложен.

## Решение

Мы публикуем образ в GHCR workflow `release.yml` с аттестациями GitHub и выкладываем курс workflow `pages.yml`.

- **Когда.** `release.yml` и `pages.yml` запускаются событием `workflow_run` после workflow `ci` и выполняют джобу, только если `ci` завершился `success` и был запущен событием `push` (то есть на `main`, а не на PR). `release.yml` ещё и на `push` тега `v*`. Собирается ровно проверенный коммит — `github.event.workflow_run.head_sha`, а не последний коммит `main` к моменту старта. Публикация идёт, только если `head_sha` совпадает с `github.sha`: OIDC-токен джобы, а значит, сертификат Fulcio и provenance аттестации, несёт `github.sha`, и при расхождении подпись назвала бы не собранный коммит. Устаревший прогон пропускается — новый коммит опубликует его собственный прогон `ci`, и `main` в реестре не откатывается назад.
- **Права.** На уровне workflow `permissions: {}`; джоба `image` получает `contents: read`, `packages: write`, `id-token: write`, `attestations: write`. Вход в GHCR — `GITHUB_TOKEN`, никаких PAT. Джоба Pages разделена на `build` (`contents: read`, `pages: read`) и `deploy` (`pages: write`, `id-token: write`, окружение `github-pages`).
- **Имя и теги.** `ghcr.io/<owner в нижнем регистре>/messenger`. `docker/metadata-action` с `context: git` выдаёт `sha-<7>` всегда, `main` — на `workflow_run`, `X.Y.Z` и `X.Y` — на теге, `latest` — только на теге без пре-релизной части. Версия, зашитая в бинарь (`VERSION`), — первый по приоритету тег: `X.Y.Z` на релизе и `sha-<7>` на `main`.
- **Сборка.** `linux/amd64,linux/arm64` одной джобой, кросс-компиляцией Go без QEMU. BuildKit кладёт в индекс образа SBOM (SPDX, `sbom: true`) и provenance SLSA v1 (`provenance: mode=max`) как аттестации.
- **Подпись.** `actions/attest-build-provenance` создаёт подписанную через Sigstore аттестацию provenance на digest индекса и кладёт её и в API аттестаций GitHub, и в реестр (`push-to-registry: true`). Запись хранения (storage record) отключена: она доступна только репозиториям организаций.
- **Проверка.** Перед использованием образа — `gh attestation verify oci://ghcr.io/<owner>/messenger@sha256:… --owner <owner>`. Это ручная проверка; **политика допуска** (кластер не запускает образ без валидной аттестации из нашего workflow) — модуль 13a.
- **Обновления.** Dependabot еженедельно для `gomod`, `npm`, `github-actions` и `docker` с выдержкой 14 дней (`cooldown`) и группой минорных и патч-обновлений на экосистему; мажорные — отдельными PR.

## Последствия

- **Плюсы:** у проекта нет ни одного долгоживущего секрета публикации; по любому тегу находится коммит (`sha-…`, метка `org.opencontainers.image.revision`); подмену образа выдаёт `gh attestation verify` — подпись привязана к workflow, а не к ключу; SBOM отвечает на «где у нас библиотека X» без разбора образов; arm64-образ стоит секунды, а не минуты; закреплённые SHA и digest не застывают.
- **Минусы:** доверие GitHub и Sigstore как единственной точке проверки; GHCR-пакет надо один раз сделать публичным руками; SBOM и аттестации сами по себе ничего не блокируют — их кто-то должен читать (сканер по SBOM, политика допуска); старые `sha-…` копятся в пакете. Тег `v*` публикуется без нового прогона `ci`: предполагается, что тег ставится на коммит `main`, уже прошедший ворота, — защищать это правилом для тегов (tag ruleset) придётся отдельно. Описание образа в `release.yml` повторяет `LABEL` Dockerfile: иначе `metadata-action` подставляет описание репозитория.
- **Что станет сложнее и когда пересмотреть:**
  - появится cgo или тяжёлые `RUN` в финальной стадии — нативные arm64-раннеры и склейка индекса вместо одной джобы;
  - нужен уровень SLSA Build L3 — сборка в переиспользуемом workflow (reusable workflow), изолированном от вызывающего;
  - образ поедет в Kubernetes (модуль 13a) — политика допуска, проверяющая аттестацию по digest; деплой только по digest, не по тегу;
  - пакет разрастётся — политика хранения: удалять `sha-…` старше N дней, кроме помеченных semver.
