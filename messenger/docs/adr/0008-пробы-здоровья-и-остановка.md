# ADR-0008. Пробы здоровья и остановка: livez без зависимостей, readyz с дренажем, мимо цепочки API

## Статус

Принято, 2026-10-15.

## Контекст

С части 1c мессенджер работает в контейнере, а решения о нём принимает уже не человек, а оркестратор: compose сегодня, Nginx в модуле 2.5, Kubernetes в модуле 13a. Оркестратор задаёт сервису два вопроса и действует по ответам:

- **жив ли процесс?** Если нет — перезапустить контейнер;
- **можно ли слать ему трафик?** Если нет — убрать экземпляр из балансировки, но не трогать.

Отвечает сервис пробами — HTTP-запросами, которые оркестратор шлёт по расписанию. Как сервис на них отвечает, решает, сколько запросов теряется при каждой выкатке и что происходит при сбое зависимости.

Выкатка новой версии — это остановка старых экземпляров. И Docker, и Kubernetes останавливают одинаково: SIGTERM, ожидание, SIGKILL. Kubernetes ждёт `terminationGracePeriodSeconds` (по умолчанию 30 с), Docker — `docker stop -t` или `stop_grace_period` (умолчание демона — 10 с по документации, а у Docker Desktop в его конфиге демона — 3 с, урок 1.17). Если сервис выходит по SIGTERM сразу, обрываются начатые запросы; если перестаёт принимать соединения сразу — отказ получают запросы, которые балансировщик ещё шлёт, потому что о неготовности экземпляра он узнаёт не мгновенно: со следующей пробой, а в Kubernetes — когда изменение Endpoints дойдёт до kube-proxy на каждом узле.

Силы, которые действуют на решение:

- **цена ложного «мёртв».** Перезапуск — дорогая мера: процесс теряет состояние в памяти (у мессенджера сегодня — все данные), а одновременный перезапуск всех экземпляров — отказ сервиса целиком;
- **цена ложного «готов».** Трафик на экземпляр, который не может обслужить запрос, — ошибки у клиентов;
- **распределённость знания.** Экземпляр знает о своей остановке первым, балансировщик — с задержкой; общего «выключателя» нет;
- **шум.** Пробы приходят каждые 1–10 секунд от каждого оркестратора и балансировщика; журнал доступа, аутентификация и таймаут запроса им не нужны;
- **будущие зависимости.** В модуле 2a появится Postgres, потом Redis и Kafka: правило «что проверяет какая проба» должно пережить их появление.

## Рассмотренные варианты

1. **Одна проба `/health`, которая проверяет всё** — процесс, базу, кэш. Плюсы: одна точка, просто объяснить. Минусы: оркестратор использует одну и ту же пробу и для перезапуска, и для трафика. Недоступна база — проба падает на всех экземплярах, и оркестратор перезапускает здоровые процессы, которые перезапуск не починит; Kubernetes прямо предупреждает, что неверная проба живости ведёт к каскадным отказам. Отвергнут.
2. **Liveness = readiness: обе пробы — один обработчик.** Плюсы: формально две пробы. Минусы: та же беда, что у первого варианта, плюс дренаж невозможен: стоит `/readyz` ответить 503 при остановке, как и `/livez` скажет «мёртв», и оркестратор начнёт перезапуск посреди дренажа. Отвергнут.
3. **Liveness без зависимостей, readiness с зависимостями и дренажем.** `/livez` отвечает 200, пока процесс обслуживает HTTP; `/readyz` — 200, если проходят проверки зависимостей (`health.Checker` со сроком 1 с), и 503 с момента SIGTERM. Плюсы: сбой базы выводит экземпляры из трафика, но не перезапускает их; остановка проходит в три шага: `/readyz` → 503, пауза `MESSENGER_DRAIN_DELAY`, пока балансировщик это заметит (новые запросы в это время ещё обслуживаются), затем `http.Server.Shutdown`, который ждёт начатые запросы не дольше `MESSENGER_SHUTDOWN_TIMEOUT`. Минусы: остановка длится на `DRAIN_DELAY` дольше; пара сроков должна укладываться в grace period платформы — это проверяется при старте.
4. **Пробы внутри цепочки middleware и в OpenAPI-контракте.** Плюсы: единообразие — request ID, журнал, формат ошибок, описание в контракте. Минусы: проба проходила бы аутентификацию (нужен токен оркестратору или исключение в `publicRoutes`), таймаут запроса и журнал доступа, где пробы заняли бы бо́льшую часть строк; контракт описывает API для клиентов, а пробы — интерфейс для платформы, и версионируются они по-разному. Отвергнут.
5. **Пробы на отдельном порту.** Плюсы: пробы не видны снаружи вовсе, у служебного порта может быть своя сетевая политика; так часто делают для метрик и pprof. Минусы: второй слушатель со своим жизненным циклом и своей остановкой, второй порт в Dockerfile, compose и манифестах — сегодня ради двух ответов `{"status":"ok"}` без секретов. Отложен до модуля наблюдаемости (12), где появятся метрики и pprof, которым внешний порт действительно противопоказан.

## Решение

Мы принимаем третий вариант и отвечаем на пробы на том же порту, но мимо цепочки API.

- **`/livez`** не проверяет ничего, кроме того, что процесс отвечает по HTTP. **`/readyz`** проверяет зависимости (`health.Check` с именем и `Checker`; сегодня их нет) за общий срок 1 с — столько по умолчанию ждёт ответа Kubernetes (`timeoutSeconds`). Причина отказа — только в журнал, наружу — имя проверки. Оба отвечают только на `GET` и `HEAD` и запрещают кэширование.
- **Остановка** — `httpserver.Run`: по отмене контекста (SIGTERM, SIGINT) — `Drain` (`/readyz` → 503), ожидание `MESSENGER_DRAIN_DELAY` (по умолчанию 5 с), `Shutdown` не дольше `MESSENGER_SHUTDOWN_TIMEOUT` (10 с), при неудаче — `Close`. Сумма двух сроков должна быть меньше 30 с (`terminationGrace`), иначе сервер не стартует; `stop_grace_period` в compose — 30 с, как `terminationGracePeriodSeconds` по умолчанию. *Дополнение (2026-10-19, ADR-0012):* после HTTP останавливаются фоновые компоненты со своим сроком `lifecycle.BackStopTimeout` (2 с), поэтому бюджет — сумма трёх сроков, `DRAIN_DELAY + SHUTDOWN_TIMEOUT + 2 с` < 30 с; второй SIGINT/SIGTERM во время остановки — немедленный выход с кодом 1.
- **Маршрутизация** — в корне композиции развилка по точному пути: `/livez` и `/readyz` идут в отдельный `ServeMux` проб, всё остальное — целиком в цепочку API. Общий `ServeMux` с маршрутом `"/"` не годится: на «нечистый» путь (`/v1//x`) он отвечает голым 307 раньше цепочки — без request ID, журнала и problem+json (тест `TestUncleanPathIsAPIError`).
- **Healthcheck образа** — подкоманда `messenger healthcheck` (в distroless нет `curl`), которая стучится в `/livez` на loopback того же порта; `HEALTHCHECK` в Dockerfile, compose его не переопределяет.
- **Зависимости проб** — контексты (`auth`, `user`, `chat`) не импортируют `platform/health` (правило `depguard`): что считать зависимостью готовности, решает корень композиции.

## Последствия

- **Плюсы:** выкатка без потерянных запросов — экземпляр сначала уходит из ротации, потом дорабатывает начатое и выходит с кодом 0 (замер в уроке 1.17: остановка за 5,2 с — длина дренажа). Сбой зависимости в будущем выведет экземпляры из трафика, но не устроит волну перезапусков. Журнал доступа не засорён пробами. Те же два адреса подойдут compose, Nginx (2.5) и Kubernetes (13a) без изменений.
- **Минусы:** каждая остановка длится не меньше `DRAIN_DELAY`, даже если трафика нет; срок надо согласовывать с платформой (период пробы балансировщика, задержка Endpoints). Пробы доступны на публичном порту — сегодня они не раскрывают ничего, кроме «готов/не готов», и закрыть их снаружи должен шлюз (модуль 6). Пробы не описаны в OpenAPI — их контракт живёт в этом ADR и в `platform/health`.
- **Что станет сложнее и когда пересмотреть:**
  - появятся метрики и pprof (модуль 12) — переносим служебные адреса, вместе с пробами, на отдельный порт;
  - появятся долгоживущие соединения (WebSocket, модуль 3) — `Shutdown` их не ждёт и не закрывает; понадобится свой шаг остановки (`RegisterOnShutdown`, сообщение клиентам о переподключении);
  - зависимость, без которой можно работать частично (кэш), не должна валить `/readyz` — решаем отдельно для каждой, когда она появится;
  - в Kubernetes задержка распространения Endpoints окажется больше 5 с — увеличиваем `MESSENGER_DRAIN_DELAY` или добавляем `preStop` с действием `sleep` и пересматриваем бюджет grace period.
