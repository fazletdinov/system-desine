# ADR-0014. Схема PostgreSQL на контекст в одной базе, межсхемные внешние ключи только к users.users, ограничения как контракт

## Статус

Принято, 2026-10-21. Дополняет ADR-0001 (раскладка кода по контекстам) и ADR-0004 (регистрация через два контекста).

## Контекст

В модуле 2a хранилища мессенджера переезжают из памяти в PostgreSQL. В коде граница между контекстами `user`, `auth` и `chat` проведена каталогами и проверяется `depguard` (ADR-0001): контексты не импортируют друг друга, единственные мосты — `auth/adapters/userbridge` и `chat/adapters/userchecker`. Теперь нужно решить, как эта граница выглядит в базе: где лежат таблицы каждого контекста и какие связи между ними держит сама база.

Силы, которые действуют на решение:

- **распил в модуле 6.** Контексты станут отдельными сервисами со своими базами. Каждая связь между таблицами разных контекстов, которую держит база, — пункт в плане распила;
- **инварианты при любом писателе.** Уникальность имени, «один личный чат на пару», «участник — существующий пользователь» должны держаться при втором экземпляре сервиса, скрипте и ручном SQL, а не только в коде одного процесса (урок 2.4). Часть из них связывает таблицы разных контекстов;
- **одна база дешевле.** Пока контексты живут в одном процессе, одна база PostgreSQL — один пул соединений, одна миграция, одна резервная копия и транзакции поверх нескольких контекстов (регистрация: профиль в `user`, учётные данные в `auth`, ADR-0004);
- **идентичность пользователя — общий язык.** И `auth`, и `chat` говорят о «пользователе с этим id»; в коде этот формат — общее ядро `kernel/ident` (урок 1.13);
- **ошибки ограничений — часть контракта адаптеров.** Postgres-адаптеры переводят нарушения в доменные ошибки (`ErrUsernameTaken`, `ErrDirectChatExists`, `ErrDuplicateMessage`), и им нужно что-то стабильное, по чему узнать, какое правило нарушено.

## Рассмотренные варианты

1. **Все таблицы в схеме `public`.** Плюсы: ничего настраивать не нужно, так начинается большинство проектов. Минусы: граница контекстов в базе не видна — `messages`, `credentials` и `idempotency_keys` лежат рядом, и `JOIN` через границу ничем не отличается от `JOIN` внутри контекста; права нельзя выдать на контекст целиком; при выделении сервиса его таблицы нужно отбирать по списку, и список неизбежно разойдётся с кодом; одинаковые имена (`members` у чатов и, возможно, у будущих каналов) приходится разводить префиксами. Отвергнут.
2. **Схема на контекст в одной базе, межсхемные внешние ключи запрещены.** Плюсы: контексты связаны в базе только соглашением, схему можно вынести в другую базу, ничего не снимая. Минусы: «участник — существующий пользователь» держит только код (`UserChecker` перед `CreateChat`), и между проверкой и вставкой остаётся гонка с удалением пользователя; учётные данные без пользователя станут возможны при записи в обход приложения. Гарантия, которую база даёт почти бесплатно, отдаётся ради распила, до которого четыре модуля.
3. **Схема на контекст в одной базе, межсхемные внешние ключи только к `users.users`.** Плюсы: граница видна (`chat.messages`, `auth.credentials`), права выдаются на схему, выделение контекста начинается с переноса одной схемы; два самых ценных межконтекстных инварианта держит база. Минусы: две связи между схемами в базе — их придётся снять перед распилом; схемы нельзя мигрировать и выносить полностью независимо.
4. **База на контекст.** Плюсы: контексты разделены физически уже сейчас, распил в модуле 6 — смена строки подключения. Минусы: никаких межконтекстных гарантий в базе вовсе, и транзакция регистрации поверх двух баз невозможна — вернулось бы окно неатомарности из ADR-0004, а закрыть его можно только сагой или outbox (модуль 7) уже сейчас; три пула, три миграции и три резервные копии ради одного процесса. Это цена распила, заплаченная за четыре модуля до него. Отвергнут.

## Решение

Мы принимаем вариант 3.

- **Схемы.** `users` (профили), `auth` (учётные данные), `chat` (чаты, участники, сообщения) и `platform` для технических таблиц вне предметной области (ключи идемпотентности). Код контекста ходит только в свою схему. Исключение — `chat/adapters/postgres.UserChecker`: он читает `users.users` за портом `UserChecker`, и это та же цена одной базы, что и внешний ключ ниже (комментарий в `users.go`).
- **Межсхемные внешние ключи — только к `users.users(id)`**, и их ровно два:
  - `auth.credentials.user_id` (`credentials_user_id_fkey`, `ON DELETE CASCADE`): связь 1:1, учётным данным незачем жить без пользователя;
  - `chat.members.user_id` (`members_user_id_fkey`, без `ON DELETE`, то есть `NO ACTION`): участник — существующий пользователь; удаление пользователя — бизнес-решение (личные чаты, сообщения, приватность), которого пока нет, и база запрещает его случайно.
  `chat.messages.author_id` внешнего ключа не имеет: «автор — участник» проверяет агрегат `Chat.Post`, а участник уже ссылается на пользователя; таблица сообщений самая горячая и самая большая (урок 2.1). Новый межсхемный ключ — только через изменение этого ADR.
- **Ограничения как контракт.**
  - Имена всех ограничений заданы в миграции явно (`users_username_key`, `chats_direct_key_key`, `messages_client_id_key`, …). Адаптеры переводят нарушение в доменную ошибку по `pgconn.PgError.Code` **и** `ConstraintName` (`platform/pgerr`), никогда по тексту сообщения. Переименовать ограничение — изменить контракт адаптера.
  - В доменную ошибку переводятся только нарушения, которые бывают при правильной работе (гонка двух правильных запросов): занятое имя, повторные учётные данные, второй личный чат пары, повтор `client_message_id`. Остальные (`23514`, дубль первичного ключа, `23503`) — ошибки сервера с `%w`.
  - Длины и форматы в `CHECK` повторяют константы домена; источник истины — домен. Лимит расширяют сначала в базе, сужают сначала в домене.
  - У каждого внешнего ключа ссылающийся столбец — первый столбец какого-то индекса (`members_user_id_idx` для `chat.members.user_id`, первичные ключи для остальных).
  - `ON DELETE` выбирается для каждого ключа: `CASCADE` — для частей агрегата (`members` и `messages` чата) и 1:1 (`credentials`), `NO ACTION` — где удаление родителя должно быть явным решением.
  - Отложенных (`DEFERRABLE`) ограничений нет: их ошибка приходит на `COMMIT` в `platform/pgtx`, где её не перевести в доменную, и они несовместимы с `ON CONFLICT`. Чат и его участники вставляются одной командой.
- **Транзакции поверх контекстов.** Регистрация пишет `users.users` и `auth.credentials` в одной транзакции (порт `Transactor`); это осознанный компромисс одной базы, закрывающий окно неатомарности ADR-0004. Как устроена граница транзакции — ADR-0015 (урок 2.9).

## Последствия

- **Плюсы:**
  - граница контекстов видна в базе: имя таблицы называет контекст, права можно выдавать на схему, `\dt chat.*` показывает всё, что переедет вместе с контекстом;
  - «участник — существующий пользователь» и «учётные данные — существующего пользователя» держит база при любом писателе; гонка между `UserChecker` и вставкой закрыта внешним ключом (проверка блокирует строку пользователя `FOR KEY SHARE` до конца транзакции);
  - регистрация атомарна без outbox и саг;
  - нарушения ограничений превращаются в доменные ошибки предсказуемо и одинаково во всех адаптерах; `storetest`-батареи проверяют это на настоящем PostgreSQL, включая одновременные записи.
- **Минусы:**
  - **схемы связаны.** Пока существуют два межсхемных ключа, `users` нельзя вынести в другую базу, а миграции `auth` и `chat` зависят от того, что `users.users(id)` существует и остаётся уникальным;
  - **удаление пользователя затрагивает чужие контексты.** `CASCADE` из `auth` удалит учётные данные молча, `NO ACTION` из `chat` запретит удаление участника. Сценарий удаления придётся проектировать сразу для трёх контекстов (урок 2.6);
  - **цена проверки.** Каждая вставка в `chat.members` и `auth.credentials` ищет строку в `users.users` по первичному ключу и блокирует её `FOR KEY SHARE`; для этих таблиц (запись редкая) это приемлемо, для `chat.messages` — нет, поэтому там ключа и нет;
  - **граница держится соглашением.** PostgreSQL выполнит `JOIN` между `chat.messages` и `auth.credentials`, если у роли есть права. Нарушение ловят ревью и тесты адаптеров, а не линтер. Одна роль базы на весь сервис — пока так; роль на контекст с правами только на свою схему — следующий шаг, если границу понадобится проверять механически;
  - **дублирование знания.** Длины в `CHECK` повторяют константы домена, и автоматической проверки их согласованности сейчас нет (тест границы через Postgres-адаптер — упражнение урока 2.4).
- **Что станет сложнее и когда пересмотреть:**
  - **выделение сервиса (модуль 6). Первый шаг** — снять межсхемный внешний ключ выделяемого контекста и заменить его проверкой через порт: для `chat` это `members_user_id_fkey`, а проверку уже делает `UserChecker` в `CreateChat`, который станет клиентом сервиса пользователей. Гонку с удалением пользователя после этого закрывает не база, а событие «пользователь удалён» (модуль 7). Затем — перенос схемы в отдельную базу; код контекста не переписывается, он и так ходил только в свою схему;
  - **регистрация после распила** `auth` и `user` — транзакция невозможна, нужен outbox или сага (модуль 7, ADR-0004);
  - **удаление пользователя** — пересмотреть `ON DELETE` у обоих межсхемных ключей вместе с политикой приватности (урок 2.6);
  - **новый контекст**, которому нужна ссылка на пользователя (устройства, уведомления), — по умолчанию без внешнего ключа, через порт; внешний ключ — только изменением этого ADR с обоснованием, какую гонку он закрывает.
