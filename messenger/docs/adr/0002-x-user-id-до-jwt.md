# ADR-0002. Заголовок X-User-ID вместо аутентификации до JWT

## Статус

Принято, 2026-10-13. Будет заменено ADR о JWT в части 1b.

## Контекст

У трёх сценариев контекста `chat` есть действующее лицо: кто создаёт чат (`CreatorID`), кто отправляет сообщение (`AuthorID`), кто читает историю (`ReaderID`). От него зависят бизнес-правила: писать и читать может только участник чата, группа включает своего создателя.

Аутентификации (проверки, что клиент — тот, кем назвался) в мессенджере пока нет: она — тема части 1b (REST API по-взрослому, JWT). Часть 1a учит архитектуре сервиса, и тащить в неё выпуск и проверку токенов значит смешать две большие темы в одном уроке.

Сервис при этом должен запускаться и проходить сквозной сценарий через `curl` уже в конце 1a.

## Рассмотренные варианты

1. **Без автора.** Use case'ы не знают, кто действует; автора сообщения присылают в теле. Плюсы: ничего не нужно. Минусы: правило «пишет только участник» нечем проверить; поле `author_id` в теле потом придётся убирать из контракта API — ломающее изменение для клиентов.
2. **Заголовок `X-User-ID`.** Клиент присылает свой id в заголовке; HTTP-адаптер разбирает его и передаёт в use case как `CreatorID` / `AuthorID` / `ReaderID`. Плюсы: use case'ы и домен получают действующее лицо уже сейчас и в 1b не меняются; контракт тела запроса окончательный. Минусы: заголовок ничем не защищён — любой клиент может представиться кем угодно.
3. **Сразу JWT.** Плюсы: честная аутентификация с первого дня. Минусы: регистрация с паролем, выпуск и проверка токенов, хранение секрета, middleware — объём отдельной части курса; урок об архитектуре утонул бы в криптографии и протоколах.

## Решение

Мы принимаем заголовок `X-User-ID` (вариант 2) как заглушку до части 1b. Правила:

- Заголовок разбирает обработчик `chat/adapters/httpapi` **до** вызова use case, функцией `domain.ParseUserID`. Нет заголовка или в нём не UUID в нижнем регистре — ответ `401 unauthenticated`. Если отдать сырую строку в use case, ошибка валидации поля `user_id` превратилась бы в `400` — а «не знаю, кто вы» и «вы прислали неверные данные» — разные ответы.
- Заголовок с корректным UUID несуществующего пользователя проверяется так же, как сейчас любой участник: `POST /chats` отвечает `400 invalid_input` с `field: "creator_id"`. Отдельного `401` для «такого пользователя нет» не делаем: настоящая проверка личности появится только с JWT, а до тех пор это просто ошибка во входных данных.
- Отправка и чтение от имени несуществующего пользователя отвечают `403 not_member`: такого пользователя нет ни в одном чате.
- Отсутствующий `Content-Type` `httpjson.Decode` пропускает сознательно (RFC 9110, §8.3 разрешает получателю определить тип самому; строгий декодер всё равно отвергнет не-JSON). Явно чужой тип — `415`. Обратите внимание: `curl -d` без `-H` ставит `application/x-www-form-urlencoded` и получает `415`, поэтому в примерах заголовок указан всегда.

## Последствия

- **Плюсы:** домен и use case'ы уже работают с действующим лицом и в 1b не изменятся; контракт тел запросов окончательный; сквозной сценарий через `curl` доступен в конце 1a.
- **Минусы:** **любой клиент может представиться кем угодно** — прочитать чужую переписку или писать от чужого имени. Поэтому сборку 1a запускают только на локальном стенде; выставлять её в сеть нельзя.
- **Что изменится в 1b:** только `chat/adapters/httpapi/auth.go` (вместо чтения заголовка — id из проверенного токена) и новый middleware аутентификации, который положит id в контекст запроса. Обработчики, use case'ы и домен не меняются. Заголовок `X-User-ID` из API уйдёт; клиенты стенда 1a перейдут на токен.
