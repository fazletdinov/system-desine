# Лабораторная 2a — проектирование базы данных

Уроки части 2a модуля 2 «База данных»: 2.2 (нормализация), 2.3 (ключи и типы), 2.4 (ограничения),
2.6 (JSONB) и 2.7 (антипаттерны). Лаба — одноразовый PostgreSQL 18.6 в Docker, SQL-скрипты с
намеренными ошибками и Go-программа `keys` на `pgx` в общем модуле `labs/`.

```
2a/
├── compose.yaml         # PostgreSQL 18.6 по digest, порт только на 127.0.0.1, данные на tmpfs
├── scenario.sh          # поднимает базу, прогоняет всё и проверяет ключевые строки (его запускает check:labs)
├── anomalies.sql        # урок 2.2: аномалии вставки, обновления и удаления; 3НФ; 3НФ без НФБК
├── keys/                # урок 2.3: bigint identity, UUIDv4 и UUIDv7 — индекс, WAL, время
├── constraints.sql      # урок 2.4: NOT NULL, CHECK, UNIQUE, FK, EXCLUDE, отложенные ограничения — и их SQLSTATE
├── jsonb/
│   ├── settings.sql     # урок 2.6: настройки столбцами и в JSONB, запросы, CHECK для JSONB
│   └── gin.sql          # урок 2.6: размер строки, GIN jsonb_ops и jsonb_path_ops (подробно — в 2b)
├── antipatterns.sql     # урок 2.7: EAV, полиморфная связь, список через запятую, наивное дерево, float для денег
└── results/             # полные выводы, на которые ссылаются уроки (README внутри)
```

Каждый SQL-скрипт создаёт свою схему (`anomalies`, `constraints`, …) и в начале удаляет её, так что его
можно запускать сколько угодно раз. Фрагменты, которые цитируют уроки, отмечены регионами
`-- #region <имя>` / `-- #endregion`.

## Требования

- Docker с Compose; образ `postgres:18.6-trixie` (около 650 МБ на диске) скачивается при первом запуске;
- Go 1.27 (`labs/go.mod`) для `keys`; единственная новая зависимость — `github.com/jackc/pgx/v5` v5.11.0;
- `psql` на машине не нужен: скрипты выполняет `psql` внутри контейнера, каталог `2a/` смонтирован в
  него как `/lab` только для чтения.

## Запуск

Из каталога `labs/`:

```bash
bash 2a/scenario.sh                     # всё с проверками, около 5 с (первый раз — дольше: образ и сборка)

docker compose -f 2a/compose.yaml up -d --wait          # база для ручных опытов на 127.0.0.1:55432
docker compose -f 2a/compose.yaml exec -T db sh -c 'psql -X -f /lab/constraints.sql 2>&1'
docker compose -f 2a/compose.yaml exec db psql           # свой psql в той же базе (пользователь и база — lab)
go run ./2a/keys -n 1000000                              # 5–10 с на i5-12400
docker compose -f 2a/compose.yaml down -v                # данные на tmpfs: после down не остаётся ничего
```

`2>&1` внутри контейнера, а не снаружи: `psql` пишет ошибки в stderr, и по пути через `docker compose
exec` они перемешались бы с выводом запросов. Скрипты не останавливаются на ошибках (`ON_ERROR_STOP` не
задан): ошибки в них намеренные, и после каждой скрипт печатает её код — `SQLSTATE 23505` и т. п.

Порт меняется переменной `LAB2A_PORT` (по умолчанию 55432); `keys` берёт строку подключения из `-dsn` или
`LAB2A_DSN`. `scenario.sh` поднимает свою копию базы (проект `lab2a-scenario`, порт 55433) и убирает её
при выходе, даже если проверка упала, — базу для ручных опытов он не трогает.

## Что показывает каждый скрипт

### anomalies.sql — урок 2.2

Таблица `messages_flat` хранит сообщение вместе с именем автора и названием чата. Три аномалии:

- **вставки** — пользователя без сообщения сохранить негде (`SQLSTATE 23502`: строка — это сообщение, и
  без него её нет);
- **обновления** — переименование, применённое к одному сообщению, оставляет у автора два имени
  (`{alice,alice_w}`); правильное — `UPDATE 3`, по строке на каждое сообщение;
- **удаления** — с единственным сообщением bob пропадает и сам bob (`rows_about_bob = 0`).

Затем те же данные в 3НФ (`users`, `chats`, `messages`): все три правки — одна строка, и «большая
таблица» возвращается запросом с `JOIN`. Последние два шага — таблица дежурных `support_duty`, которая в
3НФ, но не в НФБК (`agent → topic`, а `agent` не ключ), и её разбиение до НФБК с ценой: правило «у
клиента по теме один дежурный» больше не выражается `UNIQUE`.

### keys/ — урок 2.3

Три таблицы отличаются только первичным ключом: `bigint GENERATED ALWAYS AS IDENTITY`,
`uuid DEFAULT gen_random_uuid()` (UUIDv4) и `uuid DEFAULT uuidv7()` (UUIDv7, встроена в PostgreSQL 18).
В каждую загружается `-n` строк (по умолчанию 10⁶) пачками `COPY` по 10 000 строк, каждая пачка — своя
транзакция. Затем — ещё десятая часть строк в уже заполненный индекс после `CHECKPOINT`.

```
загрузка 1000000 строк в пустую таблицу:
    ключ  индекс PK, КиБ  байт индекса на строку  листовых страниц  заполнение листьев, %  таблица, КиБ  WAL, МиБ  время, мс  строк/с
  bigint           21960                    22.5              2733                   90.0         43432      89.8       1012   987842
  uuidv4           38760                    39.7              4820                   71.6         51200     162.3       2472   404384
  uuidv7           30824                    31.6              3832                   90.0         51200     148.6       1492   669834

ещё 100000 строк после CHECKPOINT, индекс уже заполнен:
    ключ  WAL, МиБ  WAL на строку, байт  полных образов страниц  время, мс  строк/с
  bigint       9.0                   94                       7         95  1043198
  uuidv4      43.3                  454                    4847        277   360643
  uuidv7      14.9                  156                       7        148   675024
```

- «индекс PK» — `pg_relation_size` индекса; «листовых страниц» и «заполнение листьев» — `pgstatindex` из
  расширения `pgstattuple` (оно есть в официальном образе). Монотонный ключ (bigint, UUIDv7) всегда
  вставляется в правый лист: B-tree делит его не пополам, а оставляет левую страницу заполненной на 90 %
  (`fillfactor` индекса по умолчанию). Случайный UUIDv4 попадает в случайный лист, листы делятся пополам,
  и в среднем они заполнены примерно на 70 %;
- UUIDv7 больше bigint, потому что ключ вдвое шире: 16 байт против 8 (плюс 8 байт заголовка записи
  индекса и 4 байта указателя на неё в странице);
- «WAL» — `pg_wal_lsn_diff` между `pg_current_wal_lsn()` до и после серии; «полных образов страниц» —
  прирост `wal_fpi` из `pg_stat_wal`. После контрольной точки первое изменение каждой страницы пишет в WAL
  её полный образ (8 КиБ, `full_page_writes = on`). Монотонный ключ меняет несколько правых страниц,
  UUIDv4 — почти все листья индекса, отсюда почти втрое больше WAL на дозагрузке. При загрузке в пустую таблицу
  этого не видно: страницы, созданные после контрольной точки, полных образов не требуют;
- у таблиц выключен autovacuum: его проход посреди замера добавил бы в WAL свои записи.

Полные выводы трёх прогонов и короткого режима — в `results/keys-*.txt`.

### constraints.sql — урок 2.4

Схема `users`/`chats`/`members` с явно названными ограничениями, затем каждое нарушается:
`NOT NULL` — 23502, `CHECK` — 23514, `UNIQUE` — 23505 (с `\set VERBOSITY verbose`: видны `SCHEMA NAME`,
`TABLE NAME`, `CONSTRAINT NAME` — те же поля, что `pgx` кладёт в `pgconn.PgError`), `FOREIGN KEY` с
обеих сторон связи — 23503, `ON DELETE CASCADE`, частичный уникальный индекс по выражению
`lower(address) WHERE deleted_at IS NULL` — 23505, `EXCLUDE USING gist` с `btree_gist` для
непересекающихся периодов — 23P01. Отложенный `FOREIGN KEY` (`DEFERRABLE` + `SET CONSTRAINTS … DEFERRED`)
проверяется в `COMMIT`; отложенный `UNIQUE` разрешает сдвиг позиций одной командой; `CHECK` и `NOT NULL`
отложить нельзя — 0A000.

### jsonb/ — урок 2.6

`settings.sql`: настройки пользователя столбцами (тип и `CHECK` держит база) и в JSONB (`->`, `->>`, `@>`,
`?`, `||`, `jsonb_set`); JSONB без проверок принимает число вместо строки и опечатку в ключе; три `CHECK`
(`jsonb_typeof`, «только известные ключи» через `settings - ARRAY[…] = '{}'`, допустимые значения через
`<@`) ловят оба случая — 23514. `gin.sql`: 100 000 одинаковых настроек столбцами и в JSONB — средняя строка
55 байт против 126 (JSONB хранит имена ключей в каждой строке); `@>` без индекса — `Seq Scan`, с GIN —
`Bitmap Index Scan`; `jsonb_path_ops` меньше `jsonb_ops`; `->> … =` индекс GIN не использует.

### antipatterns.sql — урок 2.7

Для каждого антипаттерна — запрос, который ломается, и исправление:

| Антипаттерн | Что ломается | Исправление |
|---|---|---|
| EAV | `'10' < '9'` при сортировке, `'вчера'` принят как дата и роняет приведение (22007) | столбцы с типами и `CHECK` |
| Полиморфная связь | жалоба на несуществующее сообщение принята — `FOREIGN KEY` не объявить | столбец-ссылка на каждый тип цели + `CHECK (num_nonnulls(…) = 1)` (23503, 23514) |
| Список через запятую | `LIKE '%2%'` находит чат пользователя 12; несуществующий 404 принят | таблица-связка с `FOREIGN KEY` (23503) |
| Наивное дерево | два самосоединения теряют третий уровень ответов | `WITH RECURSIVE` по той же таблице «родитель — потомок» |
| Деньги во float | `0.1 + 0.2 <> 0.3`, сумма десяти `0.1` — `0.9999999999999999` | `numeric` |

## Проверки scenario.sh

Для SQL-скриптов — число ошибок и строк `SQLSTATE` совпадает с задуманным (лишняя ошибка или
`SQLSTATE 00000` — провал), плюс ключевые строки: коды, имена ограничений, результаты запросов. Для `keys`
на 10⁵ строк — только относительные проверки: индекс UUIDv4 больше индекса UUIDv7 больше чем в 1,1 раза,
WAL дозагрузки UUIDv4 больше UUIDv7 больше чем в 1,5 раза, индекс UUIDv7 больше индекса bigint.
