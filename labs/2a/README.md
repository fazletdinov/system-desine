# Лабораторная 2a — проектирование базы данных

Уроки части 2a модуля 2 «База данных»: 2.2 (нормализация), 2.3 (ключи и типы), 2.4 (ограничения),
2.5 (паттерны доступа), 2.6 (JSONB, мягкое удаление и история) и 2.7 (антипаттерны). Лаба — одноразовый PostgreSQL 18.6 в Docker, SQL-скрипты с
намеренными ошибками и Go-программа `keys` на `pgx` в общем модуле `labs/`.

```
2a/
├── compose.yaml         # PostgreSQL 18.6 по digest, порт только на 127.0.0.1, данные на tmpfs
├── scenario.sh          # поднимает базу, прогоняет всё и проверяет ключевые строки (его запускает check:labs)
├── anomalies.sql        # урок 2.2: аномалии вставки, обновления и удаления; 3НФ; 3НФ без НФБК
├── keys/                # урок 2.3: bigint identity, UUIDv4 и UUIDv7 — индекс, WAL, время
├── types.sql            # урок 2.3: timestamp/timestamptz, varchar/text + CHECK, enum, время в UUIDv7, citext, ICU-коллация, casefold
├── constraints.sql      # урок 2.4: NOT NULL, CHECK, UNIQUE, FK, EXCLUDE, отложенные ограничения — и их SQLSTATE
├── jsonb/
│   ├── settings.sql     # урок 2.6: настройки столбцами и в JSONB, запросы, CHECK для JSONB
│   └── gin.sql          # урок 2.6: размер строки, GIN jsonb_ops и jsonb_path_ops (подробно — в 2b)
├── history.sql          # урок 2.6: мягкое удаление и UNIQUE/FK, архив, обезличивание, аудит триггером и его цена
├── antipatterns.sql     # урок 2.7: восемь антипаттернов Карвина с исправлениями; имена ограничений по умолчанию
├── tenancy.sql          # урок 2.7: общая схема с tenant_id, RLS, set_config(…, true) против SET, FORCE
├── messenger-explain.sql  # урок 2.5: планы запросов мессенджера на схеме из его миграции (10⁶ чатов)
└── results/             # полные выводы, на которые ссылаются уроки (README внутри)
```

Каждый SQL-скрипт создаёт свою схему (`anomalies`, `constraints`, …) и в начале удаляет её, так что его
можно запускать сколько угодно раз. Фрагменты, которые цитируют уроки, отмечены регионами
`-- #region <имя>` / `-- #endregion`.

## Требования

- Docker с Compose; образ `postgres:18.6-trixie` (около 650 МБ на диске) скачивается при первом запуске;
- Go 1.27 (`labs/go.mod`) для `keys`; единственная новая зависимость — `github.com/jackc/pgx/v5` v5.11.0;
- `psql` на машине не нужен: скрипты выполняет `psql` внутри контейнера, каталог `2a/` смонтирован в
  него как `/lab` только для чтения.

## Запуск

Из каталога `labs/`:

```bash
bash 2a/scenario.sh                     # всё с проверками, около 15 с (первый раз — дольше: образ и сборка)

docker compose -f 2a/compose.yaml up -d --wait          # база для ручных опытов на 127.0.0.1:55432
docker compose -f 2a/compose.yaml exec -T db sh -c 'psql -X -f /lab/constraints.sql 2>&1'
docker compose -f 2a/compose.yaml exec db psql           # свой psql в той же базе (пользователь и база — lab)
go run ./2a/keys -n 1000000                              # 5–10 с на i5-12400
docker compose -f 2a/compose.yaml down -v                # данные на tmpfs: после down не остаётся ничего
```

`2>&1` внутри контейнера, а не снаружи: `psql` пишет ошибки в stderr, и по пути через `docker compose
exec` они перемешались бы с выводом запросов. Скрипты не останавливаются на ошибках (`ON_ERROR_STOP` не
задан): ошибки в них намеренные, и после каждой скрипт печатает её код — `SQLSTATE 23505` и т. п.

Порт меняется переменной `LAB2A_PORT` (по умолчанию 55432); `keys` берёт строку подключения из `-dsn` или
`LAB2A_DSN`. Бюджет `scenario.sh` в CI — 2 минуты на двух ядрах без учёта скачивания образа (около 650 МБ
на диске). Замер на машине автора (Intel Core i5-12400, 12 потоков, Linux, образ уже скачан): с прогретым
кешем Go — 13,9 с, с пустым (`GOCACHE` в новом каталоге) — 18,9 с. На двух ядрах раннера холодная сборка
дольше — по оценке около 35 с, это не замер. `scenario.sh` поднимает свою копию базы (проект
`lab2a-scenario`, порт 55433) и убирает её при выходе, даже если проверка упала, — базу для ручных опытов
он не трогает.

## Что показывает каждый скрипт

### anomalies.sql — урок 2.2

Таблица `messages_flat` хранит сообщение вместе с именем автора и названием чата. Три аномалии:

- **вставки** — пользователя без сообщения сохранить негде (`SQLSTATE 23502`: строка — это сообщение, и
  без него её нет);
- **обновления** — переименование, применённое к одному сообщению, оставляет у автора два имени
  (`{alice,alice_w}`); правильное — `UPDATE 3`, по строке на каждое сообщение;
- **удаления** — с единственным сообщением bob пропадает и сам bob (`rows_about_bob = 0`).

Затем те же данные в 3НФ (`users`, `chats`, `messages`): все три правки — одна строка, и «большая
таблица» возвращается запросом с `JOIN`. Последние два шага — таблица дежурных `support_duty`, которая в
3НФ, но не в НФБК (`agent → topic`, а `agent` не ключ), и её разбиение до НФБК с ценой: правило «у
клиента по теме один дежурный» больше не выражается `UNIQUE`.

### keys/ — урок 2.3

Три таблицы отличаются только первичным ключом: `bigint GENERATED ALWAYS AS IDENTITY`,
`uuid DEFAULT gen_random_uuid()` (UUIDv4) и `uuid DEFAULT uuidv7()` (UUIDv7, встроена в PostgreSQL 18).
В каждую загружается `-n` строк (по умолчанию 10⁶) пачками `COPY` по 10 000 строк, каждая пачка — своя
транзакция. Затем — ещё десятая часть строк в уже заполненный индекс после `CHECKPOINT`.

```
загрузка 1000000 строк в пустую таблицу:
    ключ  индекс PK, КиБ  байт индекса на строку  листовых страниц  заполнение листьев, %  таблица, КиБ  WAL, МиБ  время, мс  строк/с
  bigint           21960                    22.5              2733                   90.0         43432      89.8        932  1072593
  uuidv4           38384                    39.3              4773                   72.3         51200     162.2       2423   412592
  uuidv7           30824                    31.6              3832                   90.0         51200     148.6       1469   680658

ещё 100000 строк после CHECKPOINT, индекс уже заполнен:
    ключ  WAL, МиБ  WAL на строку, байт  полных образов страниц  время, мс  строк/с
  bigint       9.0                   94                       7         90  1110110
  uuidv4      43.3                  454                    4800        273   366207
  uuidv7      14.9                  156                       7        143   695838
```

- «индекс PK» — `pg_relation_size` индекса; «листовых страниц» и «заполнение листьев» — `pgstatindex` из
  расширения `pgstattuple` (оно есть в официальном образе). Монотонный ключ (bigint, UUIDv7) всегда
  вставляется в правый лист: B-tree делит его не пополам, а оставляет левую страницу заполненной на 90 %
  (`fillfactor` индекса по умолчанию). Случайный UUIDv4 попадает в случайный лист, листы делятся пополам,
  и в среднем они заполнены примерно на 70 %;
- UUIDv7 больше bigint, потому что ключ вдвое шире: 16 байт против 8 (плюс 8 байт заголовка записи
  индекса и 4 байта указателя на неё в странице);
- «WAL» — `pg_wal_lsn_diff` между `pg_current_wal_lsn()` до и после серии; «полных образов страниц» —
  прирост `wal_fpi` из `pg_stat_wal`. Оба счётчика — на весь кластер, не на таблицу; это допустимо, потому
  что в одноразовую базу во время замера пишет только `keys` (повторные прогоны совпадают в пределах 1–2 %). После контрольной точки первое изменение каждой страницы пишет в WAL
  её полный образ (8 КиБ, `full_page_writes = on`). Монотонный ключ меняет несколько правых страниц,
  UUIDv4 — почти все листья индекса, отсюда почти втрое больше WAL на дозагрузке. При загрузке в пустую таблицу
  этого не видно: страницы, созданные после контрольной точки, полных образов не требуют;
- у таблиц выключен autovacuum: его проход посреди замера добавил бы в WAL свои записи.

Полные выводы трёх прогонов и короткого режима — в `results/keys-*.txt`.

### types.sql — урок 2.3

Типы, которые выбирают «по привычке». `timestamp` и `timestamptz` получают одну вставку `12:00+00` из
сессии в Москве: `timestamp` молча отбрасывает зону и хранит `12:00`, и тот же ряд — тот же момент для
сессии в UTC и другой для сессии в Москве (`t` и `f`). `varchar(5)` отвергает длинную строку ошибкой
типа 22001 без имени ограничения, `text` с `CHECK` — 23514 с именем; `enum` — 22P02 без имени, `text` +
`CHECK (kind IN …)` — 23514 с именем. `uuid_extract_timestamp` читает время создания из UUIDv7 (из
UUIDv4 — `NULL`), `uuid` — 16 байт против 40 у того же id текстом. Имя без учёта регистра: `citext` и
недетерминированная ICU-коллация `und-u-ks-level2` обе ловят `Alice`/`alice` (23505); с коллацией
работают `=` и `LIKE` (с PostgreSQL 18), но регулярные выражения и `ILIKE` — 0A000 (регулярка в
`CHECK` создаётся без ошибок и роняет каждую вставку), а внешний ключ на
столбец с другой коллацией — 42P21. `casefold` (PostgreSQL 18) со встроенной коллацией `pg_unicode_fast`
приводит `Straße` к `strasse`, а `lower` — нет; уникальный индекс по `casefold` ловит `Straße`/`STRASSE`
(23505).

### constraints.sql — урок 2.4

Схема `users`/`chats`/`members` с явно названными ограничениями, затем каждое нарушается:
`NOT NULL` — 23502, `CHECK` — 23514, `UNIQUE` — 23505 (с `\set VERBOSITY verbose`: видны `SCHEMA NAME`,
`TABLE NAME`, `CONSTRAINT NAME` — те же поля, что `pgx` кладёт в `pgconn.PgError`), `FOREIGN KEY` с
обеих сторон связи — 23503, `ON DELETE CASCADE`, частичный уникальный индекс по выражению
`lower(address) WHERE deleted_at IS NULL` — 23505, `EXCLUDE USING gist` с `btree_gist` для
непересекающихся периодов — 23P01. Отложенный `FOREIGN KEY` (`DEFERRABLE` + `SET CONSTRAINTS … DEFERRED`)
проверяется в `COMMIT`; отложенный `UNIQUE` разрешает сдвиг позиций одной командой; `CHECK` и `NOT NULL`
отложить нельзя — 0A000. Ошибка ограничения обрывает транзакцию: следующий `SELECT` в ней — 25P02, после
`ROLLBACK` — обычный ответ. Внешний ключ без индекса на ссылающемся столбце: 10⁶ сообщений, удаление
чата без сообщений, `EXPLAIN (ANALYZE)` до и после `CREATE INDEX` — строка `Trigger for constraint`
показывает цену поиска детей (`scenario.sh` проверяет только соотношение: без индекса дольше в 10 раз и
больше). Отложенное ограничение в арбитрах `ON CONFLICT` — 55000; `UNIQUE … WITHOUT OVERLAPS` (PostgreSQL 18)
ловит пересечение периодов тем же 23P01.

### jsonb/ — урок 2.6

`settings.sql`: настройки пользователя столбцами и в JSONB (`->`, `->>`, `@>`, `?`, `||`, `jsonb_set`).
У столбцов строку `'often'` отвергает сам тип `boolean` (22P02), а число 42 в столбце `text` тип не
остановит — оно станет строкой `'42'`, и отвергает его `CHECK` со списком значений (23514). JSONB без
проверок принимает и число вместо строки, и опечатку в ключе; три `CHECK` (корень — объект, «только
известные ключи» через `settings - ARRAY[…] = '{}'`, `theme` — строка из списка: `jsonb_typeof(…) =
'string'` и `->> … IN (…)`) ловят число, опечатку и массив `["dark", "light"]` — 23514. Проверка типа
нужна: одно `<@ '["light", "dark", "system"]'` массив пропустило бы. `gin.sql`: 100 000 одинаковых настроек столбцами и в JSONB — средняя строка
55 байт против 126 (JSONB хранит имена ключей в каждой строке); `@>` без индекса — `Seq Scan`, с GIN —
`Bitmap Index Scan`; `jsonb_path_ops` меньше `jsonb_ops`; `->> … =` индекс GIN не использует.

### history.sql — урок 2.6

Пользователи с `deleted_at`, их сессии (`ON DELETE CASCADE`), сообщения (`NO ACTION`) и журнал аудита
`users_audit`: триггер `AFTER … FOR EACH ROW` пишет `to_jsonb(OLD)`/`to_jsonb(NEW)` и автора из `SET LOCAL
app.actor` с самой первой вставки. Мягкое удаление alice — это `UPDATE`, поэтому каскад не срабатывает и
сессия жива; при обычном `UNIQUE (username)` имя удалённой alice занять нельзя (23505). Частичный
уникальный индекс `WHERE deleted_at IS NULL` пускает новую alice, но не вторую живую (23505 с именем
индекса). Запрос без `deleted_at IS NULL` находит обеих, а внешний ключ принимает сообщение от удалённой:
он проверяет, что строка есть, а не что она жива. Представление `active_users` записывает «живой» в одном
месте. На 10⁵ пользователях (каждый десятый удалён) запрос без условия частичного индекса — `Seq Scan`, с
условием и через представление — `Index Scan using users_username_active_key`. Перенос в архив (`WITH …
DELETE … RETURNING … INSERT`) упирается во внешний ключ сообщений (23503), без детей — проходит. В журнале
правка из приложения записана с автором, ручная из `psql` — без него. Право на удаление: мягко удалённая
alice по-прежнему хранит имя, `DELETE` упирается в её сообщения (23503); обезличивание оставляет строку
ради ссылок и удаляет сессии явно, но журнал хранит имя alice во всех трёх строках её истории, пока их не
почистит `old_row - ARRAY[…]`. Цена триггера: 10⁵ `UPDATE` одной командой с журналом и без — время и WAL
(между отметками `pg_current_wal_lsn()`, после `CHECKPOINT` перед каждым опытом) и прирост журнала;
`scenario.sh` проверяет только соотношение: с триггером дольше хотя бы в 1,2 раза и WAL больше хотя бы в
1,3 раза.

### antipatterns.sql — урок 2.7

Для каждого антипаттерна — запрос, который ломается, и исправление:

| Антипаттерн | Что ломается | Исправление |
|---|---|---|
| EAV | `'10' < '9'` при сортировке, `'вчера'` принят как дата и роняет приведение (22007) | столбцы с типами и `CHECK` |
| Полиморфная связь | жалоба на несуществующее сообщение принята — `FOREIGN KEY` не объявить | столбец-ссылка на каждый тип цели + `CHECK (num_nonnulls(…) = 1)` (23503, 23514) |
| Список через запятую | `LIKE '%2%'` находит чат пользователя 12; несуществующий 404 принят | таблица-связка с `FOREIGN KEY` (23503) |
| Наивное дерево | два самосоединения теряют третий уровень ответов | `WITH RECURSIVE` по той же таблице «родитель — потомок» |
| Деньги во float | `0.1 + 0.2 <> 0.3`, сумма десяти `0.1` — `0.9999999999999999` | `numeric` |
| `SELECT *` | после `ADD COLUMN` архивация `INSERT … SELECT *` падает (42601), а представление с `*` нового столбца не видит | явные списки столбцов |
| «ID для всего» | суррогатный `id` у строки участия — и alice в чате дважды | ключ из того, что уникально: `PRIMARY KEY (chat_id, user_id)` (23505) |
| Ключ без ограничения | сообщения удалённого и несуществующего чата остаются сиротами | `FOREIGN KEY`; на грязные данные он не встаёт (23503) — `NOT VALID`, чистка, `VALIDATE CONSTRAINT` |

Последний шаг — имена, которые PostgreSQL выбирает сам, если их не задать: `<таблица>_<столбцы>_<суффикс>`
(`pkey`, `key`, `fkey`, `check`, `idx`, в PostgreSQL 18 и `not_null`), `CHECK` по нескольким столбцам —
`<таблица>_check`, повтор — с суффиксом `1`, длиннее 63 байт — молча обрезается.

### tenancy.sql — урок 2.7

Два арендатора (`acme`, `globex`) в общих таблицах `chats` и `messages`: `tenant_id` — первый столбец
первичного ключа, внешний ключ сообщений — составной `(tenant_id, chat_id)`. RLS включена, политика
`USING (tenant_id = current_setting('app.tenant_id')::bigint)`, приложение работает ролью `tenancy_app` (не
владелец и не суперпользователь). Суперпользователь `lab` видит все строки; роль приложения без
арендатора — 42704; с `set_config('app.tenant_id', '1', true)` в транзакции — только чаты acme, чужой чат по
`id` не найти и не изменить (`UPDATE 0`), политика видна в `Index Cond` плана; вставка строки globex —
42501, сообщение в чат globex — 23503 по составному ключу. После `COMMIT` настройка пуста (`''`) и запрос
падает с 22P02; `SET` без `LOCAL` переживает «запрос» и показывает следующему чаты globex. `SET LOCAL … = $1`
через `\bind` (расширенный протокол, как у `pgx`) — 42601, `set_config(…, $1, true)` — работает. Владелец
таблицы обходит политику, пока не `FORCE ROW LEVEL SECURITY`; суперпользователь — и с `FORCE`. Роли
`tenancy_app` и `tenancy_owner` — общие на кластер; скрипт удаляет их в начале вместе со своей схемой.

### messenger-explain.sql — урок 2.5

Схема — сама миграция `messenger/migrations/00001_init.sql` (compose монтирует её каталог в контейнер
как `/messenger-migrations`, скрипт берёт из файла часть Up), запросы — те же, что в
`chat/adapters/postgres/store.go`. Данные: 10⁵ пользователей, 10⁶ чатов по два участника, «тяжёлый»
пользователь в 1 000 чатах и «лёгкий» в 20, история одного чата в 10 000 сообщений; около 40 с на
tmpfs. Параллельные планы выключены (`max_parallel_workers_per_gather = 0`): иначе от случайной выборки
`ANALYZE` план то зовёт параллельного исполнителя, то нет, и цитаты урока не воспроизводились бы. Планы
`EXPLAIN (ANALYZE, BUFFERS)`: список чатов (первая страница и страница после курсора); индекс
`chat.chats (last_activity_at DESC, id DESC)`, которого в схеме нет, — создаётся на время опыта: план его
не берёт, а доля HOT-обновлений строки чата на 200 сообщениях падает с 200 до 0; индекс
`chat.members (user_id, chat_id)` вместо `(user_id)` (в транзакции с откатом); страница истории чата;
та же страница истории и списка чатов через `OFFSET` вместо курсора; размеры таблицы `chat.messages` и
трёх её индексов. В `scenario.sh` скрипт не входит: он идёт около 40 с, а его числа — для урока, а не для
проверки.

## Проверки scenario.sh

Для SQL-скриптов — число ошибок и строк `SQLSTATE` совпадает с задуманным (лишняя ошибка или
`SQLSTATE 00000` — провал), плюс ключевые строки: коды, имена ограничений, результаты запросов. Для `keys`
на 10⁵ строк — только относительные проверки: индекс UUIDv4 больше индекса UUIDv7 больше чем в 1,1 раза,
WAL дозагрузки UUIDv4 больше UUIDv7 больше чем в 1,5 раза, индекс UUIDv7 больше индекса bigint.
