# Лабораторная 0.4 — задержки на машине автора

Урок 0.4 «Числа задержек» строит шкалу по таблице Colin Scott («Latency Numbers Every Programmer
Should Know», оценки на 2020 г.). Почти все её числа — не замеры, а экстраполяция трендов: в исходнике
модели (`interactive_latency.html`) задержка SSD после 2014 г. — константа 16 мкс, полоса шины удваивается
каждые ~3 года от 4 ГБ/с в 2001-м, RTT в ЦОД — константа 0,5 мс из таблицы Дина 2009 года. Эта лаба
меряет те же строки на одной настоящей машине: память — Go-программой, SSD — `fio`, `fsync` —
`pg_test_fsync`, сеть — `ping` между контейнерами. Числа нужны шкале урока как «реально на машине
автора» рядом с «по модели Scott».

```
0-4/
├── scenario.sh       # запускает всё, пишет results/; с --check — короткий прогон для check:labs
├── compose.yaml      # контейнеры fio, pg_test_fsync (postgres:18.6) и два busybox для ping
├── fio/              # образ с fio 3.39 на alpine 3.22 и скрипт одного замера (run.sh)
├── mem/              # Go: обход цепочки указателей (L1, L2, RAM) и чтение 1 МБ подряд
├── data/             # тестовые файлы диска во время прогона (в .gitignore, после прогона пуст)
└── results/          # выводы полного прогона: шапка машины, вывод замера, строки RESULT
```

## Запуск

Нужны Go 1.27 (`labs/go.mod`), Docker и около 4,5 ГБ свободного места на диске. Из каталога `labs/`:

```bash
bash 0-4/scenario.sh            # полный прогон, около 3 минут; перезаписывает 0-4/results/
bash 0-4/scenario.sh --check    # короткий, около минуты; только порядок величины, results/ не трогает
go run ./0-4/mem -mode latency  # одна память, без Docker
go run ./0-4/mem -mode seq
```

Тестовые файлы `fio` (4 ГБ) и `pg_test_fsync` пишутся в `0-4/data/` и удаляются в конце прогона, в том
числе при ошибке. Каталог должен лежать на настоящем диске: в tmpfs или в слое контейнера (overlay) `fio`
измерил бы память. Другой каталог — через `LAB04_DATA=/путь/на/диске bash 0-4/scenario.sh`. Сценарий
проверяет тип ФС на хосте (`df --output=fstype`), а `fio/run.sh` — ещё раз внутри контейнера и пробой
`O_DIRECT`; при tmpfs, overlay, ФС без `O_DIRECT` или без Docker он останавливается с объяснением.
Проверка одного типа ФС нужна потому, что tmpfs с Linux 6.6 принимает `O_DIRECT` и проба его не ловит.

Каждый файл `results/*.txt` начинается шапкой — CPU, ОЗУ, ОС, ядро, версии Go и Docker, ФС и модель
диска (`lsblk -d -o NAME,MODEL,ROTA,TRAN`), дата — и кончается строками
`RESULT <ключ> <значение> <единица>`: их читают `scenario.sh` и тесты курса. Ключи:

| файл | ключи |
| --- | --- |
| `mem-latency.txt` | `l1_random_ns`, `l2_random_ns`, `ram_random_ns` |
| `mem-seq-1mb.txt` | `ram_seq_1mb_us` |
| `ssd-randread-4k.txt` | `ssd_rand4k_p50_us`, `ssd_rand4k_p99_us`, `ssd_rand4k_mean_us`, `ssd_rand4k_lat_mean_us` |
| `ssd-seqread-1m.txt` | `ssd_seq1m_p50_us`, `ssd_seq1m_p99_us`, `ssd_seq1m_mean_us`, `ssd_seq1m_lat_mean_us` |
| `fsync.txt` | `fsync_ms` |
| `net-rtt.txt` | `rtt_container_us`, `rtt_localhost_us` |

Рядом с выводами `fio` лежит его полный JSON (`*.fio.json`): все перцентили, а не только p50 и p99.

закоммичен один прогон целиком, а не «лучшие» числа из разных.

## Как читать числа

### mem — урок 0.4, строки «L1», «L2», «RAM»

Массив узлов по 64 байта (одна строка кэша), связанных в один случайный цикл (алгоритм Саттоло:
обычное перемешивание дало бы несколько циклов, и обход мог бы застрять в маленьком, уместившемся в
кэш). Следующий адрес известен только после загрузки текущего узла, поэтому обращения не перекрываются,
а аппаратный prefetcher не угадывает адрес: время шага — задержка одного обращения. Один и тот же обход
по 16 КиБ (целиком в L1), 1 МиБ (в L2, но не в L1) и 256 МиБ (в 14 раз больше L3). Печатается медиана
7 замеров.

```
случайное обращение, L1 (16 КиБ)        1.53 нс (медиана 7 замеров по 200000000 переходов)
случайное обращение, L2 (1 МиБ)         6.89 нс (медиана 7 замеров по 200000000 переходов)
случайное обращение, RAM (256 МиБ)    100.85 нс (медиана 7 замеров по 20000000 переходов)
```

- L1 — несколько тактов процессора: это задержка «загрузка → использование», и она почти не менялась
  десятилетиями.
- L2 почти вдвое дольше модели: у Alder Lake L2 большой (1,25 МиБ), а большой кэш — медленнее.
- RAM ≈ 100 нс совпадает с моделью. В число входит и промах TLB: 256 МиБ на страницах по 4 КиБ —
  65 536 страниц, а TLB помнит пару тысяч, так что почти каждое обращение ещё и ищет страницу в таблице
  страниц. Так и выглядит случайный доступ к большим данным в обычной программе.

`-mode seq` читает подряд по мегабайту из буфера 256 МиБ, каждый раз следующий мегабайт по кругу:
к повторному чтению того же мегабайта прочитано ещё 255 МиБ, и он давно вытеснен из L3. Сумма идёт в
четыре аккумулятора, чтобы замер упёрся в память, а не в цепочку сложений.

```
последовательное чтение 1 МБ из буфера 256 МиБ: 57.7 мкс (18.2 ГБ/с; медиана 7 замеров по 4096 МБ)
```

58 мкс — это 18 ГБ/с из одного ядра. Модель Scott даёт 3 мкс, то есть ≈330 ГБ/с: так не умеет ни одна
настольная машина, это экстраполяция роста полосы шины. У Дина в 2009-м было 250 мкс. Вывод урока не
меняется: 1 МБ подряд (58 мкс) против 1 МБ вразнобой — 16 384 строк по 101 нс ≈ 1,7 мс, в 28 раз дольше.

### ssd-randread-4k, ssd-seqread-1m — урок 0.4, строки «SSD»

`fio` в контейнере по файлу 4 ГБ на диске хоста: `--direct=1` (O_DIRECT, мимо page cache — иначе
повторное чтение шло бы из RAM), `--ioengine=libaio --iodepth=1` (ровно один запрос в полёте — задержка
одного чтения, а не пропускная способность очереди NVMe), `--runtime=20 --time_based`.

```
--rw=randread --bs=4k:  IOPS 19286; slat 3.7 мкс, lat (slat + clat) 50.9 мкс
                        clat: среднее 47.2, p50 41.728, p90 58.624, p99 68.096, p99.9 136.192 мкс
--rw=read --bs=1M:      полоса 3374 МБ/с; slat 128.4 мкс, lat (slat + clat) 309.9 мкс
                        clat: среднее 181.5, p50 177.152, p90 211.968, p99 254.976 мкс
```

- `clat` — от передачи запроса устройству до завершения, `slat` — время самой отправки (`io_submit`).
  Ключи `*_p50_us`, `*_p99_us`, `*_mean_us` — по `clat`, как печатает `fio`; `*_lat_mean_us` — полное
  время, которое видит программа.
- 4 КБ вразнобой: 42–58 мкс на p50 в разных прогонах, в 3 раза дольше 16 мкс модели. Это NAND TLC:
  чтение страницы флеш-памяти само по себе — десятки микросекунд. 10–20 мкс дают только Optane и
  SLC-накопители.
- 1 МБ подряд: 310 мкс, в 6 раз дольше 49 мкс модели. Здесь `slat` большой: ядро режет 1 МБ на куски по
  `max_sectors_kb` (у этого диска 128 КБ), и `io_submit` занимает время, поэтому строка шкалы — это
  `lat`, а не `clat`. 3,4 ГБ/с при одном запросе в полёте; паспортные 7 450 МБ/с 990 PRO достигаются
  только с глубокой очередью.
- Вывод урока «подряд дешевле, чем вразнобой» верен и здесь: 1 МБ подряд — 310 мкс, 256 случайных
  чтений по 4 КБ — 256 × 51 мкс ≈ 13 мс, в 40 раз дольше.

### fsync — урок 0.3, «fsync ≈ 2 мс»

`pg_test_fsync` из образа PostgreSQL 18.6 на том же каталоге, 5 с на каждый метод. Ключ `fsync_ms` —
строка `fdatasync` раздела «Compare file sync methods using one 8kB write»: `fdatasync` — значение
`wal_sync_method` по умолчанию на Linux, а одна запись 8 КБ с синхронизацией — то, что делает COMMIT с
одной страницей WAL. Время считается из `ops/sec` (в `usecs/op` утилита округляет до целых микросекунд).

```
Compare file sync methods using one 8kB write:
        open_datasync                       263.059 ops/sec    3801 usecs/op
        fdatasync                           745.381 ops/sec    1342 usecs/op
```

1,3 мс (1,3–1,9 в разных прогонах) — порядок «≈2 мс» урока подтверждается. Это потребительский NVMe без
защиты от потери питания: на каждую синхронизацию он сбрасывает свой кэш записи во флеш. Серверные
диски с конденсаторами (PLP) отвечают на `fsync` за десятки микросекунд — кэш у них считается надёжным.

### net-rtt — урок 0.4, строка «RTT внутри ЦОД»

`ping -c 50 -i 0.2` из контейнера `pinger` в контейнер `peer` одной bridge-сети Docker и по loopback
внутри `pinger`. **Это не ЦОД — нижняя граница сетевого стека одной машины**: пакет не выходит в провод,
а проходит veth → мост → veth внутри одного ядра.

```
pinger → peer:  round-trip min/avg/max = 0.037/0.085/0.216 ms
127.0.0.1:      round-trip min/avg/max = 0.027/0.051/0.105 ms
```

Десятки микросекунд — это почти не сеть, а пробуждение процессора: за 0,2 с между пакетами ядро уходит
в глубокий сон (C-state), и каждый ответ начинается с пробуждения. Попробуйте на хосте
`ping -q -c 1000 -i 0.002 127.0.0.1` — при паузе 2 мс процессор не засыпает, и среднее падает в разы.
Между серверами в ЦОД добавляются сетевые карты и коммутаторы: обычно десятки–сотни микросекунд, так что
0,5 мс модели — консервативная оценка Дина 2009 года, а не замер.

### HDD — не мерилось

На машине нет вращающегося диска (`ROTA=0` у единственного), поэтому строки «HDD» шкалы — по даташиту.
Последовательно 7200-оборотный диск читает 150–285 МБ/с (Seagate Exos X20 — до 285 МБ/с), то есть 1 МБ
за 3,5–7 мс, а не 825 мкс модели; поиск дорожки плюс полоборота ожидания — несколько миллисекунд, до ~10.

## Чем ваши числа будут отличаться

Диапазоны ниже — ориентиры, а не замеры этой лабы: проверить их можно только своим прогоном.

- **Память.** DDR4 против DDR5, число каналов, частота — полоса одного ядра 10–30 ГБ/с, то есть
  35–100 мкс на 1 МБ. Задержка случайного обращения — 70–130 нс почти везде; на двухсокетном сервере
  обращение к памяти чужого сокета (NUMA) добавляет ещё десятки наносекунд. Если у вас L2 меньше 1 МиБ
  (многие Ryzen, старые Intel), строка «L2» покажет задержку L3.
- **SSD.** PCIe 3.0 или SATA, DRAM-кэш или его отсутствие, заполненность и температура диска. SATA SSD:
  4 КБ — около 100 мкс, 1 МБ подряд — ≈2 мс (≈550 МБ/с). Ноутбук в режиме экономии усыпляет NVMe
  (APST), и первые чтения после паузы дольше.
- **Облачная ВМ.** Сетевой диск (EBS, Persistent Disk) — это сеть: 4 КБ за 0,5–1 мс и `fsync` — столько же.
  Локальный NVMe инстанса близок к числам выше.
- **macOS и Windows (Docker Desktop).** Bind mount идёт через файловую систему виртуальной машины Docker
  (virtiofs), а не прямо на ваш диск: `fio` и `pg_test_fsync` измерят этот слой. Числа памяти — честные,
  если запускать `go run` на хосте.
- **Сеть.** Число RTT почти целиком зависит от энергосбережения процессора: на сервере с режимом
  `performance` и без глубоких C-state оно в разы меньше.
