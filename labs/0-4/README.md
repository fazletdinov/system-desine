# Лабораторная 0.4 — задержки на машине автора

Урок 0.4 «Числа задержек» строит шкалу по таблице Colin Scott («Latency Numbers Every Programmer
Should Know», значения для 2020 г.). Большая часть её чисел не измерена, а посчитана по трендам. Так
устроен исходник модели ([colin-scott/interactive_latencies](https://github.com/colin-scott/interactive_latencies),
файл `interactive_latency.html`):

- `getCycle` — частота 3 ГГц, постоянная с 2005 г.; L1 — 3 такта (1 нс), L2 — 13 тактов (4 нс);
- `getMemLatency` — обращение к RAM: постоянные 100 нс с 2000 г.;
- `getBusTransmissionDelay` — 1 МБ из RAM: полоса 4 ГБ/с в 2001 г., дальше удваивается каждые 3 года;
- `getSSDLatency` — случайное чтение с SSD: после 2014 г. постоянные 16 000 нс;
- `getSSDTransmissionDelay` — 1 МБ с SSD: полоса 3 ГБ/с в 2012 г., удваивается каждые 3 года;
- `getDCRTT` — RTT внутри ЦОД: постоянные 500 000 нс (в коде комментарий «Assume this doesn't change much?»).

Эта лаба меряет те же строки на одной настоящей машине: память — Go-программой, SSD — `fio`,
`fsync` — `pg_test_fsync`, сеть — `ping` между контейнерами. Шкале урока эти числа нужны как
«реально на машине автора» рядом с «по модели Scott».

```
0-4/
├── scenario.sh       # запускает всё, пишет results/; с --check — короткий прогон для check:labs
├── compose.yaml      # контейнеры fio, pg_test_fsync (postgres:18.6) и два busybox для ping
├── fio/              # образ с fio 3.39 на alpine 3.22 и скрипт одного замера (run.sh)
├── mem/              # Go: обход цепочки указателей (L1, L2, RAM) и чтение 1 МБ подряд
├── data/             # тестовые файлы диска во время прогона (в .gitignore, после прогона пуст)
└── results/          # выводы полного прогона: шапка машины, вывод замера, строки RESULT
```

## Запуск

Нужны Go 1.27 (`labs/go.mod`), Docker и около 4,5 ГБ свободного места на диске. Из каталога `labs/`:

```bash
bash 0-4/scenario.sh            # полный прогон, около 3 минут; перезаписывает 0-4/results/
bash 0-4/scenario.sh --check    # короткий, меньше минуты; только порядок величины, results/ не трогает
taskset -c 2 go run ./0-4/mem -mode latency   # одна память, без Docker
taskset -c 2 go run ./0-4/mem -mode seq
```

Сценарий запускает `mem` через `taskset -c 2`, если `taskset` есть: поток замера остаётся на одном ядре
процессора, иначе планировщик ОС может перенести его на ядро с холодными L1 и L2.

Тестовые файлы `fio` (4 ГБ) и `pg_test_fsync` пишутся в `0-4/data/` и удаляются в конце прогона, в том
числе при ошибке. Каталог должен лежать на настоящем диске: в tmpfs или в слое контейнера (overlay) `fio`
измерил бы память. Другой каталог — через `LAB04_DATA=/путь/на/диске bash 0-4/scenario.sh`. Сценарий
проверяет тип ФС на хосте (`df --output=fstype`), а `fio/run.sh` проверяет его ещё раз внутри контейнера
и пробует `O_DIRECT`. При tmpfs, overlay, ФС без `O_DIRECT` или без Docker он останавливается и объясняет
причину. Пробы `O_DIRECT` мало: tmpfs с Linux 6.6 принимает `O_DIRECT` и проба его не ловит.

Каждый файл `results/*.txt` начинается шапкой: CPU, ОЗУ, ОС, ядро, версии Go и Docker, ФС и модель
диска (`lsblk -d -o NAME,MODEL,ROTA,TRAN`), режим transparent hugepages, дата. Кончается файл строками
`RESULT <ключ> <значение> <единица>`: их читают `scenario.sh` и тесты курса. Ключи:

| файл | ключи |
| --- | --- |
| `mem-latency.txt` | `l1_random_ns`, `l2_random_ns` (256 КиБ), `l2_512k_random_ns`, `ram_random_ns` |
| `mem-seq-1mb.txt` | `ram_seq_1mb_us` |
| `ssd-randread-4k.txt` | `ssd_rand4k_lat_p50_us`, `ssd_rand4k_lat_p99_us`, `ssd_rand4k_lat_mean_us`; по clat — `ssd_rand4k_p50_us`, `ssd_rand4k_p99_us`, `ssd_rand4k_mean_us` |
| `ssd-seqread-1m.txt` | `ssd_seq1m_lat_p50_us`, `ssd_seq1m_lat_p99_us`, `ssd_seq1m_lat_mean_us`; по clat — `ssd_seq1m_p50_us`, `ssd_seq1m_p99_us`, `ssd_seq1m_mean_us` |
| `fsync.txt` | `fsync_ms` (fdatasync), `fsync_full_ms` (fsync) |
| `net-rtt.txt` | `rtt_container_us`, `rtt_localhost_us` (плотный ping); `rtt_container_idle_us`, `rtt_localhost_idle_us` (редкий) |

Рядом с выводами `fio` лежит его полный JSON (`*.fio.json`): там все перцентили, а не только p50 и p99.

«лучших» чисел из разных.

## Как читать числа

### mem — урок 0.4, строки «L1», «L2», «RAM»

Узлы массива занимают по 64 байта (одна строка кэша) и связаны в один случайный цикл по алгоритму
Саттоло. Обычное перемешивание дало бы несколько циклов, и обход мог бы застрять в маленьком цикле,
который целиком помещается в кэш. Следующий адрес известен только после загрузки текущего узла,
поэтому обращения не перекрываются, а аппаратный prefetcher не угадывает адрес. Время шага — задержка
одного обращения. Обход идёт по 16 КиБ (целиком в L1), 256 и 512 КиБ (в L2, но не в L1) и 256 МиБ
(в 14 раз больше L3). Печатается медиана 7 замеров.

```
случайное обращение, L1 (16 КиБ)        1.54 нс (медиана 7 замеров по 200000000 переходов)
случайное обращение, L2 (256 КиБ)       4.08 нс (медиана 7 замеров по 200000000 переходов)
случайное обращение, L2 (512 КиБ)       4.58 нс (медиана 7 замеров по 200000000 переходов)
случайное обращение, RAM (256 МиБ)    100.17 нс (медиана 7 замеров по 20000000 переходов)
```

- L1 — несколько тактов: загрузка плюс вычисление адреса следующего узла по загруженному индексу.
  Модель Scott (3 такта на 3 ГГц) это почти совпадает.
- L2 на 256 КиБ — 4,1 нс, как в модели. L2 меряется не «на весь L2», а с запасом. 1 МиБ — это 256
  страниц по 4 КиБ, и на нём замер собирал бы ещё промахи первого уровня TLB. Случайные адреса к тому же
  сталкиваются в наборах кэша, и часть строк уходит в L3. Уже на 512 КиБ число подрастает (4,6 нс), а на
  1 МиБ первая версия лабы показывала 6,9–8,0 нс: это смесь L2, L3 и TLB, а не задержка L2.
- RAM ≈ 100 нс совпадает с моделью. В это число входит промах TLB: 256 МиБ — это 65 536 страниц по
  4 КиБ, TLB помнит лишь малую их часть, и почти каждое обращение ещё ищет страницу в таблице страниц.
  Так выглядит случайный доступ к большим данным в обычной программе. Шапка показывает режим
  transparent hugepages: при `always` куча может попасть на страницы по 2 МиБ, и число станет меньше.

`-mode seq` читает подряд по мегабайту из буфера 256 МиБ, каждый раз следующий мегабайт по кругу.
К повторному чтению того же мегабайта прочитано ещё 255 МиБ, и он давно вытеснен из L3. Сумма идёт в
четыре аккумулятора, чтобы замер упёрся в память, а не в цепочку сложений.

```
последовательное чтение 1 МБ из буфера 256 МиБ: 59.0 мкс (17.8 ГБ/с; медиана 7 замеров по 4096 МБ)
```

59 мкс — это 18 ГБ/с с одного ядра. Модель Scott даёт 3 мкс, то есть ≈330 ГБ/с: так не умеет ни одна
настольная машина. Это экстраполяция полосы шины, которая в модели удваивается каждые 3 года. Вывод урока
не меняется: 1 МБ подряд — 59 мкс, а 1 МБ вразнобой — 16 384 строки по 100 нс ≈ 1,6 мс, в 28 раз дольше.

### ssd-randread-4k, ssd-seqread-1m — урок 0.4, строки «SSD»

`fio` читает в контейнере файл 4 ГБ на диске хоста. `--direct=1` — это O_DIRECT, чтение мимо page cache:
иначе повторное чтение шло бы из RAM. `--ioengine=libaio --iodepth=1` — программа держит в полёте один
запрос. Ещё два флага: `--runtime=20 --time_based`, а также `--clat_percentiles=1 --lat_percentiles=1`.

```
--rw=randread --bs=4k:  IOPS 16472; slat 5.9 мкс
                        lat:  среднее 59.3, p50 63.744, p90 67.072, p99 85.504, p99.9 138.24 мкс
                        clat: среднее 53.4, p50 57.088, p90 59.136, p99 71.168, p99.9 118.272 мкс
--rw=read --bs=1M:      полоса 3660 МБ/с; slat 101.3 мкс
                        lat:  среднее 285.4, p50 259.072, p90 329.728, p99 790.528, p99.9 2768.896 мкс
                        clat: среднее 184.1, p50 164.864, p90 201.728, p99 643.072, p99.9 2637.824 мкс
```

- Правило одно: строка шкалы — `lat` (`slat + clat`), время от вызова `io_submit` до завершения чтения,
  то есть то, что видит программа. `clat` (от отправки запроса до завершения) — для сравнения. Ключи
  без `lat_` в имени — по `clat`.
- 4 КБ вразнобой: p50 64 мкс, в 4 раза дольше 16 мкс модели. Сам диск обещает близкое: в
  [даташите Samsung 990 PRO](https://download.semiconductor.samsung.com/resources/data-sheet/Samsung_NVMe_SSD_990_PRO_Datasheet_Rev.1.0_10129514072296.pdf)
  случайное чтение 4 КБ при QD 1 — 22K IOPS для 1 ТБ, то есть ≈45 мкс на чтение. Остальное — путь через
  ядро и libaio.
- 1 МБ подряд: p50 259 мкс, в 5 раз дольше 49 мкс модели. Это **не задержка устройства при одном
  запросе**. Ядро режет 1 МБ на куски по `max_sectors_kb` (у этого диска
  `/sys/block/nvme0n1/queue/max_sectors_kb` = 128), и устройство получает около 8 запросов по 128 КБ
  сразу. Отправка этих кусков — заметная доля времени (`slat` 101 мкс), поэтому `clat` здесь занижает
  время. 3,7 ГБ/с при одном запросе программы в полёте; паспортные 7 450 МБ/с из того же даташита
  достигаются с глубокой очередью.
- Вывод урока «подряд дешевле, чем вразнобой» верен и здесь: 1 МБ подряд — 259 мкс, а 256 случайных
  чтений по 4 КБ — 256 × 64 мкс ≈ 16 мс, в 60 раз дольше.

### fsync — урок 0.3, «fsync ≈ 2 мс»

`pg_test_fsync` запускается из образа PostgreSQL 18.6 на том же каталоге, по 5 с на каждый метод.
Обе строки берутся из раздела «Compare file sync methods using one 8kB write». `fsync_ms` — строка
`fdatasync`: это значение `wal_sync_method` по умолчанию на Linux, а одна запись 8 КБ с синхронизацией —
то, что делает COMMIT с одной страницей WAL. Время считается из `ops/sec`, потому что в `usecs/op`
утилита округляет до целых микросекунд.

```
Compare file sync methods using one 8kB write:
        open_datasync                       274.585 ops/sec    3642 usecs/op
        fdatasync                           746.514 ops/sec    1340 usecs/op
        fsync                               164.325 ops/sec    6085 usecs/op
```

1,3 мс (1,3–1,9 мс в разных прогонах) — порядок «≈2 мс» из урока подтверждается. `fsync` той же записи
(`fsync_full_ms`) — 6,1 мс, в 4,5 раза дольше. `fsync` сбрасывает ещё и метаданные файла (время
изменения), а на ext4 это коммит журнала ФС. `fdatasync` сбрасывает метаданные, только если без них
данные не прочитать: например, когда изменился размер файла. Поэтому PostgreSQL заранее выделяет
сегменты WAL целиком и на Linux по умолчанию берёт `fdatasync`.

### net-rtt — урок 0.4, строка «RTT внутри ЦОД»

Контейнер `pinger` пингует контейнер `peer` в той же bridge-сети Docker, а затем loopback у себя внутри.
Каждый замер идёт в двух режимах. Число — медиана по строкам `time=… ms` отдельных пакетов, а не среднее
итоговой строки: единичные выбросы на сотни микросекунд (прерывание, вытеснение) сдвигают среднее,
а медиану — нет.

```
плотный, ping -c 500 -i 0.002:   peer — медиана 28 мкс,   127.0.0.1 — медиана 24 мкс
редкий,  ping -c 50  -i 0.2:     peer — медиана 125 мкс,  127.0.0.1 — медиана 101 мкс
```

- **Плотный режим (основные ключи) — нижняя граница сетевого стека одной машины, это не ЦОД.** Пакет не
  выходит в провод: он проходит veth → мост → veth внутри одного ядра. Пауза 2 мс меньше 0,2 с,
  поэтому busybox ping разрешает её только root; в контейнере ping и работает от root. В число входят
  оба прохода через стек и пробуждение процесса `ping` в userspace: busybox считает время сам, а не
  по метке ядра.
- **Редкий режим (`*_idle_us`)** — это обычный ping. За 0,2 с между пакетами процессор уходит в
  глубокий сон (C-state), и каждый ответ начинается с пробуждения ядра: отсюда в 4–5 раз больше. Так
  выглядит RTT редкого запроса на ненагруженной машине. Эффект убирают настройки энергосбережения:
  `sudo cpupower frequency-set -g performance` (на этой машине стоит `powersave`) и
  `sudo cpupower idle-set -D <мкс>`, который запрещает состояния сна с задержкой выхода больше заданной.
  На серверах с низкой задержкой так и делают.
- Между двумя серверами в ЦОД к этому добавляются сетевые карты, кабели и коммутаторы. 0,5 мс в модели
  Scott — постоянная, которую модель не пересчитывает по годам, а не замер. Эта лаба её не
  проверяет: у неё нет второго сервера.

### HDD — не мерилось

Вращающегося диска на машине нет (`ROTA=0` у единственного), поэтому строки «HDD» в шкале — по даташиту.
В [даташите Seagate Exos X20](https://www.seagate.com/content/dam/seagate/migrated-assets/www-content/datasheets/pdfs/exos-x22-channel-DS2080-2111US-en_US.pdf)
(документ DS2080 серии X20, хотя в имени файла стоит x22) указаны 7200 об/мин, максимальная
устойчивая скорость на внешних дорожках 285 МБ/с и средняя задержка вращения 4,16 мс. Значит, 1 МБ
подряд — не меньше 3,5 мс, а не 825 мкс модели. На внутренних дорожках скорость ниже, и время больше.
К случайному чтению добавляются поиск дорожки и в среднем пол-оборота ожидания (те самые 4,16 мс) —
это больше 2 мс модели.

## Чем ваши числа будут отличаться

Ниже — направления, а не замеры этой лабы. Насколько они сдвигают числа, покажет только ваш прогон.

- **Память.** Тип памяти (DDR4 или DDR5), число каналов и частота меняют полосу одного ядра, а с ней
  строку «1 МБ подряд». На двухсокетном сервере обращение к памяти чужого сокета (NUMA) дольше. Если L2
  меньше 512 КиБ, точка `l2_512k_random_ns` попадёт в L3. У гибридных CPU (Intel 12-го поколения и новее
  с E-ядрами) кэши и задержки P- и E-ядер разные: узнайте по `lscpu -e`, какое ядро производительное, и
  поменяйте номер в `taskset -c` в `scenario.sh`. У i5-12400 E-ядер нет.
- **SSD.** Поколение PCIe или SATA, наличие DRAM-кэша, заполненность и температура диска. SATA-диск
  упирается в интерфейс 6 Гбит/с, поэтому 1 МБ подряд у него заметно дольше. Ноутбук в режиме экономии
  усыпляет NVMe (APST), и первые чтения после паузы дольше.
- **fsync.** Серверные SSD с защитой от потери питания (PLP) считают свой кэш записи надёжным и отвечают
  на `fsync` намного быстрее потребительских, которые на каждую синхронизацию сбрасывают кэш во флеш.
- **Облачная ВМ.** Сетевой диск (EBS, Persistent Disk) — это сеть: и чтение 4 КБ, и `fsync` дольше, чем
  у локального NVMe. Локальный NVMe инстанса ближе к числам выше.
- **macOS и Windows (Docker Desktop).** Bind mount идёт через файловую систему виртуальной машины Docker,
  а не прямо на ваш диск, поэтому `fio` и `pg_test_fsync` измерят этот слой. Числа памяти честные, если
  запускать `go run` на хосте.
- **Сеть.** Редкий режим почти целиком зависит от энергосбережения процессора: с `performance` и без
  глубоких C-state он приближается к плотному.
