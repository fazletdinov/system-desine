## 1. Контекст и цель всего курса

**Для кого.** Для одного человека: Go-разработчика с опытом чуть больше года.
Цель — выйти на уровень Middle+/Senior в проектировании систем.

**Стек ученика:** Go, PostgreSQL, Docker, docker-compose, Git, Linux (Ubuntu), Redis, Kafka, Kubernetes.
С Kafka, Kubernetes и внутренним устройством PostgreSQL ученик знаком мало, поэтому их объясняем с нуля.

**Формат курса:**
- язык — русский, каждый термин поясняется (английский оригинал указывается рядом);
- теория опирается на признанные источники (см. раздел 7); материал излагается своими словами со ссылками на главы, книги не копируются;
- интерактивные пошаговые визуализации в духе AlgoMaster — обязательная часть, а не украшение;
- сквозной практический проект — мессенджер (аналог Telegram) на Go. Он растёт от монолита до распределённой системы в Kubernetes.

**Голос автора.** Курс написан от лица доктора наук в области компьютерных технологий и проектирования высоконагруженных систем. У автора глубокая экспертиза и опыт наставничества, он объясняет сложное простыми словами человеку, который только постигает азы. Это значит:
- **глубина не упрощается до неправды.** Упрощение допустимо, искажение — нет. Если модель упрощена, это явно сказано: «на самом деле чуть сложнее, вернёмся к этому в модуле N»;
- **простые слова, без жаргона без нужды.** Сложный термин вводится только тогда, когда он действительно нужен, и сразу объясняется;
- **от знакомого к новому.** Новое строится на том, что ученик уже знает: Go, повседневные аналогии, предыдущие уроки;
- **тон наставника, а не лектора.** Короткие абзацы, обращение на «вы», вопросы к ученику по ходу текста («как думаете, что случится, если…?»), признание того, что тема трудная;
- **научная честность.** Утверждения подкреплены источниками; где в индустрии нет единого мнения, это сказано прямо.

**Критерий успеха всего курса.** Ученик может:
- спроектировать систему уровня мессенджера, объясняя компромиссы каждого решения;
- реализовать ключевые части на своём стеке;
- пройти system design интервью.

### 2.1 Сквозные практики (во всех модулях)

- **ADR.** Каждое архитектурное решение по мессенджеру оформляется как ADR (Architecture Decision Record): контекст, варианты, решение, последствия. ADR лежат в `messenger/docs/adr/`.
- **Мини-интервью в конце каждого модуля.** Задача в формате 45-минутного system design интервью по материалу модуля. Эталонный разбор скрыт под спойлером.
- **Разбор реальной системы.** Где есть подходящий публичный материал (инженерные блоги и доклады Discord, Slack, WhatsApp и др.), модуль заканчивается уроком-кейсом.

### 2.2 Стандарт подробности объяснений

Подробность — главное требование ученика, поэтому она проверяется для каждого урока:

1. **«Зачем» до «как».** Урок начинается с конкретной проблемы, которую ученик может почувствовать: цифры, сбой, жалоба пользователя. Только после этого идёт решение.
2. **Каждый термин объяснён при первом появлении.** Определение даётся в тексте или через `<T>`. Английский оригинал указывается в скобках. Термины не используются «авансом».
3. **Ментальная модель или аналогия** для каждого нового механизма. Затем — где аналогия перестаёт работать.
4. **Конкретика вместо абстракций.** Числовые примеры, реальные команды, реальный вывод (`EXPLAIN`, `kubectl`, `tcpdump`), реальный код.
5. **Механизм на уровне «почему так работает».** Не «Kafka гарантирует порядок», а «порядок гарантируется внутри партиции, потому что…».
6. **Типичные заблуждения и ошибки** — отдельным блоком.
7. **Компромиссы явно.** Для каждого решения: что выигрываем, чем платим, когда не применять.
8. **Связь с остальным курсом.** Ссылки назад («это тот же WAL из модуля 2b») и вперёд.
9. **Самопроверка:** вопросы на понимание, а не на воспроизведение определений.

### 2.3 Стандарт визуализации

- **Каждый новый механизм** (алгоритм, протокол, поток данных) получает интерактивную визуализацию.
- **Диаграммы Mermaid** — только для статичной структуры (схемы компонентов). Процессы во времени показываются в `Player`.
- **Каждый урок** с механизмом содержит минимум одну интерактивную визуализацию.
- **Предпочтительный формат — песочница.** Где поведение зависит от действий (падение узла, добавление консьюмера, смена алгоритма), ученик должен иметь возможность «сломать» систему сам.
- **Каждый шаг визуализации** сопровождается пояснением на русском. Визуализация без текста не допускается.
- **Единый визуальный язык** во всём курсе: одинаковые цвета для клиента, сервиса, БД, кэша и брокера; одинаковое обозначение запроса, ответа и ошибки. Палитра и легенда описаны в `course/viz/README.md`.

## 4. Движок визуализаций

### 4.1 Принцип

Сценарий отделён от отрисовки:

```
Simulation (чистая функция)  →  Step[]  →  Player (управление)  →  Renderer (SVG)
```

### 4.2 Модель данных

```ts
interface Step<S> {
  state: S                 // полный снимок состояния системы на этом шаге
  highlight?: string[]     // id элементов, которые подсвечиваются
  caption: string          // пояснение на русском (может содержать термины)
  codeLine?: number        // строка в CodePanel, которая сейчас «выполняется»
}

// Режим «пошаговый разбор»: фиксированный сценарий
type Scenario<S> = () => Step<S>[]
```

`codeLine` подсвечивает строку в блоке кода, который VitePress рендерит через Shiki; `CodePanel` только переключает класс у `span.line`.

Тип `Simulation<S, A>` (песочница, порождающая шаги по действию пользователя) вводится вместе с первой такой визуализацией — в модуле 2.5 (алгоритмы балансировки). В модуле 0 песочница-калькулятор работает без шагов плеера.

- `state` — полный снимок, а не дельта. Поэтому переход назад и прыжок на любой шаг тривиальны.
- Симуляции и сценарии — чистые функции без зависимости от Vue. Они тестируются отдельно.

### 4.3 Компоненты

**`Player`.** Получает `steps` и слот для рендерера. Умеет:
- кнопки ⏮ ◀ ▶ ⏭ и ⏯;
- скорость 0.5×, 1× и 2×;
- полосу прогресса с переходом на любой шаг;
- клавиши ← / → / пробел, которые работают только когда плеер в фокусе;
- блок пояснения к текущему шагу.

**`CodePanel`.** Показывает фрагмент кода с подсветкой синтаксиса и выделяет строку `codeLine` текущего шага.

**Рендереры.** Vue-компоненты на SVG. Получают `state` и `highlight` и рисуют их.
- Простые переходы делаются средствами Vue/CSS.
- Движение объектов по траекториям (например, «пакет летит по стрелке») — через GSAP.
- Если пользователь включил `prefers-reduced-motion`, анимации заменяются мгновенной сменой кадра.

### 4.4 Визуализации подпроекта 1

1. **`request-path`** (пошаговый разбор). Путь запроса «Отправить сообщение»:
   1. клиент → DNS;
   2. TCP/TLS;
   3. балансировщик;
   4. сервер приложения;
   5. БД;
   6. ответ клиенту.

   На каждом шаге: подсвеченный узел, «летящий» пакет, пояснение и накопленная задержка.
2. **`latency-scale`** (интерактивная шкала). Справочные задержки (L1, RAM, SSD, сеть внутри ЦОД, межконтинентальный запрос) в двух режимах:
   - реальные значения в логарифмической шкале;
   - «человеческий масштаб», где 1 нс = 1 с.

   Числа приводятся со ссылкой на источник и с оговоркой, что это порядки величин.
3. **`estimation-calculator`** (песочница). Ползунки: DAU, сообщений на пользователя в день, средний размер сообщения, коэффициент пика, срок хранения, коэффициент репликации. Вывод по шагам:
   1. средний RPS;
   2. пиковый RPS;
   3. объём в день и за срок хранения;
   4. входящий трафик.

   Каждая формула видна. Калькулятор используется в уроках 0.5 и 0.6.

## 5. Глоссарий и термины

Формат `glossary/terms.yaml`:

```yaml
wal:
  term: WAL (журнал предзаписи)
  en: Write-Ahead Log
  short: Журнал, куда изменение записывается до изменения самих данных; нужен для восстановления после сбоя.
  long: |
    Подробное объяснение в Markdown...
  links:
    - title: Клеппман, гл. 3
```

- **В тексте:** `<T id="wal">WAL</T>`. Термин подчёркнут; при наведении или фокусе показывается `short`, клик ведёт на страницу глоссария. На сенсорных устройствах первое касание показывает определение, второе открывает глоссарий; Esc закрывает подсказку.
- **Несуществующий `id`** — ошибка сборки, а не молчаливый пропуск.
- **Страница глоссария** генерируется из YAML: сортировка по алфавиту, якорь у каждого термина.

## 9. Технические решения

| Решение | Выбор | Причина |

## 10. Проверка готовности

- `npm run build` проходит без ошибок и предупреждений о битых ссылках и терминах.
- `npm test` (Vitest) зелёный. Тестами покрыты:
  - логика плеера: переходы, границы, автопроигрывание;
  - симуляция калькулятора: формулы на контрольных значениях;
  - сценарий `request-path`: число шагов и инварианты;
  - валидация глоссария.
- Все уроки модуля 0 открываются, три визуализации работают мышью и с клавиатуры.
- Все термины модуля 0 имеют записи в глоссарии.
- Каждый урок модуля 0 проходит чек-лист стандарта подробности (раздел 2.2); визуализации соответствуют стандарту из раздела 2.3, включая палитру и легенду в `course/viz/README.md`.
- Корректный вид в светлой и тёмной теме и на ширине 375 px без горизонтальной прокрутки.
