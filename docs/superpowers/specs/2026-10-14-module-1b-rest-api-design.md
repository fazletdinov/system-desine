## 1. Цель и критерий успеха

**Цель.** Ученик проектирует HTTP API так, как это делают в больших компаниях, и может защитить каждое решение на собеседовании:
- почему метод и статус — часть контракта, а не украшение, и какие методы идемпотентны по RFC 9110;
- что такое contract-first, что из контракта ловит компилятор, а что только тест;
- зачем единый машиночитаемый формат ошибок (RFC 9457);
- почему offset-пагинация теряет и дублирует записи, а курсор — нет, и какую цену платит курсор;
- как сделать повтор запроса безопасным: естественный ключ против `Idempotency-Key`, и где каждый из них атомарен;
- как хранить пароли (Argon2id) и не выдать атакующему, существует ли пользователь;
- что JWT гарантирует (целостность и срок) и чего не гарантирует (секретность, мгновенный отзыв); какие атаки на проверку токена существуют.

**Критерий успеха:**
- код `messenger/` на теге `m01-l14` собирается, проходит `go test -race`, `go vet`, `golangci-lint` и проверку актуальности сгенерированного кода;
- каждый ответ API в тестах, включая ошибки, соответствует `api/openapi.yaml`; у каждой операции контракта есть хотя бы один проверенный ответ;
- сквозной сценарий урока 1.14 (регистрация → вход → чат с `Idempotency-Key` → повтор → сообщение с `client_message_id` → повтор → история с курсором → подделанный токен) даёт вывод, показанный в уроке;
- на каждом теге `m01-l08` … `m01-l14` код собирается и тесты проходят;
- заголовка `X-User-ID` в коде больше нет; запрос без валидного токена к закрытому маршруту получает 401.

### 3.2 Правила зависимостей (дополняют 1a §3.2, проверяет `depguard`)

- `auth/*` не импортирует `chat/*`. `auth/*` импортирует `user/*` только из `auth/adapters/userbridge` и только `user/usecase` и `user/domain` — как `userchecker` в 1a.
- `user/*` и `chat/*` не импортируют `auth/*`. Кто вызывает, они узнают только из `platform/principal`.
- `platform/*` не импортирует контексты. `httpauth` знает только свой порт `TokenVerifier`; реализацию из `auth/adapters/jwt` подставляет `main.go`.
- Сгенерированные пакеты `*/adapters/httpapi/gen` импортирует только свой `httpapi`.
- Строгие allow-list'ы для `domain` и `usecase` из 1a распространяются на `auth`.

### 3.3 Контракт и генерация

- `api/openapi.yaml` — OpenAPI **3.0.3** (oapi-codegen v2 полноценно поддерживает 3.0; поддержка 3.1 неполная — проверить на версии, закреплённой в плане). Пишется руками.
- Теги операций: `users`, `auth`, `chats`. У каждого контекста свой конфиг oapi-codegen с `include-tags`, генерация `std-http-server` + `models` в `*/adapters/httpapi/gen/`. Директива `//go:generate` в пакете адаптера.
- oapi-codegen подключается как инструмент через `tool` в `go.mod` (Go 1.24+), рантайм — `github.com/oapi-codegen/runtime`. Версии закрепляются в плане.
- Тело запроса читает наш `httpjson.Decode` (лимит 1 MiB, `DisallowUnknownFields`, один объект, 415) в сгенерированный тип. Ошибки разбора параметров пути и строки запроса из сгенерированной обёртки идут через её `ErrorHandlerFunc` в `problem` как `invalid_params`.
- Хендлеры реализуют сгенерированный `ServerInterface`; мапперы «gen-DTO ↔ команды use case'ов и доменные модели» остаются в адаптере. Доменные модели по-прежнему без тегов.
- **Контрактный тест:** помощник `openapitest` оборачивает `http.Handler` в тестах адаптеров и проверяет каждый ответ (статус, заголовки, тело) по контракту через `github.com/getkin/kin-openapi` (`openapi3filter.ValidateResponse`). Отдельный тест на уровне `main`-сборки: у каждой операции контракта есть маршрут и хотя бы один проверенный ответ.
- **Актуальность генерации:** `go generate ./...` и `git diff --exit-code` в `check:messenger`. В CI — в 1c.

- Параметры страниц: `limit` (1–100, по умолчанию 50, константы из 1a) и `cursor`. Параметр `after` из 1a удаляется.
- Имена полей в `invalid_params` совпадают с именами в контракте (закрывает пункт бэклога «имена полей против `{id}`»: параметр пути `{id}` называется в ошибке `id`).
- Неизвестный маршрут → 404, неверный метод → 405 с сохранённым `Allow`; оба в формате problem.

### 3.5 Ошибки (RFC 9457)

- `Content-Type: application/problem+json`. Поля: `type`, `title`, `status`, `detail`, `instance` (путь запроса). Расширения: `code` (стабильный машинный код), `request_id`, `invalid_params: [{name, reason}]`.
- `type` — абсолютный URI `https://messenger.example/problems/<code>` (домен `.example` зарезервирован RFC 2606 под примеры; урок объясняет, что в продакшене это страница документации).
- Реестр кодов — одна таблица в `platform/problem` и одна в контракте; тест сверяет, что множества совпадают.
- Политика из 1a сохраняется: внутренности только в `slog`, 5xx без деталей; отмена контекста запроса — без ответа; `DeadlineExceeded` → 503.
- 401 дополнительно несёт `WWW-Authenticate: Bearer` (с `error="invalid_token"`, если токен был, но не прошёл проверку — RFC 6750 §3).

### 3.6 Пагинация

- **История сообщений:** порт `MessageLister` меняется на «до `beforeSeq` по убыванию `seq`, не больше `limit`». Use case запрашивает `limit+1`; если пришло больше `limit` — есть `next_cursor` (по `seq` последнего отданного). Без курсора — с самых новых.
- **Список чатов:** новый use case `ListChats` и порт `ChatLister`: чаты, где пользователь участник, по убыванию `(LastActivityAt, ID)`. `LastActivityAt` равен времени создания и обновляется в `Chat.Post`.
- **Курсор:** `platform/cursor` кодирует base64url(JSON) с полем версии формата и видом курсора; курсор истории привязан к `chat_id`. Курсор не подписывается: подделка даёт лишь другую позицию, которую мы всё равно проверяем; урок разбирает, когда подпись (HMAC) нужна. Битый, чужой или неизвестной версии курсор → 400 `invalid_params: cursor`.
- Use case'ы получают обычные значения (`beforeSeq`, пару `(time, ChatID)`), про кодирование курсора не знают.

### 3.7 Идемпотентность

- **Сообщения — естественный ключ.** `client_message_id` (UUID, генерирует клиент, обязателен) в теле `POST /v1/chats/{id}/messages`. Хранилище гарантирует уникальность `(chat_id, author_id, client_message_id)`: `AppendMessage` возвращает `domain.ErrDuplicateMessage` вместе с уже сохранённым сообщением. Use case:
  - тот же текст → возвращает существующее сообщение, адаптер отвечает 200;
  - другой текст → `ErrClientMessageIDReused` → 409.
  Проверка уникальности и запись сообщения — одна операция хранилища, поэтому приём атомарен уже сейчас и останется атомарным в 2a (уникальный индекс).
- **`Idempotency-Key` — для `POST /v1/chats`.** Middleware в `platform/idempotency`, подключается к конкретным маршрутам в `main.go`, стоит после аутентификации.
  - Ключ: 1–255 печатных ASCII-символов; область — пара (пользователь, ключ). Без заголовка запрос обрабатывается как обычно.
  - Отпечаток: SHA-256 от метода, пути и тела. Тело читается с тем же лимитом 1 MiB и подставляется обратно.
  - Порт `Store`: `Reserve` атомарно создаёт запись «в работе» или возвращает существующую; `Complete` сохраняет статус, нужные заголовки (`Content-Type`, `Location`) и тело; `Release` удаляет запись.
  - Повтор с тем же отпечатком и готовым ответом → тот же ответ байт в байт плюс `Idempotent-Replayed: true`. Запись «в работе» → 409 `idempotency_in_progress`. Другой отпечаток → 422 `idempotency_key_reused`.
  - Сохраняются ответы 2xx и 4xx. После 5xx и после паники запись освобождается, чтобы повтор мог пройти.
  - Срок хранения — 24 часа (константа), время из порта `Clock`; просроченные записи удаляются при обращении.
  - **Честное ограничение:** запись ключа и создание чата — две разные операции. Если процесс упадёт между ними, повтор создаст второй групповой чат. ADR-0005 фиксирует это; в 2a запись ключа переезжает в ту же транзакцию.

### 3.8 Контекст `auth`, пароли, токены

- **Домен:**
  - `Password` — политика NIST SP 800-63B-4 для пароля как единственного фактора: минимум 15 символов Unicode, максимум 128 (с запасом над требуемыми NIST 64), без требований к составу; управляющие символы отклоняются. Цифры сверить с финальной редакцией NIST при реализации и сослаться в уроке.
  - `Credentials{UserID, PasswordHash}`; хеш — непрозрачная строка, домен не знает алгоритма.
  - Ошибки: `ErrInvalidCredentials` (одна на «нет пользователя» и «не тот пароль»), `ErrCredentialsExist`; `ValidationError` по образцу 1a.
- **Use case'ы:**
  - `SignUp`: проверить пароль → хешировать → `ProfileRegistrar.Register` (создаёт профиль в `user`) → `CredentialsStore.Save`. Ошибка на последнем шаге возвращается как ошибка сервера и оставляет профиль без пароля — фиксирует ADR-0004; закрывается в 2a единой транзакцией (unit of work, Фаулер), в модуле 6 — сагой или outbox.
  - `Login`: `UserLookup.IDByUsername` → `CredentialsStore.Find` → `PasswordHasher.Verify` → `TokenIssuer.Issue`. Если пользователя или учётных данных нет — всё равно `Verify` с фиктивным хешем (вычислен при сборке с теми же параметрами), затем `ErrInvalidCredentials`.
- **Порты (в `auth/usecase`):** `PasswordHasher{Hash, Verify}`, `TokenIssuer{Issue}`, `ProfileRegistrar`, `UserLookup`, `CredentialsSaver`, `CredentialsFinder`, `Clock`.
- **Argon2id:** `golang.org/x/crypto/argon2`, параметры не ниже минимума OWASP (m = 19 MiB, t = 2, p = 1 — сверить с актуальной редакцией памятки при реализации), соль 16 байт из `crypto/rand`, ключ 32 байта, формат PHC `$argon2id$v=19$m=…,t=…,p=…$соль$хеш`. `Verify` читает параметры из хеша и сравнивает через `subtle.ConstantTimeCompare`.
- **JWT:** `github.com/golang-jwt/jwt/v5`, алгоритм EdDSA (Ed25519).
  - Claims: `iss = "messenger"`, `aud = "messenger-api"`, `sub` = UserID, `iat`, `nbf`, `exp` = `iat` + 15 минут, `jti` (UUIDv7). Заголовок `kid` = отпечаток открытого ключа по RFC 7638.
  - Проверка: только `EdDSA` (`WithValidMethods`), обязательный `exp`, `iss`, `aud`, допуск на расхождение часов 30 секунд, известный `kid`. Время — из порта `Clock`.
  - Ключ: `MESSENGER_JWT_KEY_FILE` (PKCS#8 PEM) обязателен; без него сервис не стартует с понятным сообщением. `cmd/keygen` создаёт файл с правами 0600 и отказывается перезаписать существующий.
  - JWKS-эндпоинт, refresh-токены, отзыв и ротация ключей — модуль 6.7 (у JWKS появится потребитель — шлюз модуля 6).
- **`platform/httpauth`:** заголовок `Authorization: Bearer <token>`; нет заголовка или другая схема → 401; токен не прошёл проверку → 401 с `error="invalid_token"`. При успехе `sub` кладётся в `context` через `principal`. Маршрут закрыт, если он не перечислен в списке публичных в `main.go`.
- **Цепочка middleware:** `RequestID → AccessLog → Recover → httpauth → (idempotency на отдельных маршрутах) → mux`. `Recover` внутри `AccessLog`, чтобы паника попала в лог как 500. `RequestID` принимает входящий `X-Request-ID` только при допустимом формате, иначе генерирует свой, и возвращает его в ответе.

### 3.9 Внешние зависимости и окружение

- Новые модули: `github.com/oapi-codegen/oapi-codegen/v2` (инструмент), `github.com/oapi-codegen/runtime`, `github.com/golang-jwt/jwt/v5`, `golang.org/x/crypto`, `github.com/getkin/kin-openapi` (только тесты). Версии закрепляются в плане по состоянию на дату реализации и не моложе двух недель.
- Окружение: `MESSENGER_ADDR` (по умолчанию `127.0.0.1:8080`, как в 1a), `MESSENGER_JWT_KEY_FILE` (обязателен).
- Линтеры как в 1a; `depguard` дополняется правилами §3.2; сгенерированный код исключается из линтеров по пути `gen/`.

### 3.10 Связь с курсом и проверки

## 4. Визуализации

Движок 1a: `Scenario`/`Step`, `Simulation<S, A, F>`, `VizFrame` с полноэкранным режимом, `Player` (в том числе `startAtEnd`).

### 4.1 Песочницы

1. **`pagination`** (1.11).
   - Модель: лента из ~30 сообщений, клиент листает страницами по 5; два режима — offset и курсор.
   - Действия: «следующая страница», «вставить новое сообщение в начало», «удалить сообщение», «переключить режим», «сброс».
   - Вывод: прочитанные страницы, выделенные **дубли** и **пропуски**; для курсора — его раскрытое содержимое.
   - Тесты: при вставках между страницами offset даёт дубль, курсор — нет; при удалениях offset даёт пропуск, курсор — нет; без изменений оба режима дают одинаковую ленту.
2. **`idempotency`** (1.12).
   - Модель: клиент, сеть, сервер, хранилище ключей; запрос может потеряться на пути туда или на пути обратно.
   - Действия: «отправить», «потерять ответ», «повторить», «повторить параллельно», «повторить с другим телом», переключатель «без ключа / с ключом».
   - Вывод: сколько чатов создано, что вернул сервер (201, повтор ответа, 409, 422), состояние записи ключа.
   - Тесты: без ключа потеря ответа + повтор = два чата; с ключом — один и тот же ответ; параллельный повтор → 409; другое тело → 422; после 5xx повтор проходит.
3. **`jwt`** (1.14).
   - Модель: настоящий токен (заранее подписанный тестовым ключом, без криптографии в браузере не обойтись — проверка подписи выполняется через WebCrypto Ed25519, если браузер поддерживает; иначе — заранее посчитанные результаты; решение — в плане).
   - Действия: «изменить claim», «изменить байт подписи», «поставить `alg: none`», «перевести часы», «сменить `aud`».
   - Вывод: три части токена в раскраске, декодированный JSON, вердикт проверки и какое правило сработало.
   - Тесты: каждое действие даёт ожидаемый вердикт и правило; исходный токен проходит.

### 4.2 Пошаговые плееры

- **`request-pipeline`** (1.8): запрос проходит `RequestID → AccessLog → Recover → auth → mux → handler`; варианты сценария: успех, паника в хендлере, нет заголовка личности, неизвестный маршрут, неверный метод.
- **`contract-pipeline`** (1.9): `openapi.yaml` → `go generate` → сгенерированный интерфейс и DTO → наш хендлер → контрактный тест; два намеренных расхождения и где каждое ловится (компилятор против теста).
- **`problem-mapping`** (1.10): ошибка из домена, ошибка параметра, ошибка маршрутизатора и паника — как каждая превращается в problem+json; поля ответа подсвечены.
- **`login-timing`** (1.13): вход с несуществующим именем и с неверным паролем — наивная реализация (разное время и разный текст) против правильной (фиктивный хеш, один ответ); шкала времени показывает утечку.

### 4.3 Общие требования

Как в 1a §4.3: подписи на русском с `termId`, чистые функции с тестами Vitest, `VizFrame`, палитра `--viz-*`, узкая раскладка для 375 px, `prefers-reduced-motion`.

## 6. Попутно из бэклога

- Имена полей ошибок против параметра пути `{id}` — §3.4.
- 405 текстом — теперь problem+json с `Allow` (§3.4).
- Дублирование `queryInt`/`queryInt64` исчезает: параметры разбирает сгенерированная обёртка.
- Тесты адаптеров не различают `Canceled` от живого клиента — добавить в тесты `problem`.
- Esc в полноэкранном режиме — проверить живой клавишей в Playwright в проверке готовности (§8).

## 7. Вне рамок

- Refresh-токены, отзыв, ротация ключей, JWKS, RBAC, OAuth2/OIDC, rate limiting входа — модуль 6.7.
- Postgres, транзакции и перенос записи `Idempotency-Key` в транзакцию — модуль 2a.
- ETag и условные запросы, HTTP-кеширование — упоминаются в «Под капотом» урока 1.8.
- CI и Docker — часть 1c.
- Доставка в реальном времени — модуль 3.
- Генерация клиента по контракту и Swagger UI — не делаем; упоминаются в уроке 1.9.
