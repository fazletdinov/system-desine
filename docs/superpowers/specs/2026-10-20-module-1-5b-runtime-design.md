## 0. Место в курсе

Часть 1.5b закрывает модуль 1.5 «Конкурентность и рантайм Go». 1.5a научила писать конкурентный код; 1.5b объясняет, во что этот код превращается в рантайме, и учит **измерять**, а не гадать: где сервис тратит CPU, память и время ожидания.

## 1. Цель и критерий успеха

**Цель.** Ученик понимает, что рантайм делает за его код, и умеет это измерить:
- как блокирующий на вид `conn.Read` превращается в `epoll_wait` и парковку горутины; почему модель «горутина на соединение» масштабируется до 10⁵ соединений и сколько на самом деле стоит простаивающее соединение (свой замер против оценки урока 0.6);
- где живёт значение — на стеке или в куче, как это решает escape-анализ, как читать `-gcflags=-m`; как растёт и сжимается стек горутины; как устроен аллокатор (классы размеров, `mcache`/`mcentral`/`mheap`, tiny-аллокатор) и почему «меньше аллокаций» — главный рычаг производительности Go-сервиса;
- как работает сборщик мусора: трёхцветная разметка, барьер записи, фазы и паузы STW, помощь мутатора (mark assist), pacer и цель кучи, `GOGC` и `GOMEMLIMIT` вместе, спираль смерти и её ограничитель, Green Tea (по умолчанию с Go 1.26);
- как профилировать сервис: CPU, heap/allocs, goroutine, `goroutineleak`, mutex, block; как читать flame graph и `pprof -top/-list`; execution trace и flight recorder; PGO; почему профили снимают с продакшена, а не с ноутбука;
- как рассказать всё это на собеседовании (мини-интервью модуля).

**Критерий успеха** — §10.

## 3. Код мессенджера (урок 1.5.10)

### 3.1 Служебный порт (`platform/debugserver`)

- Отдельный HTTP-слушатель для `net/http/pprof`, как предусматривал ADR-0008 (вариант 5: «служебный порт — для метрик и pprof»). **ADR-0013** «Служебный порт и профилирование в продакшене» дополняет ADR-0008: pprof приезжает раньше модуля 12, потому что 1.5.10 профилирует живой сервис; пробы `/healthz`/`/readyz` **остаются** на основном порту до модуля 12 (решение автора: перенос проб — изменение контракта с оркестратором, а нужда в нём появится вместе с метриками).
- Регистрация обработчиков pprof — явно на своём `http.ServeMux` (`pprof.Index`, `Cmdline`, `Profile`, `Symbol`, `Trace` и `pprof.Handler(name)`), **не** через импорт `_ "net/http/pprof"` в `DefaultServeMux` (урок 1.7 уже объяснял, почему глобальный мультиплексор — плохо).
- Конфиг: `MESSENGER_DEBUG_ADDR`, по умолчанию пусто — слушатель выключен (безопасно по умолчанию: pprof раскрывает аргументы командной строки и стеки). В `compose.yaml` — `:6060` внутри контейнера, опубликован только на `127.0.0.1` хоста. Урок объясняет, чем опасен открытый pprof (CPU-профиль на 30 с — нагрузка, `cmdline`, стеки с данными) и как это закрывают в Kubernetes (порт не в Service, NetworkPolicy).
- Компонент жизненного цикла: слушатель — компонент `lifecycle` во **второй** стадии (фоновой): основной HTTP дренируется первым, служебный порт живёт до конца, чтобы можно было снять профиль зависшей остановки. Остановка — `Shutdown` с коротким сроком: идущий в этот момент `/profile?seconds=30` обрывается, урок и ADR-0013 это оговаривают; таймауты сервера: `WriteTimeout` больше максимальной длительности CPU-профиля/трассы (константа и проверка `seconds` сверху, иначе `?seconds=600` держит соединение), `ReadHeaderTimeout` как у основного.
- Профили mutex и block включаются при старте с умеренной выборкой (`runtime.SetMutexProfileFraction`, `runtime.SetBlockProfileRate`; значения и их цена — в плане по документации и замеру, решение автора — включены, когда включён служебный порт).
- Тесты: слушатель выключен при пустом адресе; `/debug/pprof/` отвечает на служебном порту и **не** отвечает на основном; лимит `seconds`; остановка вместе с компонентами (через `httpserver.Serve` + `net.Pipe`, как в 1.5a).

### 3.2 Зависимости и слои

- `platform/debugserver` знает только `net/http`, `net/http/pprof`, `runtime`, `platform/httpserver` и порт рекордера; `platform/flightrec` — `runtime/trace`. Собираются в `app.go`. Правила `depguard`: `net/http/pprof` разрешён только в `platform/debugserver` (это же запрещает пустой импорт, регистрирующий pprof в `DefaultServeMux`), `runtime/trace` — только в `platform/flightrec`.

### 3.3 Flight recorder

- В процессе может быть активен только один `trace.FlightRecorder`, поэтому он один на процесс: создаётся и запускается в composition root при старте, middleware получает узкий порт (`WriteTo`) и не владеет записью. `MinAge` окна обязан быть больше `MESSENGER_FLIGHT_THRESHOLD` (проверка конфига; иначе снимок не содержит медленного запроса), `MaxBytes` — потолок памяти. Пакет — `platform/flightrec` (рекордер, порог, ограничение частоты); middleware в `platform/middleware` зависит только от его порта. Он и при запросе дольше порога пишет снимок в каталог (`MESSENGER_FLIGHT_DIR`; пусто — выключено) не чаще одного раза в интервал (иначе медленный период завалит диск снимками). Рекордер запускается, когда задан `MESSENGER_DEBUG_ADDR`: тогда снимок всегда доступен на служебном порту `GET /debug/flight`, а запись файлов по медленным запросам включается дополнительно `MESSENGER_FLIGHT_DIR` (решение автора: файл — для продакшена, эндпоинт — для урока).
- Цена включённого трассировщика (по release notes 1.21 — 1–2 % CPU; сверяется в плане) замеряется в лабе/уроке и указывается.
- Тесты: снимок пишется при медленном запросе, не пишется при быстром, повторный медленный в пределах интервала не пишет второй файл (время — `synctest`).

### 3.4 Чего мессенджер не получает

- PGO (`default.pgo`) — только лаба: профиль учебной нагрузки не представляет продакшен, а закоммиченный «нерепрезентативный» профиль — антипаттерн; урок объясняет, когда его включать (решение автора).
- Метрики Prometheus и `runtime/metrics`-экспорт — модуль 12.

### 3.5 Конфиг (новое)

| Переменная | По умолчанию | Проверка |
|---|---|---|
| `MESSENGER_DEBUG_ADDR` | пусто (выключено) | `host:port` или пусто |
| `MESSENGER_FLIGHT_DIR` | пусто (выключено) | существующий каталог или пусто; требует `MESSENGER_DEBUG_ADDR` |
| `MESSENGER_FLIGHT_THRESHOLD` | `1s` | `time.ParseDuration`, > 0 и меньше окна рекордера (константа `MinAge`, например 10 с) |

Имена — константами (как в 1.5a), тесты табличные, `compose.yaml` и README мессенджера обновляются.

## 5. Визуализации

### 5.1 Песочницы

1. **`escape-lab`** (1.5.8). Набор из 8–10 коротких функций (выбор из списка); у каждой переключатели, меняющие одну деталь (вернуть значение/указатель, размер массива константа/переменная, передать в `fmt.Println`/в свою функцию, `//go:noinline`). Вывод: где окажется значение (стек/куча) и **реальная** строка `-gcflags=-m` для этого варианта. Данные — таблица, снятая на Go 1.27.2 скриптом в лабе (не вычисляется в браузере — компилятор не моделируем; решение автора), тест сверяет, что для каждого варианта есть снятая строка.
2. **`gc-pacer`** (1.5.9). Модель: живая куча, скорость аллокаций, `GOGC`, `GOMEMLIMIT`, лимит контейнера; во времени — куча, цель, доля CPU на GC, число циклов, OOM. Действия: ползунки, «утечка» (живая куча растёт), «всплеск аллокаций». Развивает модель `gomemlimit` из 1.17 (переиспользует её формулы, добавляет ограничитель 50 % и `GOGC=off`). Тесты: при `GOGC=100` без лимита цель = 2× живой; лимит ниже цели поднимает частоту GC; живая куча выше лимита — CPU GC упирается в 50 %, а не в 100 % (ограничитель); `GOGC=off` без лимита — GC не запускается.
3. **`flamegraph`** (1.5.10). Интерактивный flame graph по реальному профилю мессенджера: наведение — имя функции, доля; клик — увеличение поддерева; поиск по имени с подсветкой; переключение CPU/alloc_space/inuse_space. Тесты: свёртка стеков в дерево, доли в сумме 100 %, зум сохраняет доли относительно корня поддерева.

### 5.2 Пошаговые плееры

- **`netpoller`** (1.5.7): `conn.Read` → `EAGAIN` → горутина паркуется на `pollDesc`, M свободен → данные пришли → `epoll_wait` в `findRunnable` возвращает событие → горутина готова → читает. Вариант «дедлайн истёк».
- **`tricolor`** (1.5.9): разметка небольшого графа объектов; мутатор во время разметки перекладывает указатель с серого на чёрный; без барьера — белый объект потерян (подсветка «освобождён живой»); с барьером — затенён и сохранён.

## 9. Решения автора (сводка для ревью)

1. Пять уроков 1.5.7–1.5.11 в той же папке, теги `m01-5-l07…l11`.
2. Замер 10⁴/10⁵ соединений — лаба без Docker на loopback с несколькими адресами; в CI — короткий режим 10³.
3. Служебный порт для pprof приезжает в 1.5.10 (раньше модуля 12), выключен по умолчанию, в compose — только на 127.0.0.1; пробы остаются на основном порту; ADR-0013.
4. Обработчики pprof регистрируются явно на своём мультиплексоре; `net/http/pprof` разрешён `depguard` только в `platform/debugserver`.
5. Служебный слушатель останавливается во второй стадии, после основного HTTP.
6. Профили mutex/block включены вместе со служебным портом.
7. Flight recorder в мессенджере: один рекордер на процесс, снимок по медленному запросу в файл с ограничением частоты + эндпоинт на служебном порту.
8. PGO — только в лабе, мессенджер `default.pgo` не получает.
9. `escape-lab` показывает снятые реальные строки компилятора, а не модель; `gc-pacer` развивает модель `gomemlimit` из 1.17.
10. Flame graph — на реальном профиле мессенджера, закоммиченном как данные курса.
11. Мини-интервью — формат 1.20 и `InterviewSim` с новым банком.

## 10. Проверка готовности

- `npm test`, `npm run typecheck`, `npm run check:go`, `npm run check:labs`, `npm run check:messenger`, `npm run check:refs`, `npm run check:workflows`, `npm run build` проходят.
- На каждом теге `m01-5-l07…l11`: `go build ./...`, `go test -race ./...` в `messenger/` и `labs/` проходят; `golangci-lint` без замечаний; новые пакеты мессенджера — `-count=20` без падений, без `time.Sleep` для ожидания.
- `docker compose up`: `curl 127.0.0.1:6060/debug/pprof/` отвечает, основной порт на `/debug/pprof/` — 404; CPU-профиль под `overload.sh` снимается и открывается; медленный запрос даёт файл flight recorder; `docker compose stop` — служебный порт останавливается после основного, код 0.
- Замер соединений: реальные числа 10⁴ и 10⁵ в уроке 1.5.7 с описанием машины и сравнением с оценкой 0.6.
- Playwright на 375 и 1280 px, тёмная и светлая тема, уроки 1.5.7–1.5.11: без горизонтальной прокрутки, песочницы реагируют, полноэкранный режим, mermaid без обрезки.
- Ревью фактов по исходникам Go 1.27.2 (`runtime/netpoll.go`, `netpoll_epoll.go`, `stack.go`, `malloc.go`, `internal/runtime/gc/sizeclasses.go`, `mgc.go`, `mgcpacer.go`, `mbarrier.go`, `runtime/pprof`, `runtime/trace`), Go GC Guide (go.dev/doc/gc-guide), release notes 1.19–1.27, документации `cmd/compile` (`-m`) и `cmd/pprof`; внешний источник не нужен для понимания.
