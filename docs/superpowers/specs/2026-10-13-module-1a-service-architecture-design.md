## 1. Цель и критерий успеха

**Цель.** Ученик умеет построить Go-сервис так, чтобы бизнес-логику не приходилось переписывать при смене хранилища (модуль 2a), транспорта (модули 3 и 6) или формата API (1b). Он может объяснить на собеседовании:
- что такое правило зависимостей и зачем порт объявляют у потребителя;
- где проверять инварианты и почему не в HTTP-обработчике;
- как устроены ошибки в Go и где их переводят в коды ответа;
- как `context` отменяет работу по всей цепочке вызовов;
- чем фейк отличается от мока и что такое контрактный тест порта.

**Критерий успеха:**
- код `messenger/` на теге `m01-l07` собирается, проходит `go test -race`, `go vet` и `golangci-lint` без замечаний;
- сервис запускается командой из урока 1.7, а сценарий через `curl` (создать двух пользователей, чат, отправить и прочитать сообщения) даёт вывод, показанный в уроке;
- на каждом теге `m01-l01` … `m01-l07` код собирается и тесты проходят;
- добавление запрещённого импорта (например, `chat/domain` → `chat/adapters/memory`) роняет `golangci-lint` с понятным сообщением.

## 3. Код мессенджера

### 3.1 Раскладка

```
messenger/
├── go.mod                        # module messenger, go 1.26
├── .golangci.yml                 # golangci-lint v2, depguard — правила слоёв
├── cmd/messenger/main.go         # composition root
├── internal/
│   ├── user/
│   │   ├── domain/
│   │   ├── usecase/
│   │   └── adapters/{memory,httpapi}/
│   ├── chat/
│   │   ├── domain/
│   │   ├── usecase/
│   │   └── adapters/{memory,httpapi,userchecker}/
│   └── platform/                 # отдельные пакеты по смыслу, не «utils»
│       ├── clock/
│       ├── idgen/
│       └── httpserver/
└── docs/adr/
    ├── 0000-template.md
    ├── 0001-раскладка-по-контекстам.md
    └── 0002-x-user-id-до-jwt.md
```

Имена файлов ADR и точные имена пакетов `adapters/*` уточняются в плане; правило — пакет называется по смыслу.

### 3.2 Правила зависимостей (проверяет `depguard`)

- `*/domain` импортирует только стандартную библиотеку (без `net/http`, `database/sql`, `encoding/json`, `log/slog`).
- `*/usecase` импортирует только свой `domain` и стандартную библиотеку. Время и идентификаторы приходят через порты `Clock` и `IDGenerator`, объявленные в `usecase`; их реализации в `platform/*` подключаются в `main.go`. Импорт адаптеров и `platform/*` из `usecase` запрещён.
- `*/adapters/*` не импортируют другие адаптеры.
- `chat/*` не импортирует `user/*` и наоборот. Связь — через порт `UserChecker` в `chat/usecase`, его реализацию в `chat/adapters/userchecker` над `user/usecase` и сборку в `main.go`. Это исключение из «адаптеры не знают друг о друге» оформлено правилом `depguard` и объяснено в уроке 1.7: адаптер `userchecker` зависит от **use case** другого контекста, а не от его адаптеров; в модуле 6 он станет gRPC-клиентом.
- Доменные структуры без тегов `json:` и `db:`.

### 3.3 Домен v0

- **Пользователь:** `UserID` (UUIDv7), `Username` — 3–32 символа из `[a-z0-9_]`, уникален; `DisplayName` — 1–64 символа.
- **Чат:** `ChatID` (UUIDv7), вид `direct` (ровно 2 разных участника; повторное создание личного чата для той же пары возвращает существующий) или `group` (2–200 участников, название 1–128 символов). Создатель обязан входить в участников.
- **Сообщение:** `MessageID` (UUIDv7), автор, текст 1–4096 символов Unicode после обрезки пробелов по краям, время, `seq` — номер внутри чата, начиная с 1, без пропусков.
- **Инварианты агрегата `Chat`:** отправитель — участник; `seq` следующего сообщения = последний + 1. Агрегат хранит `version`; хранилище сохраняет с проверкой версии (`ErrConcurrentUpdate`), use case повторяет до 3 раз.
- **Чтение истории:** порт `ListMessages(ctx, chatID, afterSeq, limit)`, `limit` 1–100 (по умолчанию 50). Читать может только участник.
- Все лимиты — именованные константы в `domain`.

### 3.4 Внешние зависимости и окружение

- Только стандартная библиотека Go 1.26. Исключение — генерация UUIDv7: если в stdlib 1.26 её нет, берётся `github.com/google/uuid` (версия закрепляется в `go.mod`). Решение и проверка фиксируются в отчёте задачи.
- `golangci-lint` v2 (у автора 2.12.2). Набор линтеров в `.golangci.yml`: стандартный (`errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused`) плюс `depguard`, `errorlint`, `wrapcheck` — последний только если не даёт шума на адаптерах; финальный набор — в плане.
- HTTP-сервер: адрес из `MESSENGER_ADDR` (по умолчанию `:8080`), таймауты сервера как в уроке 0b.6 (`ReadHeaderTimeout` и др.). Корректное завершение по сигналу — минимальное (`signal.NotifyContext` + `Shutdown`); подробно — модуль 1.5.

### 3.5 Связь с курсом

- Фрагменты кода в уроках подключаются только из настоящих файлов через `<<< @/../messenger/...#region` (регионы `// #region имя` … `// #endregion`). Код в уроке не расходится с рабочим.
- Код, которого нет в мессенджере (антипримеры «большого кома», неправильные варианты), проверяется `check:go` через маркер `<!-- go-check -->`, как в 0b.
- Теги `m01-l01` … `m01-l07` ставятся на коммит, завершающий урок. Если ревью урока меняет код, тег переносится на новый коммит (`git tag -f`) до слияния ветки — после слияния теги не двигаются.

Новый скрипт `npm run check:messenger` (по образцу `check-labs.ts`):

- `go vet ./...`;
- `golangci-lint run ./...`;

- **проверка регионов:** каждый `<<< @/../messenger/...#имя` в уроках указывает на существующий файл и существующий регион (закрывает пункт бэклога про непроверяемые регионы; проверка распространяется и на `labs/`).

## 4. Визуализации

Используется существующий движок: `Scenario`/`Step` для плееров и `Simulation<S, A, F>` для песочниц (раздел 4 спецификации 0b), `VizFrame` с полноэкранным режимом.

### 4.1 Песочницы

1. **`deps`** (урок 1.1).
   - Модель: пакеты мессенджера (domain, usecase, adapters, infrastructure для `user` и `chat`) и разрешённые импорты.
   - Действия: «добавить импорт A → B» из списка кандидатов, «сбросить».
   - Вывод: граф с подсветкой; для запрещённого импорта — какое правило нарушено и что сломается (например, «чтобы заменить хранилище на Postgres, придётся менять домен»); для цикла — «Go не соберёт: import cycle».
   - Тесты: каждое правило §3.2 даёт нарушение на своём кандидате; разрешённые импорты нарушений не дают.
2. **`ctx-tree`** (урок 1.5).
   - Модель: дерево контекстов (корень → запрос с таймаутом → use case → хранилище и параллельный вызов `UserChecker`), часы в тиках.
   - Действия: «отменить узел», «прошло N мс», «отвязать узел (`WithoutCancel`)», «сброс».
   - Вывод: какие узлы отменены, с какой причиной (`Canceled` или `DeadlineExceeded`), какие «горутины» остановились.
   - Тесты: отмена родителя отменяет всех потомков; отмена потомка не трогает родителя; дедлайн потомка не позже дедлайна родителя; `WithoutCancel` не получает отмену.

### 4.2 Пошаговые плееры

- **`validation-gates`** (1.2): сырой ввод → DTO → конструктор объекта-значения → агрегат; на каких воротах отсекается какой ввод.
- **`error-chain`** (1.3): ошибка хранилища оборачивается в use case и адаптере; на каждом шаге — строка `Error()`, что вернут `errors.Is(err, ErrChatNotFound)` и `errors.As(err, &ve)`, какой статус выберет адаптер.
- **`layer-flow`** (1.4): `POST /chats/{id}/messages` сквозь слои; на каждом шаге — какой пакет работает, какие типы он видит, где проверяется инвариант, где оптимистическая блокировка и повтор.
- **`test-layers`** (1.6): набор намеренных багов (нарушен инвариант, неверный маппинг статуса, гонка в хранилище, сломанный SQL в будущем адаптере) и какой уровень тестов ловит каждый.
- **`http-mapping`** (1.7): JSON → DTO → команда use case → доменная модель → DTO ответа → JSON; где проходят границы моделей и почему доменная модель не сериализуется напрямую.

### 4.3 Общие требования

Как в 0b §4.4: подписи на русском с `termId`, чистые функции с тестами Vitest, `VizFrame`, палитра `--viz-*`, узкая раскладка для 375 px, `prefers-reduced-motion`.
